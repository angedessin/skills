# frontend-code-review

見つける役と確かめる役を分け、確かめられた指摘だけを返す。指摘を返したら止まる。直すのは頼まれたときだけ。

<!-- validator: no-stop-needed — 承認の止まりどころを持たない。指摘を返すだけで、作業ツリーは変えない -->

## When NOT to use

- PR に付いたレビューコメント・CI の失敗への対応 → このスキルを使わない
- 原因の分からないバグの調査 → このスキルを使わない

## Step 1 — 対象を決める

- 対象は、頼まれた範囲（指定が無ければ未コミットの変更すべて。未追跡のファイルも含む）。`git status --short` と `git diff HEAD --stat` で確かめる
- 変更が無い、または自明な変更（typo・コメントだけ・生成物だけ）なら、レビューせずにそう伝えて終わる
- 差分を作業ツリーの外に書き出す: `git diff HEAD > "${TMPDIR:-/tmp}/review.patch"`。agent は git を使えないので、このファイルと未追跡ファイルのパスを渡す
- 規約の資料を集める: 変更ファイルに関係する CLAUDE.md（ルートと変更ファイルの上の階層）・`docs/knowledge/`・`.steering/` の design.md。無ければ「規約の資料なし」として進む

## Step 2 — 一次レビュー（並列）

agent は**前面で**一度に起動し、全員の結果が返るまで待つ（`run_in_background` を使わない。待たずにターンを終えると結果が失われる）。

| agent | 起動する条件 | 渡す範囲 |
|---|---|---|
| `review-bug` | 常に | 差分だけ（patch と変更行） |
| `review-bug` | 常に | 差分と、変更コードの呼び出し元・呼び出し先・同じファイルの周辺 |
| `review-rules` | 常に | 差分と、Step 1 で集めた規約の資料 |
| `review-ui-a11y` | `*.tsx`・`*.jsx`・`*.css` の変更があるとき | 変更した UI のファイル |
| `review-test` | テストファイル（`*.test.*`・`*.spec.*`・`tests/`）の変更があるとき | 変更したテストと、テスト対象のファイル |

依頼文には、patch のパス・未追跡ファイルのパス・渡す範囲・規約の資料のパスを書く。パフォーマンスとセキュリティは、バグ担当が該当する変更を見つけたときに扱う（担当を分けない）。

## Step 3 — 指摘ごとの検証

一次レビューの指摘を集め、同じ問題はまとめる。まとめた指摘の一覧を `review-verify` に渡し、1 件ずつ本当に問題かを確かめさせる（これも前面で待つ）。

- 検証役が「確かめられた」とした指摘だけを残す。「確かめられない」「問題ではない」は捨て、件数と理由を 1 行ずつ残す
- 自分で再現を試すときは、作業ツリーを `${TMPDIR:-/tmp}` にコピーした上で行う。リポジトリの中に一時ファイル・一時テストを作らない

## Step 4 — 報告して止まる

返答に、残った指摘を**すべて**重要度順に書く（High・Medium・Low。件数だけにまとめない）。各指摘に書くこと:

- 場所（ファイルと行）・何が問題か・どう壊れうるか（具体的な入力と結果）・直し方の方向
- 確かめ方（再現した / コードを読んで確かめた）

続けて、捨てた指摘の件数、レビューできなかったもの（実行できなかったコマンド・読めなかったファイル）を書く。

`.steering/` に変更に対応する作業のフォルダがあれば、同じ内容を `review-result.md` に書く。無ければ返答だけでよい。

**ここで止まる。** コードは直さない。直すかどうか・どれから直すかはユーザーが決める。

## Related agents

- `review-bug`・`review-rules`・`review-ui-a11y`・`review-test` — 一次レビュー
- `review-verify` — 指摘ごとの検証
