# impl-from-design

承認済みの設計を、設計どおりに、確かめられる形で作る。

- 設計が `APPROVED` か `SPIKE` でなければ実装せず、**ここで止まる**
- 設計の前提がコードと食い違い、設計の約束（対象と対象外・API の形・振る舞い）が変わるなら、委任されていても**ここで止まり**、どうするか聞く
- 「確認は要らない」「最後まで進めて」と言われたら、上の 2 つ以外では止まらずに最後まで進める

## When NOT to use

- `.steering/` に設計が無い小さな修正 → そのまま直す（バグなら `tdd`）
- 設計がまだ無い・設計を直したい → `design-doc`
- 進み具合の確認だけ・再開の相談 → `steering`

## 1. 読んで、実装してよいか確かめる

タスクのディレクトリの design.md・tasklist.md・decisions.md（あれば）を読む。decisions.md に design.md より新しい決定があれば、新しい方を正とする。

| Status | 動き |
|---|---|
| `APPROVED` | 進める |
| `SPIKE` | 試し実装として進める。push・PR などの外向きの操作はしない |
| `DRAFT`・無い・ほかの値 | 実装しない。未承認であることと、承認されたら最初にやる項目を示して**ここで止まる** |

Status を自分で書き換えない。

## 2. 設計の前提をコードで確かめる

書き始める前に、設計が頼っているものが本当にあるかを読む: 呼ぶ関数や API の引数、型、モック（MSW のハンドラなど）、触るファイル、既存のテスト。

食い違いを見つけたら、扱いを分ける。

| 食い違い | 扱い |
|---|---|
| 設計の約束が変わらない（ファイルの置き場所・関数名・内部の分け方など） | 合わせて進め、decisions.md に 1 行残し、最終回答でも伝える |
| 設計の約束が変わる（対象外にしたものを変えないと作れない・API の形や振る舞いが設計と違う） | 実装しない。何が食い違うか、取れる道（設計を直す・対象を広げる・別の方法）と推奨を示して**ここで止まる** |

「確認は要らない」と言われていても、後者は委任の範囲を超えるので聞く。黙って別の方法で埋めない。

## 3. 進める

- tasklist.md の未チェックの項目を上から進める
- 振る舞いは、設計の「振る舞い」と「完了条件」をテストで確かめる。先に失敗するテストを書いてから実装するのを基本にする（テストの書き方は `tdd` の考え方に従う。無ければ: ユーザーの操作と画面に見える結果で確かめる・HTTP の境界でモックする・内部の実装をなぞらない）
- 設計に書いていない振る舞いを足さない。必要だと気づいたら、足さずに最終回答の論点に挙げる
- 項目を終えるごとに tasklist.md にチェックを付け、日付と要点を短く添える

## 4. 確かめて報告する

- テスト（と型検査があれば型検査）を実際に流す。流せなかったときはそう書く
- 最終回答に書くこと: 終えた項目・流したコマンドと結果（通った数・落ちたもの）・設計から外れたところと記録した場所・残った項目と論点
- 流していないものを「通った」と書かない。確かめていないことは「未確認」と書く

## 外向きの操作

commit・push・PR は頼まれたときだけ行う。SPIKE では頼まれても push・PR はしない（DRAFT に戻して設計を直すのが先）。
