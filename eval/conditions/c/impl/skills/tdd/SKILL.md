# tdd

振る舞いを先にテストで決め、テストに導かれて実装する。

- 依頼から「入力 → 期待する、外から見える結果」の一覧を作り、上から 1 つずつ Red → Green → Refactor で進める
- 一覧は回答に示すが、それで止まらずに進める。ユーザーが「一覧を見せて」と頼んだときだけ、示して**ここで止まる**
- 期待する振る舞いが依頼から決まらない（どちらにも取れる）ときだけ、選択肢と推奨を示して**ここで止まる**

## When NOT to use

- ブラウザで画面をまたぐ流れのテスト → `e2e`
- 承認済みの設計からの実装 → `impl-from-design`（テストの書き方はこのスキルの考え方を使う）
- 捨てる前提の試作 → テストは求めない

## 1. 一覧を作る

依頼を、1 テスト 1 振る舞いの一覧に分ける。正常系に加えて、次から当てはまるものを入れる:

- 空・空白だけ・前後の空白・最大と最小・0 件と 1 件
- 失敗（HTTP エラー・例外）と、そのときユーザーに見えるもの
- 何かを「しない」こと（送らない・呼ばない・表示しない）も振る舞いとして確かめる

バグの修正では、まずバグを再現するテストを一覧の先頭に置く。

## 2. Red → Green → Refactor

1. **Red:** 一覧の 1 件だけをテストにして流し、**正しい理由で**落ちることを見る（import の誤りや型エラーで落ちるのは Red ではない）
2. **Green:** 通る最小の実装を書く。バグは原因のある場所で直す（テスト用のモックやテストの側を直して通さない）
3. **Refactor:** テストが通ったまま、重複や名前を整える
4. 全テストを流してから次の 1 件へ

テストファイルを先に書き、実装のファイルはその後に触る。途中で気づいた振る舞いは、その場で実装せずに一覧に足す。

## 3. テストの書き方

- **振る舞いを見る:** ユーザーの操作（入力・クリック・選択）と、画面に見える結果で確かめる。内部の state・関数の呼び出し回数・実装の分岐をなぞらない
- **探し方:** 役割とアクセシブルな名前 → ラベル → 表示文字列の順。CSS セレクタや DOM 構造に頼らない。「無い」ことは、見つからなくても例外にならない探し方（queryBy など）で確かめる
- **モックの境界:** HTTP の境界でモックする（MSW の `server.use` など）。自分たちのモジュールをモックしない。日時や乱数など外から決まらないものだけはモジュール単位でモックしてよい
- **1 テスト 1 振る舞い:** 名前に期待する振る舞いを書く。準備・操作・確認の順に並べる
- テストの置き場所と流し方は、プロジェクトの既存のテストに合わせる

## 4. 報告する

最終回答に書くこと:

- 足したテストの一覧（振る舞いで書く）
- Red で落ちたこと（どのテストが、どんな理由で）と、Green で通ったこと
- 流したコマンドと結果（通った数・落ちたもの）。流せなかったときはそう書く

流していないテストを「通った」と書かない。
