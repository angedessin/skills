# design-doc

実装の前に、決めることを決めて人間に見せる。**設計を示したらここで止まり、承認を待つ。実装には入らない。**

- 大きな作業（複数セッション・あとで経緯を辿りたい）→ `.steering/` に design.md と tasklist.md を書いて止まる
- 中くらいの作業（1 セッションで終わるが決めることがある）→ 会話の中で設計を示して止まる
- 小さな作業 → このスキルを使わない

## When NOT to use

- typo・数行の修正・文言の変更・調査だけの依頼 → そのまま進める。設計の確認や段階の質問もしない
- `.steering/` に同じタスクがある（再開・続き・状況確認）→ `steering`
- 書いた design.md の穴探し → `design-premortem`

## 1. 段階を決める

依頼から段階を決め、回答の冒頭で 1 行宣言する（例:「複数セッションの作業として `.steering/` に設計を書きます」）。ユーザーが「何回かに分けて」「ちゃんと設計して」と言えば大きな作業、「直接やって」と言えば従う。

次のどれかに当たれば小さな作業として扱わない: 3 ファイル以上を変える・公開している API や型やコンポーネントの使い方を変える・原因のわからない不具合を調べる・CLAUDE.md や docs や `.claude/` に触る。迷うときだけ聞く。

## 2. 調べる

設計に必要な範囲で今のコードを読む。少なくとも次を確かめる:

- 依頼を満たすのに要るデータが、今の API・型・状態に本当にあるか（無ければ、それ自体が論点）
- 変更が触る既存の振る舞いと、それを守っているテスト
- 状態が増えるときの組み合わせ（既存の入力との AND/OR・リセットの規則・URL や保存との関係）

## 3. 書く前に、ユーザーにしか決められないことを聞く

答えによって設計の骨格（API の形・データの出どころ・状態の置き場所・対象の範囲）が変わる決定があるなら、設計を書く前にユーザーに通す。書いた後に骨格が変わると設計の大半が無駄になり、完成した文書を前にすると、直すより承認する方が楽になるため。骨格が変わらない決定は先に聞かず、推奨で書いて 4 の論点に残す。

- 聞くのは、コードを読んでも分からない決定だけ: 目的（誰の何を良くするか）・優先度・対象外にするもの・振る舞いの方針。調べれば分かる事実は聞かない
- 骨格が変わる決定を影響の大きい順に多くても 3 個選び、**1 問ずつ**、選択肢と推奨と理由を添えて聞き、**ここで止まる**。答えをもらってから次の問いへ進む。全部の答えが揃うまで design.md を書かない
- 「使いやすくしたい」のように何を変えるかが決まらない依頼では、1 問目で、今のコードから根拠のある候補を 2〜4 個挙げ、どれに当たるか（誰が・どの場面で困っているか）を聞く
- 骨格が変わる決定が無い・依頼で出そろっているなら、先に聞かずに書き、「骨格を左右する未決定は無いので、書いてから論点で確認します」と 1 行添える
- 「残りは推奨で」「おまかせ」と言われたら、残りを推奨で埋めて書き進め、design.md の論点に「推奨で仮置き」と書く
- 答えは design.md に反映する。却下した案は理由を 1 行ずつ、先送りした決定は論点に残す（会話に置き去りにしない）

## 4. 設計を書く

中身で外せないもの（見出し名は自由。短くてよい）:

| 項目 | 書くこと |
|---|---|
| 目的 | 誰の何が良くなるか。1〜3 行 |
| 対象 / 対象外 | 今回やらないことも書く |
| 振る舞い | 正常系に加え、0 件・エラー・読み込み中・素早い連続操作・既存の状態との組み合わせ |
| 構成 | 触るファイル・増える状態と置き場所・API の形 |
| 完了条件 | テストや操作で確かめられる文。「使いやすい」のような確かめられない文は書かない |
| テスト方針 | 足すテスト・既存テストへの影響・モック（MSW のハンドラなど）の変更 |
| 論点 | 人が決めること。各論点に選択肢と推奨を付ける |

- コードや依頼から確かめられなかったことは、決定として書かない。「前提」か「論点」に置く
- 代替案を検討したなら、却下の理由を 1 行ずつ残す

**大きな作業:** `.steering/[YYYYMMDD]-[task-name]/` を作り、次の 2 ファイルを書く（日付は今日、task-name は英小文字とハイフン）。

- `design.md` — 冒頭に `Status: DRAFT`。上の表の中身
- `tasklist.md` — 実装の手順を、1 項目が 1 回の作業で終わる粒度のチェックボックスで並べる。最後にレビューと tasklist の更新を入れる

**中くらいの作業:** ファイルは作らず、同じ中身を会話の中で短く示す。

## 5. STOP — レビューを求める

設計を示したら**ここで止まる**。回答の最後に次を書く:

- 何を書いたか（大きな作業なら design.md のパス）
- 決めてほしい論点の一覧（推奨つき）
- 「承認されたら実装に入ります」の 1 行

このあと、ユーザーが承認するまで `src/` などの実装ファイルを書かない。Status を自分で APPROVED に書き換えない。ユーザーが承認したら、Status を `APPROVED` に書き換えてから実装に進む。

## 中くらいの作業で承認をもらったら

`.steering/` が無いので、会話の設計は compaction で消える。実装を始める前に、決めたことを 5 行ほどに要約して会話に残し、最後にコミットメッセージか PR の本文へ写す。

## Status の決まり

design.md の Status は 3 値。

| 値 | 意味 |
|---|---|
| `DRAFT` | レビュー待ち。実装しない（既定） |
| `APPROVED` | 人間が承認した。実装してよい |
| `SPIKE` | 探索のための試し実装は可。外向きの操作（push・PR）はしない |

書き換えるのは人間の指示があったときだけ。
