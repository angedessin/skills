# Skill Design Patterns — フロントエンド開発ワークフロースキルの実践知識

---

## スキルは孤立エージェントが読む前提で書く

スキルはメインセッションだけでなく、オーケストレーターから dispatch された
フレッシュな subagent が実行する場合がある。subagent はセッション履歴を持たない。

```
# ❌ Bad: エッジケース処理を末尾の注記に分離する
## Step 1 — 入力収集
（メイン処理）

## 汎用性について（末尾）
- .steering/ がなければ review-result.md のみを使う  ← subagent は読まない可能性がある

# ✅ Good: エッジケース処理を該当ステップに直接書く
## Step 1 — 入力収集
ファイルが見つからなかった場合 → ここで止まってユーザーに確認する
（後続ステップへの影響も同じ場所に明記）
```

**暗黙のコンテキストを仮定しない:**
- 「ユーザーは `.steering/` が何か知っている」
- 「前のステップで承認を得た」

これらはメインセッションでは自明でも、subagent には伝わらない。

**検証方法:** `empirical-prompt-tuning` スキルでフレッシュな Agent にスキルを実行させると、孤立AI視点での不明瞭点が検出できる。

## スキルは単体コピーで他プロジェクトに配置される前提で書く

このリポジトリはマスター。スキルは人が選んで配置先プロジェクトの `.claude/skills/` に
手動コピーされる。配置先には CLAUDE.md のポリシー・`docs/knowledge/`・`.steering/`・
他のスキルが存在しない可能性がある。

原則: **あれば使う、無ければ無いなりに動く**

- 参照ファイル（references/・docs/knowledge/・design.md）には「無い場合の代替動作」を該当ステップに直接書く
- **「あれば使う」をファイル名の決め打ちで書かない** — 名前が違うだけで蓄積した知識が一度も読まれない。ディレクトリを走査して内容で選別する。さらに、知識ファイル側の「◯◯スキルが使う」という**自称は配線ではない**（境界の変更で消費者が入れ替わっても自称は古いまま残る）。知識を増やしたら消費者側の本文に読む手順があるかを確認する（20260723 の実例: impl-review は存在しない `antipatterns.md` を決め打ちで探し、a11y 知識が自称した消費者 impl-review は境界変更で a11y を見なくなり、実際の消費者 review-a11y は `docs/knowledge/` を一切読まなかった。3 本が被参照ゼロ）
- 依存スキル（オーケストレーターのサブスキル等）はディスパッチ前に存在確認し、無ければスキップして報告する
- `.steering/` への書き込みはタスクディレクトリが存在する場合のみ行う
- 役割分担: 「いつ使うか」のポリシーは各プロジェクトの CLAUDE.md、「どう動くか」の手順はスキル本文。スキル本文を CLAUDE.md に依存させない
- 改善は配置先で直接編集せず、マスターに還元して再コピーで配る（ドリフト防止）。配置時にマスターのコミットハッシュを配置先に記録する

**配布可スキルの本文に「マスター内部前提」を残さない（provenance の一般化）。**
規律を硬くした根拠を本文に書くとき、`YYYYMMDD に … した実例がある` のような**日付付き内部
エピソード**や、`還流` / `配布セット` / `このマスターには` / `source-commit` のような**マスター
固有語**を残すと、配置先の読み手はその文脈を持たないため根拠が解読不能なノイズになる。規律の
根拠は残しつつ、日付・固有ドメイン・配置先名・マスター固有語を落として一般化する
（例: `20260714 に WebGL 環境構築を…誤見積もりした実例` → `見積もりを確認の代用にして縮退し、
実際は複数セッションに及んだ実例`）。**とくに配置先由来の issue を昇格するとき混入しやすい**
（20260723 の配布確認で、配布可 25 本に日付付きエピソード 5・マスター固有語 6 が残存）。
skill-harvest → compound の還流経路には、集約ファイルの生の文脈を本文へそのまま転記させない
申し送りを両側に置く（`skill-harvest` Step 4 の還流ノート・`compound` Step 4 のガードレール）。
機械の網は `validate_skills.py --portability`（配布可スキルのみ走査。日付・固有語を report-only で
検出。master-only 集合の一次情報は `docs/starter-kit.md` の配布可否表）。**このファイル自身は
master-only なので日付を残してよい** — 規律が効くのは配布可スキルの本文。

## 並列サブスキル同士の責務境界は各本文に相互明記する

同一ファイルを対象とする並列サブスキル（review-* 群など）は、責務境界
（何を見て何を見ないか・見ない方はどのスキルの担当か）を**各 SKILL.md 本文に相互に書く**。

```
# ❌ Bad: 境界をオーケストレーターの統合ルールだけに置く
frontend-code-review: 「同一行の重複指摘は最専門の軸に帰属させる」
→ 並列ディスパッチされた subagent は他方のスキルもオーケストレーターも読まないため、
  越境指摘・指摘漏れ（相手がやると思って見ない）が起きる

# ✅ Good: 両方の本文に境界を明記する（20260702 review-axes-coverage の実例）
review-correctness: 「エラーのユーザー向け表示の有無は review-ui の担当。ここでは握りつぶしを見る」
review-ui:          「エラーが握りつぶされる問題は review-correctness の担当。ここでは表示の有無を見る」
```

オーケストレーターの重複統合はセーフティネットであって、境界定義の置き場ではない。

**「受け取ったが見ない」領域は、境界を書いても黙って落ちる**（20260723 の敵対レビューで検出）。
相互明記は「両方が見ない」を防ぐが、**ディスパッチ側のスコープには入るのに受け手が対象外と
している**領域には効かない:

```
# 実例（20260723）
オーケストレーターの test-agent はスコープに *.spec.ts を含み、E2E ファイルもここに入る。
だが test-review は「E2E は対象外」（担当は e2e スキル）なので指摘を返さない。
→ サマリーには test-review が「問題なし」と出るため、レビュー済みに見えて誰も見ていない。
```

規律: 受け手が対象外とする領域は**ディスパッチ側のスコープからも除外**し、除外したものを
「未レビュー（担当スキル名）」としてサマリーに明示させる。出力上で「対象なし」と
「対象だが見なかった」を区別する（区別しないと、欠落が沈黙として報告される）。

## 単独利用向けの親切な分岐は、オーケストレーター配下では順序と承認ゲートを壊す

単独利用を想定した「先に◯◯を実行しますか？」「規模が小さいので縮退しますか？」といった
分岐は、オーケストレーターから呼ばれると発火して、親が持つ順序・承認ゲート・フラグ更新を
飛ばす。子スキルの親切が、親から見ると破壊的になる。

```
# 実例（20260723・Major）
knowledge-capture は .codify-needed があれば「先に compound を実行しますか？」と確認して
中断する分岐を持つ。ところが .codify-needed はレビューフェーズで必ず立つため、
feature-pipeline 配下では 100% この分岐に入る。
→ Yes を選ぶと Gate 4（承認）を通らないまま compound が走り、capture_done が立たず、
  親の現在地検出は同じフェーズに再入し続ける。宣言された 4a→4b の順序が毎回崩れる。
```

規律: オーケストレーターから呼ばれうるスキルの分岐には、**各分岐に**「オーケストレーターから
呼ばれた場合はこの分岐を行わない」という例外句を書く（design-doc の「feature-pipeline 配下では
タスク規模によらず必ず `.steering/` を作成する」と同型）。親が現在地検出・ゲート・フラグを
成果物に依存させている以上、子が善意で中断・縮退・順序変更をしてよい場面は無い。

**この例外句は横展開されにくい** — design-doc には最初から在ったが、同じ構造を持つ
knowledge-capture には無かった。オーケストレーターにフェーズを追加したら、そのフェーズで
呼ぶ子スキルの分岐を一通り読んで例外句の有無を確認する。

## 同じ情報を持つ全箇所を直してから閉じる（片側修正の禁止）

同じ情報・契約・語彙が複数箇所に存在するとき、片側だけ直すと反対側が腐り、
次の監査まで発覚しない。20260703 の悲観監査で 3 系統が検出された:

```
# 実例（すべて「片側だけ直した」結果）
- diff 合算をオーケストレーターに入れたが、サブスキル 7 本は HEAD のみのまま
  （単独利用で silent failure）
- @参照のコスト注意を Step 5 に入れたが、Step 2 の決定木は無条件 @追記のまま
- Next.js 除去を description と review-performance に入れたが、
  review-security の例文には NEXT_PUBLIC_ が残った
```

修正時の規律:
- 直した語・コマンド・契約を**リポジトリ全体で grep してから**タスクを閉じる
  （同じ情報を持つ同義箇所を機械的に洗い出す）
- **参照はファイル名だけでなく「見出し文」を指していることがある** — スクリプトの docstring・
  hook の注入文・同一ファイル内の相互参照など、ファイル名の grep では出ない場所に潜む
  （20260811 の実測で見込み 2 件に対し 4 件）。節を再構成するなら、**見出し文字列を不変にすれば
  付け替えはゼロで済む**
- 契約が二者間にある場合（呼び出し側と呼ばれ側）は「境界の相互明記」と同様に
  **両側を同一コミットで**直す
- **必須手順をオーケストレータに書くときは、呼び出し先のスコープ早期終了条件も
  同じコミットで直す。**「スキップしない」と空スコープ終了の併存は片側修正になる
  （契約成果物のみの diff で Axis 1 が不発になった実例がある）
- **部分読み契約**（成果物の一部だけを必須入力にする）を複数スキルに足すときは、
  境界マーカーの有無だけでなく、ツールが全文を返しても必須入力をどこまでに限定するかの
  **操作定義を各読み手スキルに書く**。書き手（生成テンプレ）や一部の読み手だけ揃えても、
  抜けた読み手で完了条件を満たさない（resume だけ操作定義が無くレビューで検出された実例がある）

**契約が「値の集合」の場合、片側修正は grep でも静的検査でも検出されない**
（20260723 の敵対レビューで検出）。同じ**文**の重複と違い、enum・フラグ名・ファイル名のような
値の契約は producer と consumer が別々に定義しても**どちらも自分の中では整合している**ため、
同義箇所を探す grep に掛からない:

```
# 実例（20260723・Critical）
review-result.md の Status を
  producer（design-doc/references/templates.md）: PENDING | IN_PROGRESS | RESOLVED
  consumer（feature-pipeline の現在地判定表）  : OPEN / RESOLVED / DEFERRED
と別々に定義していた。重なるのは RESOLVED のみで、生成直後の値はどの行にもマッチしない。
→ ルーターが現在地を見失い、レビュー済みでも毎回レビューに差し戻る／知見蓄積を飛ばす。
  さらに consumer 側の「Gate 3 で OPEN から必ず変更する」は、OPEN が一度も書かれないため
  実行不能な指示になっていた。
```

規律: 契約値を定義・変更したら、その値を**照合する側**を名指しで探して同一コミットで直す。
consumer の判定表・分岐条件に現れる値を列挙し、producer がその値を書くかを突合する。
**静的検査の PASS は契約整合の保証ではない** — 上記は `validate_skills.py` 29/29 PASS の
状態で発生した（検査対象が本文の語彙・構造であって、スキル間の契約整合ではないため）。

**値の集合を増やすときは、読み手の同文規則に加え、書き手の Phase メッセージも分岐させる。**
例: `design.md` の Status に探索用の値を足して実装可にしても、設計スキルの「承認してください」案内が
旧二値のままだと、正規経路が罠になる（新 Status では承認しない／別出口なのに承認を促す）。
読み取り規則を各読み手に同文で置いただけでは足りない — **承認・停止・次アクションを出す文面**も
値ごとに分岐しているかを同一コミットで確認する。

**同じ工程表を複数箇所に別々に書くと、片側だけ増改築されてドリフトする。**
frontend-code-review の「次のステップ」チェックリストと tasklist テンプレート
（`design-doc/references/templates.md`）は同じ工程（実装 / レビュー / 知見保存 / デプロイ / 福利化 / クローズ）を
別の場所に持つ関係だが、前者から knowledge-capture と steering archive が抜けていた。
**`feature-pipeline` 経由だと後続フェーズが拾うため表面化せず、単独でレビューを回した人だけが踏む**
（経路としてはそちらが多い）。規律: 工程表・手順リストを複製したら「両方が同じ工程を指すか」を
突合する。かつ**オーケストレーター経由では隠れる欠陥は単独利用の経路で検証する**（統合層が
欠落を後から補うため、通し実行だと導線の断絶に気づけない）。

この層を拾う手段が `prompts/adversarial-skill-review.md`（横断パス）。静的検査と素通り検査の
**間**に位置し、契約ズレ・片側修正・死んだ参照・配布分類違反を証拠つきで洗い出す。
スキル間の契約に触れる改訂の後に回す。

## 停止・承認・前提条件の契約はハードストップの手順として書く（説明文では守られない）

description・When NOT to use・出口分岐の一句として書かれた「承認を得て」「〜が必要」は実行時に
守られない。対照的に design-doc の Phase 3 STOP（「必ず以下のメッセージを表示して止まる」+
「このメッセージの後は何も実装しない」）は毎回守られた。差は書き方にある。

### 規律 — 停止の置き方

- 止まってほしい地点には、該当ステップに「**ここで止まる**」と、何を待つか（ユーザーの明示承認）を書く
- 停止は**独立した見出し**にして**行動を一切書かない**。承認後の行動（承認語彙を含む分岐）は
  次のステップに分離する
- 停止は**提示ステップの末尾**に「提示したらここで必ず止まる」を置き、次の行動ステップは見出しを
  「**承認後の〜**」に改名して冒頭に「承認前にこのステップに入らない」を書く。停止の独立見出し化は
  必要条件だが、**次の見出しが行動語（適用・書き込み・実行）のままだと引力になり十分でない**
- 提示は「これから書く確定リスト」ではなく**「書き込み案（未書き込み）」として構造で示す**
  （「保存先」→「保存先（案）」・冒頭に「まだ 1 文字も書き込んでいない」）。確定列挙に見えると、
  承認を挟まず書き込みへ地続きに流れる
- 停止に**ターン境界**を入れる（「このターンでは書き込みステップに進まない。承認の返信を次のターンで
  受け取るまで書き込まない」）
- 滑りの誘因は本文側で名指す（「件数が多いときこそ 1 件も書き込まずに承認を待つ」）。本文の締めで
  滑り率が十分下がらないことを実測してから、機械の別防御を足す（「摩擦が実証されてから」）

### 規律 — 前提チェックの書き方

- 前提条件は description に書くだけでなく、本文の Step にして**不成立時の動作**（停止・案内・
  リダイレクト）まで書く。description は発動判定にしか効かない
- 会話の経緯（「さっき承認された」等）による前提チェックのスキップを**禁止する一文**を添える
- **その前提を代用しうる材料を名指しで禁止する**（「貼られたコメントを PR 実在の代用にしない」
  「渡されたパスをレジストリ作成の承認代用にしない」）。材料は Step 2 以降の入力データであって、
  前提や承認を飛ばす根拠ではない、と分離して書く。各停止に「**headless でも同じ**」も添える
- **禁止の理由（趣旨）が本文にあっても、ハードストップの手順と材料の名指しが無ければ守られない**

### 規律 — 検証と機械化

- 停止が守られるかは**実地で検証する**（素通り検査、または `empirical-prompt-tuning`）
  — 説明文の存在は保証にならない
- **承認語彙（承認 / APPROVED）を持つ全スキルは passthrough シナリオを持つ。** 静的検査の PASS で
  満足しない（静的検査は本文の語彙・構造しか見ず、実行時に守られるかは動的な検査でしか分からない）
- 停止契約の静的検査を validator に入れると、機械化そのものが「説明文だけの停止契約」を炙り出す。
  入れる際は既存資産全件 + テンプレートを回帰対象にし、誤 FAIL の逃し弁（否定形「承認不要」の除外・
  理由つきエスケープコメント）を用意する
- **外部テキストを読むスキルは同じ構造でプロンプトインジェクションに晒される。** 監査系は (1) 対象
  本文を全文解釈せずスクリプト / grep のヒット行だけを判定材料にする (2) 判別不能は OK でなく
  「要確認」に落とすフェイルクローズ (3) 監査中に外部 URL を fetch しない、を**手順の構造**にする

### 実例

**説明文として書かれた契約は守られない**（20260703-04）: design-doc の会話内設計分岐の「承認を得て
から実装」（When NOT to use 内の一句）・impl-from-design の「APPROVED である必要がある」
（description のみ）・debug の「修正の適用は承認制」（出口分岐の一句）が 3 件とも素通りした。
ハードストップの手順として書き直した後は 6/6 で停止が守られた。

**停止が独立見出しでも、同じステップ内に行動が同居すると守られない**（20260724）: debug の旧 Step 5
は停止文の直後に、同じステップ内で「**承認を得て**その場で修正する」を続けていた。停止文には材料の
名指し禁止が書いてあったのに、環境圧がその承認語彙を満たしたと解釈され、停止を越えて修正まで走り
切った。同検査で PASS した 3 本はいずれも停止が独立見出しだった。

### 確率的遵守の限界 — どこで本文の改善をやめるか

20260725 に 5 スキル 20 run を型別に実測したところ、破れたのは全て「提示 → 承認 → 実行」型で、
**前提チェック型（進む先が無く、フェイルクローズが自然な形）は破れなかった**。

- 提示 → 承認 → 実行型は**本文の技法を尽くしても 20〜25% で破れる**確率的遵守の限界として扱い、
  **本文の改善に課金を重ねない**（次に何を足せば下がるかの当てが無い状態で 4 run ずつ払うことになる）
- 対応は**書き込み先の広さ**で分ける。狭ければ機械で守れる（adr の `docs/decisions/**`）、広ければ
  守れない（debug のソースコード全般 — ゲートすると通常の開発が全て止まる）。守れない側は**残存
  リスクとして記録し、「機械的にゲートした」と書かない**
- 設計段階で停止を**前提チェック型に寄せられないか**を先に検討する（進む先を持たない形にできれば、
  そもそも破れにくい）

検証手順（環境圧の添え方・無出力 run の扱い・シナリオ入力の充実度）と過去の測定ログは
`.claude/skills/skill-test/references/passthrough-testing.md`。

## 自己レビューは、自分が書いた中核ロジックを構造的に見落とす

20260725 実測。並列レビューがセッション上限で全滅したため自己レビューで代替したところ **High を
1 件しか出せず**、上限リセット後にフレッシュな 3 体を回すと **High を 3 件追加検出**した。うち 2 件
（フェイルクローズの片側欠落・語彙抽出の取りこぼし）は**自分が書いたスクリプトの中核ロジック**で、
「そう書いたのだからそう動く」という前提が検査の目を塞ぐ種類の欠陥だった。

`design-premortem` を別エージェントに回す規律（設計に関与した文脈が攻撃の甘さになる）は、
コードレビューでも同じく成立する。規律: **自己レビューは「レビュー未実施」に近いものとして扱い、
成果物にその旨を明記する**（`review-result.md` に「自己レビューで代替・バイアス排除が効いていない」
と書く）。フレッシュエージェントが使えない事情があるなら、レビューを完了扱いにせず持ち越す。

**機械検査が内容を見ない改訂は「抽出 → 固定 → 差集合」で突合する。** 文書の圧縮・再構成では、
規律が落ちても静的検査（本文の語彙・構造しか見ない）は PASS する。要は**改訂の前**に規律を
機械抽出して固定し、抽出元の行番号を対応表として残すこと — 改訂後に「何が落ちたか」を聞いても、
比較対象が既に失われていて答えられない。改訂後、フレッシュなサブエージェントに「固定したリストと
改訂後の本文を突合し、落ちた規律を挙げよ」と回す（静的突合のみで無料）。判定は文字列一致ではなく
**意味**で行わせ、「表現が変わった」と「条件・限定・例外が落ちた」を区別させる（20260811 に
175 → 73 行へ圧縮した実測では欠落 0・軽微な差分 3 件の指摘のうち 1 件が実際に復元対象だった）。

## 検出ツールを書くときの4規律（フェイルクローズ・語幹・機械化の実益・適用順）

**検出ツールの欠陥は「検出漏れ」として現れるため、使っている側からは成功と区別がつかない。**
壊した入力で FAIL することの回帰は `tests/assets/run.py` で固定する（新しい契約を足したらケースも足す）。

1. **フェイルクローズは「両側」に要る。** 比較ツールで片側の対象不在だけを弾いても、もう一方が
   空のとき 1 ペアも比較しないまま「差分なし」の緑を出す。比較ペアが 0 件のケースも独立に弾く
   （この規律を散文で持っていたのに契約 (n) で再発した — 散文では守られず、tests/assets で固定した）
2. **語彙ベースの抽出は語幹で持つ。** 「止まる」だけを見ると「必ず止まって〜を待つ」「まだ 1 件も
   書き込まない」「（案・未書き込み）」を取りこぼす。取りこぼしは差分検出では**フェイルオープン**
   （消えても気づかない）で、検出漏れが静かに蓄積する。抽出対象は実ファイルで**捕捉できているかを
   実測**してから信用する。部分文字列を消すリストは書き順でなく**長さ順**（`sorted(key=len, reverse=True)`）で
   適用する（`.tsx` が `.spec.tsx` を先に削ると無害差分が実質差分に化ける）。報告を切り詰めるなら
   食い違い位置に窓を寄せる — 読めない検出は検出漏れと同じ
3. **「単一情報源」を作ったつもりで 2 つあることがある。** 名前のリストを返す関数と、その名前を
   キーにしたテーブルは**別々のリスト**で、どちらも自分の中では整合しているため grep に掛からない。
   20260723 と 20260726 に同じ型で 2 度、配置が KeyError で全滅した。しかも 2 度目は
   **「同送 hook の漏れ」をルール化したコミット自身**が 1 階層下で再発させている。
   `関数の全可能出力 ⊆ テーブルのキー` を検査に入れる。**「単一情報源にした」と書いた箇所こそ疑う。**
   あわせて、**分類は散文（コメント・`_comment`）でなく機械可読な定数に置く** — 「意図的な除外」と
   「入れ忘れ」は見た目が同じで、散文では機械が区別できず、宣言の無い欠落を FAIL にできない
4. **フェイルクローズを契約単位でなく全体に適用すると、他の契約の検出結果を殺す。** 検査ツールが
   1 つの契約の対象不在で `exit 2` すると、**他の契約が FAIL していても終了コードは 2** になる。
   呼び出し側（hook・CI）が「1 以外は差し戻さない」設計だと、その環境で検査は**恒久的に無音**に
   なる（20260726 に、別マシンのクローンで検査が一度も差し戻さない状態が作られていた）。
   対象不在は当該契約を SKIP に降格し、終了コードは「FAIL が 1 件でもあれば FAIL」を優先する。
   必須にしたい場面用のフラグ（`--require-*`）を別に持たせる
5. **検査の出力は「既定の呼び出し経路」で確認する。** 警告を `--verbose` 限定にすると、
   npm script や hook から呼ぶ既定経路では出ない。20260726 に「人が確認できるよう必ず列挙する」と
   コメントに書いた警告が既定出力に出ておらず、**塞ごうとした実害を再現しても全 PASS** になった。
   コメントの宣言と実際の出力を突き合わせる。**警告は verbose の外に置く。**
6. **文書と実体の突合で「等価」を既定にしない。** 文書は実体より多くを語るのが正常で、
   等価を要求すると**正しい記述が FAIL になる**。20260727 に契約を書いた実測では 3 方向とも
   等価が成立しなかった:
   - **員数**: 「文書が主張する数がすべて実体と一致」は履歴節（「9 スキルに縮小していた」）や
     番号リストを誤検知する → **「実体の数が各文書に少なくとも 1 回現れる」**にすると誤検知ゼロで
     「増減して直し忘れ」を検出できる
   - **同梱物の名前**: 文書は非同梱のものにも言及する（「◯◯は含まれていない」）→
     **「実体の全要素が文書のどこかに現れる」**（記載漏れの検出）
   - **参照先の名前**: 文書は意図的に配らないものの理由も説明する →
     **「文書が参照する名前が実在する」**（死んだ参照・typo の検出）

   判定方向は **「実体 → 文書」（記載漏れ）と「文書 → 実体」（死んだ参照）の 2 本に分ける**。
   1 本の等価にまとめようとすると、どちらかの正常系を壊す。**誤検知は「無関係な編集が
   ブロックされる」形で警報疲れを招き、最終的に検査を黙らせる修正を誘発する**ため、
   取りこぼしより誤検知を先に潰す（この判断は取りこぼしを許すので、何を捨てたかを docstring に書く）。

> bash スクリプトを扱う場合の注意:
> - **比較時**: コメント行（`#` 始まり）を落とす正規化は **heredoc の中身と shebang にも効く**。
>   hook は heredoc で JSON を出力するため、配布物側の heredoc に `#` 行が混入して標準出力が
>   壊れても差分として検出されない。heredoc 終端までは除去を止め、1 行目は常に比較対象に含める
> - **検証時**: hook の JSON 出力を検証するとき `echo "$out"` を使わない。**バックスラッシュ
>   エスケープ（`\n`）を実際の改行に展開して JSON を壊す**。`printf '%s' "$out"` を使う。
>   20260727 にこれで「hook が不正な JSON を出す」ように見え、正常なコードを直しかけた —
>   **検証が失敗したら、まず検証側を疑う**

## リポジトリ構成: スキル・スキル内リソース・マスター専用ツールを区別する

配置の基準は Agent Skills 公式仕様（Anthropic 発のオープン標準・Claude Code が準拠）に沿う。
一次情報: https://agentskills.io（クロスベンダー仕様）/ https://code.claude.com/docs/en/skills（Claude Code 固有の配置パス）。

| 種類 | 置き場所 | 例 |
|---|---|---|
| スキル本体 | `.claude/skills/[kebab-name]/SKILL.md` | 各スキル |
| スキルが実行時に使うリソース | そのスキルフォルダ内 `references/`・`scripts/`・`assets/` | カートリッジ・参照 |
| マスター専用ツール（非配布・作成/検証用） | リポジトリ**ルート直下** | `scripts/validate_skills.py`・`templates/SKILL.template.md` |

- 新規スキルの作成雛形は**スキルではない**ので `.claude/skills/_template/` に置かない
  （validator の走査対象・スキル一覧の誤認を招く）。`scripts/` と同じルート直下が正しい。
- **用語の重なりに注意**: 仕様上 `templates/` は「各スキルがスキルフォルダ内に持つファイル雛形」を指す。
  ルート直下の `templates/`（＝スキル作成用のメタ雛形）とは意味が別。README でスコープを明記して混同を防ぐ。
- 「スキルフォルダ内に README.md を置かない」は**スキルフォルダ内**の規約。ルート直下の `templates/README.md` は対象外。

### スキルの配布分類とクロスリポジトリ還流の producer/consumer 対

スキルは**配布可**（他プロジェクトへコピーする前提で自己完結に書く）と**マスター専用**
（このリポジトリの管理ツール。配置先にコピーしても無意味）に分かれる。一覧の正本は `MASTER_ONLY`
（`deploy_skills.py` と `validate_skills.py` を契約 (h) が突合する）。
**スキル本体の置き場は `.claude/skills/`**。ルート直下の `scripts/`・`tests/`・`deployments.md` は
マスター専用**ツール・資産**であり、master-only スキルの置き場ではない（用語を混線させない）。

配置先からマスターへ知見を還流させる仕組みは **producer / consumer の対**で成立する:
consumer（skill-harvest・マスター側）が回収できるのは、producer（配置先）に
`skill-issues.md` と `source-commit` が存在する場合のみ。skill-issues.md を書くルールは
マスターの CLAUDE.md にしか無いため、**配置先には producer 役のスキル（session-retrospective）を
併配する**のが供給側の推奨構成。producer を欠くと consumer は空振りする。還流系を作るときは
「取得用の情報を出力する側」と「回収する側」を必ず両方用意する（片方だけでは対が成立しない）。

**producer/consumer の対は hook 間にも存在する**（20260723 の敵対レビューで検出）。
配置スクリプトは `.capture-needed` を立てる `session-stop.sh`（書く側）を同送していたが、
それを読んで起動を促す `session-start-check.sh`（読む側）を送っていなかった。配置先では
フラグが毎セッション立つのに拾う主体が居らず、knowledge-capture / compound の
「セッション開始時にフラグがあれば起動」が**永久に発火しない**。フラグは `.gitignore` 対象で
成果物にも現れないため、レビューでも気づかれない。

規律: フラグ・成果物を「立てる」仕組みを配るときは、「読む」側が配布対象に入っているかを
必ず対で確認する。依存表には書く側だけでなく**読む側も列挙する**（書く側だけを書くと、
その表自体が片欠けを正常に見せてしまう）。

**producer 側が単一だと、それを外した瞬間に対が静かに崩れる（当時の教訓）。**
`.codify-needed`（福利化ループの起動フラグ）の producer は当初 frontend-code-review 1 本だけで、
consumer は複数箇所（compound・knowledge-capture・hook 等）あった。consumer は「フラグが無い」を
正常系として扱うため、producer を外す・差し替えると**誰もエラーにならずループだけが静かに止まる**。
**現行**: producer は frontend-code-review（レビュー完了時）と knowledge-capture（最終 Step・
`codify-log.md` が無ければ立てる no-op ガード付き）の二重。代替を注記に書くだけでは守られない
（下記「説明文では守られない」に該当）。

**メモにも producer / consumer の対が要る（20260730）。**
`blockers.md` 等は追記が承認不要でも、回収出口が無いと CLAUDE.md の「取捨は knowledge-capture 時」が空振りする
（書く導線だけあって読む側がスキルに無い状態）。フラグの対と同じく、任意メモも
**入力源・決定木・ドラフト提示まで** consumer（knowledge-capture）に載せる。自動移設はしない。

**gitignore のレジストリに方針を書かない（20260730）。**
`deployments.md` はローカル限定。配置先ごとの方針注記など追跡したい文言は `deployments.example.md` に書く。
実体だけ直すとリポジトリに残らない。

## 課金を伴う操作は前置承認のハードストップにし、hooks から自動起動しない

subagent 並列・外向き API・N 回実行など**課金が発生する操作**を持つスキルは、実行前に
「コスト見積 + 無料代替」を提示して止まる Step を必ず持つ（impl-tournament の変種並列、
skill-test の実行層が実例）。承認語彙を description や説明文に置くのでは守られない
（「停止・承認・前提条件の契約はハードストップの手順として書く」と同じ規律）。

- コスト見積と**無料代替を必ず併記**する。無料代替は「比較せず 1 本に絞る」「静的層だけで締める」等、
  課金せずに目的の大半を満たす道を具体的に書く（ユーザーが常に安い方を選べる）。
- **hooks に接続しないことを本文に明記**する。SessionStart / Stop / PostToolUse に課金スキルや
  課金スクリプトを繋ぐと無人で課金ループが回る。自動化は「摩擦が実証されてから」に倣い、
  手動起動 + 明示承認に留める（session-retrospective の Stop hook 自動化を見送ったのと同じ判断）。
