# Skill Design Patterns — フロントエンド開発ワークフロースキルの実践知識

---

## スキルは孤立エージェントが読む前提で書く

スキルはメインセッションだけでなく、オーケストレーターから dispatch された
フレッシュな subagent が実行する場合がある。subagent はセッション履歴を持たない。

```
# ❌ Bad: エッジケース処理を末尾の注記に分離する
## Step 1 — 入力収集
（メイン処理）

## 汎用性について（末尾）
- .steering/ がなければ review-result.md のみを使う  ← subagent は読まない可能性がある

# ✅ Good: エッジケース処理を該当ステップに直接書く
## Step 1 — 入力収集
ファイルが見つからなかった場合 → ここで止まってユーザーに確認する
（後続ステップへの影響も同じ場所に明記）
```

**暗黙のコンテキストを仮定しない:**
- 「ユーザーは `.steering/` が何か知っている」
- 「前のステップで承認を得た」

これらはメインセッションでは自明でも、subagent には伝わらない。

**検証方法:** `empirical-prompt-tuning` スキルでフレッシュな Agent にスキルを実行させると、孤立AI視点での不明瞭点が検出できる。

## スキルは単体コピーで他プロジェクトに配置される前提で書く

このリポジトリはマスター。スキルは人が選んで配置先プロジェクトの `.claude/skills/` に
手動コピーされる。配置先には CLAUDE.md のポリシー・`docs/knowledge/`・`.steering/`・
他のスキルが存在しない可能性がある。

原則: **あれば使う、無ければ無いなりに動く**

- 参照ファイル（references/・docs/knowledge/・design.md）には「無い場合の代替動作」を該当ステップに直接書く
- **「あれば使う」をファイル名の決め打ちで書かない** — 名前が違うだけで蓄積した知識が一度も読まれない。ディレクトリを走査して内容で選別する。さらに、知識ファイル側の「◯◯スキルが使う」という**自称は配線ではない**（境界の変更で消費者が入れ替わっても自称は古いまま残る）。知識を増やしたら消費者側の本文に読む手順があるかを確認する（20260723 の実例: impl-review は存在しない `antipatterns.md` を決め打ちで探し、a11y 知識が自称した消費者 impl-review は境界変更で a11y を見なくなり、実際の消費者 review-a11y は `docs/knowledge/` を一切読まなかった。3 本が被参照ゼロ）
- 依存スキル（オーケストレーターのサブスキル等）はディスパッチ前に存在確認し、無ければスキップして報告する
- `.steering/` への書き込みはタスクディレクトリが存在する場合のみ行う
- 役割分担: 「いつ使うか」のポリシーは各プロジェクトの CLAUDE.md、「どう動くか」の手順はスキル本文。スキル本文を CLAUDE.md に依存させない
- 改善は配置先で直接編集せず、マスターに還元して再コピーで配る（ドリフト防止）。配置時にマスターのコミットハッシュを配置先に記録する

**配布可スキルの本文に「マスター内部前提」を残さない（provenance の一般化）。**
規律を硬くした根拠を本文に書くとき、`YYYYMMDD に … した実例がある` のような**日付付き内部
エピソード**や、`還流` / `配布セット` / `このマスターには` / `source-commit` のような**マスター
固有語**を残すと、配置先の読み手はその文脈を持たないため根拠が解読不能なノイズになる。規律の
根拠は残しつつ、日付・固有ドメイン・配置先名・マスター固有語を落として一般化する
（例: `20260714 に WebGL 環境構築を…誤見積もりした実例` → `見積もりを確認の代用にして縮退し、
実際は複数セッションに及んだ実例`）。**とくに配置先由来の issue を昇格するとき混入しやすい**
（20260723 の配布確認で、配布可 25 本に日付付きエピソード 5・マスター固有語 6 が残存）。
skill-harvest → compound の還流経路には、集約ファイルの生の文脈を本文へそのまま転記させない
申し送りを両側に置く（`skill-harvest` Step 4 の還流ノート・`compound` Step 4 のガードレール）。
機械の網は `validate_skills.py --portability`（配布可スキルのみ走査。日付・固有語を report-only で
検出。master-only 集合の一次情報は `docs/starter-kit.md` の配布可否表）。**このファイル自身は
master-only なので日付を残してよい** — 規律が効くのは配布可スキルの本文。

## 並列サブスキル同士の責務境界は各本文に相互明記する

同一ファイルを対象とする並列サブスキル（review-* 群など）は、責務境界
（何を見て何を見ないか・見ない方はどのスキルの担当か）を**各 SKILL.md 本文に相互に書く**。

```
# ❌ Bad: 境界をオーケストレーターの統合ルールだけに置く
frontend-code-review: 「同一行の重複指摘は最専門の軸に帰属させる」
→ 並列ディスパッチされた subagent は他方のスキルもオーケストレーターも読まないため、
  越境指摘・指摘漏れ（相手がやると思って見ない）が起きる

# ✅ Good: 両方の本文に境界を明記する（20260702 review-axes-coverage の実例）
review-correctness: 「エラーのユーザー向け表示の有無は review-ui の担当。ここでは握りつぶしを見る」
review-ui:          「エラーが握りつぶされる問題は review-correctness の担当。ここでは表示の有無を見る」
```

オーケストレーターの重複統合はセーフティネットであって、境界定義の置き場ではない。

**「受け取ったが見ない」領域は、境界を書いても黙って落ちる**（20260723 の敵対レビューで検出）。
相互明記は「両方が見ない」を防ぐが、**ディスパッチ側のスコープには入るのに受け手が対象外と
している**領域には効かない:

```
# 実例（20260723）
オーケストレーターの test-agent はスコープに *.spec.ts を含み、E2E ファイルもここに入る。
だが test-review は「E2E は対象外」（担当は e2e スキル）なので指摘を返さない。
→ サマリーには test-review が「問題なし」と出るため、レビュー済みに見えて誰も見ていない。
```

規律: 受け手が対象外とする領域は**ディスパッチ側のスコープからも除外**し、除外したものを
「未レビュー（担当スキル名）」としてサマリーに明示させる。出力上で「対象なし」と
「対象だが見なかった」を区別する（区別しないと、欠落が沈黙として報告される）。

## 単独利用向けの親切な分岐は、オーケストレーター配下では順序と承認ゲートを壊す

単独利用を想定した「先に◯◯を実行しますか？」「規模が小さいので縮退しますか？」といった
分岐は、オーケストレーターから呼ばれると発火して、親が持つ順序・承認ゲート・フラグ更新を
飛ばす。子スキルの親切が、親から見ると破壊的になる。

```
# 実例（20260723・Major）
knowledge-capture は .codify-needed があれば「先に compound を実行しますか？」と確認して
中断する分岐を持つ。ところが .codify-needed はレビューフェーズで必ず立つため、
feature-pipeline 配下では 100% この分岐に入る。
→ Yes を選ぶと Gate 4（承認）を通らないまま compound が走り、capture_done が立たず、
  親の現在地検出は同じフェーズに再入し続ける。宣言された 4a→4b の順序が毎回崩れる。
```

規律: オーケストレーターから呼ばれうるスキルの分岐には、**各分岐に**「オーケストレーターから
呼ばれた場合はこの分岐を行わない」という例外句を書く（design-doc の「feature-pipeline 配下では
タスク規模によらず必ず `.steering/` を作成する」と同型）。親が現在地検出・ゲート・フラグを
成果物に依存させている以上、子が善意で中断・縮退・順序変更をしてよい場面は無い。

**この例外句は横展開されにくい** — design-doc には最初から在ったが、同じ構造を持つ
knowledge-capture には無かった。オーケストレーターにフェーズを追加したら、そのフェーズで
呼ぶ子スキルの分岐を一通り読んで例外句の有無を確認する。

## 新規スキルは最初から契約準拠で書き、エンジン純度を実測する

エンジン＋カートリッジ分離を後から改修するのは高くつく
（tdd 206→117行・ツール名34→1、test-review 198→103行の手術が必要だった）。
新規作成時に最初から契約準拠で書けば追加コストはほぼゼロ
（e2e は初版で本文ツール API 出現 0 件 — 20260703 実測）。

- 新規スキルの受け入れ基準に「本文（frontmatter 除く）のツール固有 API 出現数」の実測を入れる。目標はほぼゼロ
- 計測は機械的に行う（ツール名・API 名のリストを文字列カウントで当てる）
- ツール語彙を置いてよいのは compatibility frontmatter と references/ のみ
- 新規スキルは `templates/SKILL.template.md` から書き始める（frontmatter 骨格・When NOT to use・手順 Step のフォールバック・ハードストップ雛形・並列サブスキルの境界相互明記プレースホルダを最初から構造として持つ）。この節・`validate_skills.py` を更新したらテンプレも同一コミットで直す（下記「片側修正の禁止」）

## 同じ情報を持つ全箇所を直してから閉じる（片側修正の禁止）

同じ情報・契約・語彙が複数箇所に存在するとき、片側だけ直すと反対側が腐り、
次の監査まで発覚しない。20260703 の悲観監査で 3 系統が検出された:

```
# 実例（すべて「片側だけ直した」結果）
- diff 合算をオーケストレーターに入れたが、サブスキル 7 本は HEAD のみのまま
  （単独利用で silent failure）
- @参照のコスト注意を Step 5 に入れたが、Step 2 の決定木は無条件 @追記のまま
- Next.js 除去を description と review-performance に入れたが、
  review-security の例文には NEXT_PUBLIC_ が残った
```

修正時の規律:
- 直した語・コマンド・契約を**リポジトリ全体で grep してから**タスクを閉じる
  （同じ情報を持つ同義箇所を機械的に洗い出す）
- 契約が二者間にある場合（呼び出し側と呼ばれ側）は「境界の相互明記」と同様に
  **両側を同一コミットで**直す

**契約が「値の集合」の場合、片側修正は grep でも静的検査でも検出されない**
（20260723 の敵対レビューで検出）。同じ**文**の重複と違い、enum・フラグ名・ファイル名のような
値の契約は producer と consumer が別々に定義しても**どちらも自分の中では整合している**ため、
同義箇所を探す grep に掛からない:

```
# 実例（20260723・Critical）
review-result.md の Status を
  producer（design-doc/references/templates.md）: PENDING | IN_PROGRESS | RESOLVED
  consumer（feature-pipeline の現在地判定表）  : OPEN / RESOLVED / DEFERRED
と別々に定義していた。重なるのは RESOLVED のみで、生成直後の値はどの行にもマッチしない。
→ ルーターが現在地を見失い、レビュー済みでも毎回レビューに差し戻る／知見蓄積を飛ばす。
  さらに consumer 側の「Gate 3 で OPEN から必ず変更する」は、OPEN が一度も書かれないため
  実行不能な指示になっていた。
```

規律: 契約値を定義・変更したら、その値を**照合する側**を名指しで探して同一コミットで直す。
consumer の判定表・分岐条件に現れる値を列挙し、producer がその値を書くかを突合する。
**静的検査の PASS は契約整合の保証ではない** — 上記は `validate_skills.py` 29/29 PASS の
状態で発生した（検査対象が本文の語彙・構造であって、スキル間の契約整合ではないため）。

**同じ工程表を複数箇所に別々に書くと、片側だけ増改築されてドリフトする。**
frontend-code-review の「次のステップ」チェックリストと tasklist テンプレート
（`design-doc/references/templates.md`）は同じ工程（実装 / レビュー / デプロイ / 福利化 / 知見保存）を
別の場所に持つ関係だが、前者から knowledge-capture と steering archive が抜けていた。
**`feature-pipeline` 経由だと後続フェーズが拾うため表面化せず、単独でレビューを回した人だけが踏む**
（経路としてはそちらが多い）。規律: 工程表・手順リストを複製したら「両方が同じ工程を指すか」を
突合する。かつ**オーケストレーター経由では隠れる欠陥は単独利用の経路で検証する**（統合層が
欠落を後から補うため、通し実行だと導線の断絶に気づけない）。

この層を拾う手段が `prompts/adversarial-skill-review.md`（横断パス）。静的検査と素通り検査の
**間**に位置し、契約ズレ・片側修正・死んだ参照・配布分類違反を証拠つきで洗い出す。
スキル間の契約に触れる改訂の後に回す。

## 停止・承認・前提条件の契約はハードストップの手順として書く（説明文では守られない）

description・When NOT to use・出口分岐の一句として書かれた「承認を得て」「〜が必要」は、
実行時に守られない。20260703-04 の初回配置検証（_test）で 3 例が同一パターンとして実証された:

```
# 実例（すべて「契約は書いてあったが、手順のステップではなかった」結果）
- design-doc: 会話内設計分岐の「承認を得てから実装」（When NOT to use 内の一句）
  → 承認を待たず実装開始。しかも非決定的（1回目は素通り・2回目は停止）
- impl-from-design: 「design.md が APPROVED である必要がある」（description のみ）
  → design.md 不在のまま会話内承認を代用して実装開始
- debug: 「修正の適用は承認制」（出口分岐の一句）
  → Investigation Report 提示後、承認なしで修正を適用
```

対照的に、design-doc の Phase 3 STOP（「必ず以下のメッセージを表示して止まる」+
「このメッセージの後は何も実装しない」）は毎回守られた。差は書き方にある。

規律:
- 止まってほしい地点には、該当ステップに「**ここで止まる**」と、何を待つか（ユーザーの明示承認）を書く
- 前提条件は description に書くだけでなく、本文の Step（前提チェック）にして、
  不成立時の動作（停止・案内・リダイレクト）まで書く。description は発動判定にしか効かない
- 会話の経緯（「さっき承認された」等）による前提チェックのスキップを禁止する一文を添える
- 停止が守られるかは実地（または empirical-prompt-tuning）で検証する — 説明文の存在は保証にならない

再検証（20260709）: 上記 3 スキルを書き直した後、フレッシュなサブエージェント各 2 回
（計 6 run）で実地再検証したところ 6/6 で停止が守られた。特に 20260703-04 時点で
非決定的だった design-doc の会話内設計分岐が、2 回とも安定して停止した。ハードストップの
手順として書けば「毎回守られる」側に移ることが確認できた（書き直しの効果の実証）。

**軽量な検証手法「素通り検査」**（empirical-prompt-tuning の完全ループより安い）:
- フレッシュなサブエージェントに**実 SKILL.md を操作指示として読ませ**、停止すべき地点に
  至る現実的なダミー依頼を渡す。「これは停止テストだ」とは伝えない（バイアス排除）
- 作業対象は使い捨てサンドボックス。実行前後のファイル SHA1 差分で
  「実装/修正ファイルに触れたか」を機械判定する（自己申告ではなくファイルで判定）
- 非決定性に備え各スキル 2 回。1 回でも素通りしたら FAIL
- 「人間が即応できない headless」「会話内で承認済みと主張」など素通りを誘導する環境圧を
  あえて添えると、厳しめの条件での合否が取れる
- **「変化なし」は停止と無応答を区別できない** — 実行に失敗したエージェント（プロンプト未達・
  権限拒否等）も判定対象を変えないため、expect=stop が偽陽性 PASS になる（20260711 実例:
  `claude -p` にプロンプトファイルの*パス*を渡し、エージェントが何も読めずに終了 →
  2/2 PASS と誤報告）。エージェント出力を捕捉し、無出力 run は FAIL 扱い＋出力 tail の目視で
  「リスト提示・承認待ち」という停止の実体まで確認する

**停止契約の静的検査を validator に入れると、機械化そのものが「説明文だけの停止契約」を炙り出す**
（承認語彙があるのにハードストップが無いスキルを FAIL にしたら、rule-audit の適用ゲートが
説明文だけだったのが検出され明示ハードストップに直った — 検出の実利）。入れる際は既存資産全件 +
テンプレートを回帰対象にし、誤 FAIL の逃し弁（否定形「承認不要」の除外・理由つきエスケープ
コメント）を用意する。実装メカニクスは validate_skills.py 側のコメントに置く。

**素通りの主因は「依頼文に埋め込まれた材料」を前提スキップの承認代用にしてしまうこと**
（20260711 の素通り検査で 2 スキルが FAIL した共通パターン）:

```
# 実例（ハードストップは書いてあったが、迂回の材料が依頼文に入っていた）
- pr-feedback: 依頼文にレビューコメント本文が貼られる → PR 実在確認（Step 0）を飛ばして
  ローカル実装を開始（FAIL 2/2）。「貼られている＝もう確認済み」と扱った
- skill-harvest: 依頼文で配置先パスが渡される → deployments.md を勝手に作成して回収に進む
  （FAIL 1/2・非決定的）。「パスが分かる＝レジストリを作ってよい」と扱った
```

前提チェックの Step には「不成立なら止まる」だけでなく、**その前提を代用しうる材料を名指しで
禁止する一句**を添える必要がある（「貼られたコメントを PR 実在の代用にしない」「渡されたパスを
レジストリ作成の承認代用にしない」）。材料は Step 2 以降の入力データであって、前提や承認を
飛ばす根拠ではない、と分離して書く。修正後は両スキルとも再検証で PASS 2/2。

追加実例（20260718・design-doc v1.6）: Phase 1.5（決定インタビュー）は「design.md を書く前に
決定を通す。完成文書は承認バイアスを生む」という**趣旨の説明**を本文に持っていたが、手順の
ハードストップと材料の名指し禁止が無かったため、環境圧「返事を待つ間にドラフトまで作っておいて」
を承認代用にしてインタビュー前に .steering/design.md を仮置き作成した（FAIL 2/2。「質問は
1 回にまとめて」への一括提示も同時に発生）。手順 2 に「提示したらここで止まる — 回答を得るまで
次の質問にも .steering/ 作成にも進まない」+ 名指し禁止句（「まとめて出して」「ドラフト作って
おいて」を停止を飛ばす承認にしない・headless でも同じ）を入れて再検証 PASS 2/2。
**禁止の理由（趣旨）が本文に書いてあっても、ハードストップの手順と材料の名指しが無ければ
守られない** — 「説明文では守られない」の規律は、説明が趣旨レベルで正しくても適用される。

**材料の名指し禁止を書いても、停止がステップ境界でなく「1 つのステップの途中の一文」だと
守られない**（20260724・debug の素通り検査で検出）。debug の旧 Step 5 は停止文（「調査
レポートを提示したらここで止まる」）の直後に、同じステップ内で行動分岐（「**承認を得て**その場で
修正する」）を続けていた。停止文には既に材料の名指し禁止（「自動承認モードはこの契約の代わりに
ならない」）が書いてあったのに、環境圧（「そのまま直して」＋「自動承認で動かしている」＋headless）が
その承認語彙を満たしたと解釈され、**停止を越えて修正まで走り切った**（FAIL 2/2）。対して同検査で
PASS した 3 本（design-doc の `Phase 3 — STOP`、tdd の「リストの提示 — ここで止まる」、
impl-from-design の前提チェック）はいずれも停止が独立見出しだった。規律: 停止は独立した見出し
（`## Step N — …（ここで止まる）`）にして**行動を一切書かず**、承認後の行動（承認語彙を含む分岐）は
次のステップに分離する。材料の名指しは必要条件だが、停止がステップ境界になっていなければ効かない。
（Step 5 を「提示（ここで止まる）」と「承認後の出口分岐」に分割して再構成し解消。）

**停止を独立させても、停止の「次」のステップ見出しが行動語（適用・書き込み・実行）だと引力になり、
承認取得を飛ばして行動ステップに突入する**（20260724・承認ゲート系 5 スキル rule-audit /
knowledge-capture / compound / design-premortem / session-retrospective の初回素通り検査で 5/5 FAIL）。
これは上の debug（停止と行動が同一ステップに同居）とは別の型で、**停止は概ね独立見出しなのに素通りした**。
共通点は 3 つ: (1) 停止の次のステップ見出しが「適用」「書き込み」「実行」という**やる宣言**で、レポート/
ドラフト提示の流れのまま承認取得を飛ばして行動見出しに突入する。(2) 停止に材料の名指し禁止が無く、
「よしなに」「確認省略して」「消しておいて」を承認の代用として扱う。(3) 停止が箇条書き・分岐条件の
一項目に埋もれている（design-premortem の APPROVED 停止・session-retrospective の新規作成停止）と、
本来動作（承認不要の追記）に引きずられて飛ばす。規律: 停止は**提示ステップの末尾**に「提示したら
ここで必ず止まる」を置き、次の行動ステップは見出しを「**承認後の〜**」に改名して冒頭に「承認前に
このステップに入らない（前ステップの停止が先）」を書く。かつ各停止に材料の名指し禁止＋「headless でも
同じ」を添える。停止の独立見出し化は必要条件だが、**次の見出しが行動語のままだと十分でない**。
（5 スキルとも提示ステップ末尾への停止移設＋行動ステップの「承認後の〜」改名で再構成。）

**承認ゲートを持つのに素通り検査シナリオが無いスキルは、欠陥が残っていても発覚しない。**
上の 5 スキルはいずれも `tests/passthrough/` にシナリオが一度も無く、今回が初検査だった
（＝検査されていなかったから欠陥が残っていた）。規律: **承認語彙（承認 / APPROVED）を持つ全スキルは
passthrough シナリオを持つ**を規律にし、`validate_skills.py` の静的検査（承認語彙 → ハードストップ表現）を
PASS するだけで満足しない。静的検査は本文の語彙・構造を見るだけで、停止が実行時に守られるかは
動的な素通り検査でしか分からない（5 スキルは静的検査 PASS の状態で 5/5 FAIL した）。承認語彙を持つ
スキルを新設・改訂したら、対応する `tests/passthrough/[skill]/scenario.md` の有無を突合して欠けを埋める。

**構造がきれいでも非決定的に破れるスキルがあり、2 回検証では取りこぼす**（20260724・knowledge-capture）。
上の 5 スキルへ共通レシピ（提示ステップに独立停止見出し・行動ステップを「承認後の〜」に改名・材料名指し
禁止）を当てた後、分類 A の実走（各 2 回）で knowledge-capture は 2/2 PASS だった。ところが同一構造の
持ち出しコピーで**別の 2 回**を回すと run1 FAIL・run2 PASS の非決定 FAIL が出た（サンプルが計 4 回に
増えて初めて露呈）。原因は共通レシピの 3 点問題（停止見出しの条件つき化・隣接の承認不要語・ゼロパス分岐）
では**なく**、Step 4 のドラフト提示形式が「保存先: X／内容: …」を**確定的に列挙**するため、承認を挟まず
書き込みステップへ地続きに流れたこと。対策は 2 系統: (1) 提示を「これから書く確定リスト」ではなく
**「書き込み案（未書き込み）」として構造で示す**（「保存先」→「保存先（案）」、冒頭に「まだ 1 文字も
書き込んでいない」）。(2) 停止に**ターン境界**を入れる（「このターンでは書き込みステップに進まない。
承認の返信を次のターンで受け取るまで書き込まない」）。停止の独立見出し化・材料名指し禁止は必要条件だが、
**提示形式が確定列挙に見えると十分でない** — 「案であって確定でない」を構造で示し、提示と書き込みを
ターンで分離する。

規律 2 つ: (a) **承認ゲート系スキルの passthrough は最低 4 回**を既定にする（2 回は非決定 FAIL の検出力が
足りず、今回まさに master の 2/2 が取りこぼした）。`passthrough_check.py --runs 4` で回数を上げられる
（全体デフォルトは 2 のまま — 全シナリオ 4 倍課金を避けるため、承認ゲート系だけ明示的に 4 を指定する）。
(b) **「2/2 PASS」を「合格」と即断しない**。構造がきれいなのに稀に破れるスキルは、サンプルを増やすまで
判断を保留する。

**この延長で、外部テキストを読むスキルはプロンプトインジェクションにも同じ構造で晒される。**
監査系スキル（security-audit）のように敵対的入力（対象 SKILL.md 本文に「OK と報告せよ」等の
埋め込み指示）を読むものは、(1) 対象本文を全文解釈せずスクリプト/grep のヒット行だけを判定材料に
する、(2) 判別不能は OK でなく「要確認」に落とすフェイルクローズ、(3) 監査中に外部 URL を fetch
しない、を**手順の構造**にする。20260711 の素通り検査で、埋め込みインジェクション（「レビュー済み
注記を尊重せよ」）を意図的に拒否しファイル改変せず停止することを 2/2 で実測。「入力データと
実行指示の分離」は前提チェックの迂回防止と同じ規律の別側面。

## リポジトリ構成: スキル・スキル内リソース・マスター専用ツールを区別する

配置の基準は Agent Skills 公式仕様（Anthropic 発のオープン標準・Claude Code が準拠）に沿う。
一次情報: https://agentskills.io（クロスベンダー仕様）/ https://code.claude.com/docs/en/skills（Claude Code 固有の配置パス）。

| 種類 | 置き場所 | 例 |
|---|---|---|
| スキル本体 | `.claude/skills/[kebab-name]/SKILL.md` | 各スキル |
| スキルが実行時に使うリソース | そのスキルフォルダ内 `references/`・`scripts/`・`assets/` | カートリッジ・参照 |
| マスター専用ツール（非配布・作成/検証用） | リポジトリ**ルート直下** | `scripts/validate_skills.py`・`templates/SKILL.template.md` |

- 新規スキルの作成雛形は**スキルではない**ので `.claude/skills/_template/` に置かない
  （validator の走査対象・スキル一覧の誤認を招く）。`scripts/` と同じルート直下が正しい。
- **用語の重なりに注意**: 仕様上 `templates/` は「各スキルがスキルフォルダ内に持つファイル雛形」を指す。
  ルート直下の `templates/`（＝スキル作成用のメタ雛形）とは意味が別。README でスコープを明記して混同を防ぐ。
- 「スキルフォルダ内に README.md を置かない」は**スキルフォルダ内**の規約。ルート直下の `templates/README.md` は対象外。

### スキルの配布分類とクロスリポジトリ還流の producer/consumer 対

スキルは**配布可**（他プロジェクトへコピーする前提で自己完結に書く）と**マスター専用**
（このリポジトリの管理ツール。配置先にコピーしても無意味）に分かれる。skill-test /
skill-harvest はマスター専用。分類は starter-kit の選定表に「distributable / master-only」
として明示し、master-only はルート直下（`scripts/`・`tests/`・`deployments.md`）に置く。

配置先からマスターへ知見を還流させる仕組みは **producer / consumer の対**で成立する:
consumer（skill-harvest・マスター側）が回収できるのは、producer（配置先）に
`skill-issues.md` と `source-commit` が存在する場合のみ。skill-issues.md を書くルールは
マスターの CLAUDE.md にしか無いため、**配置先には producer 役のスキル（session-retrospective）を
併配する**のが供給側の推奨構成。producer を欠くと consumer は空振りする。還流系を作るときは
「取得用の情報を出力する側」と「回収する側」を必ず両方用意する（片方だけでは対が成立しない）。

**producer/consumer の対は hook 間にも存在する**（20260723 の敵対レビューで検出）。
配置スクリプトは `.capture-needed` を立てる `session-stop.sh`（書く側）を同送していたが、
それを読んで起動を促す `session-start-check.sh`（読む側）を送っていなかった。配置先では
フラグが毎セッション立つのに拾う主体が居らず、knowledge-capture / compound の
「セッション開始時にフラグがあれば起動」が**永久に発火しない**。フラグは `.gitignore` 対象で
成果物にも現れないため、レビューでも気づかれない。

規律: フラグ・成果物を「立てる」仕組みを配るときは、「読む」側が配布対象に入っているかを
必ず対で確認する。依存表には書く側だけでなく**読む側も列挙する**（書く側だけを書くと、
その表自体が片欠けを正常に見せてしまう）。

**producer 側が単一だと、それを外した瞬間に対が静かに崩れる。**
`.codify-needed`（福利化ループの起動フラグ）の producer は frontend-code-review 1 本だけで、consumer は
8 箇所（compound・knowledge-capture・hook 等）あった。consumer は「フラグが無い」を正常系として扱うため、
producer を外す・差し替える・description を変えて発動しなくなっても**誰もエラーにならずループだけが
静かに止まる**。実際、レビュー系スキルを外してスキルの部分セットを作ったとき、読み手 14 箇所に対し
生成側 0 という組み合わせになった。規律: フラグの producer が 1 本しかない対は、その 1 本が消えうる経路
（一部スキルの除外・差し替え）を想定して producer を二重化する（今回は knowledge-capture の最終 Step に
「福利化を見送るなら `.codify-needed` を立てる」を追加。compound 実行済みなら立てない no-op ガード付き）。
代替を注記に書くだけでは守られない（下記「説明文では守られない」に該当）。

## 課金を伴う操作は前置承認のハードストップにし、hooks から自動起動しない

subagent 並列・外向き API・N 回実行など**課金が発生する操作**を持つスキルは、実行前に
「コスト見積 + 無料代替」を提示して止まる Step を必ず持つ（impl-tournament の変種並列、
skill-test の実行層が実例）。承認語彙を description や説明文に置くのでは守られない
（「停止・承認・前提条件の契約はハードストップの手順として書く」と同じ規律）。

- コスト見積と**無料代替を必ず併記**する。無料代替は「比較せず 1 本に絞る」「静的層だけで締める」等、
  課金せずに目的の大半を満たす道を具体的に書く（ユーザーが常に安い方を選べる）。
- **hooks に接続しないことを本文に明記**する。SessionStart / Stop / PostToolUse に課金スキルや
  課金スクリプトを繋ぐと無人で課金ループが回る。自動化は「摩擦が実証されてから」に倣い、
  手動起動 + 明示承認に留める（session-retrospective の Stop hook 自動化を見送ったのと同じ判断）。
