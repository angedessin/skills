## 2. 課題整理

### 課題A: レビュー観点の欠落（タスク再起動が必要）
correctness（ロジックバグ）/ UI・ビジュアル・レスポンシブ / UX状態網羅の 3 観点が不在（issues-and-plan.md 課題3）。対応タスク `.steering/20260622-review-axes-coverage/` は 2026-06-22 に着手されたが**成果物が残っておらず、design-doc からの再起動が必要**。設計判断の素材（3-A の「ビルトイン /code-review 委譲か自前軸か」等）は issues-and-plan.md 課題3 に揃っている。

### 課題B: 持ち運び機構が半完成
- 手動コピー ADR（[20260612](./decisions/20260612-manual-copy-skill-distribution.md)）は確立しているが、規律を支える機構が未整備: `metadata.source-commit` によるドリフト追跡（4-B）、`skills-ref validate` による機械検証（4-C）がいずれも「次フェーズ」のまま
- 新規プロジェクトに配置するときの**スターターキット**（最小推奨セット + references 再生成テンプレート + CLAUDE.md 雛形）がなく、配置のたびに取捨選択と生成を頭から考える必要がある

### 課題C: ワークフローの穴
- E2E（Playwright）を主役にしたスキルが不在（スタックに明記されているのに付録扱い）
- debug（障害調査）が design-doc の看板に間借りしており、専用手順がない
- **変更を世に出すステップ（PR 作成・CI 確認）がワークフロー図にも feature-pipeline のフェーズにも不在**（課題1-C。pr-create ビルトインの位置づけで解決可能）
- README のスキル一覧に feature-pipeline が未掲載（ドキュメントドリフト）

### 課題D: 剪定機構の不在 — 懐疑派への回答が片輪
compound（ルールの追加・昇格）はあるが、rule-audit（既存ルールの削除・統合・GC）は設計案止まり。「AI が読めるドキュメントの維持コストは見合うのか」という社内の懐疑に対し、**肥大化を構造的に抑える仕組みがない状態では説明責任を果たせない**。追加と剪定は両輪で初めて健全（new-skills.md の診断どおり）。

### 課題E: 説明責任の定量根拠が未稼働
skill-creator による baseline 比較（スキルあり/なしの効果測定）・triggering 精度測定・回帰検出は設計済み（evaluation-system.md）だが運用未組み込み。懐疑派を説得する最強の材料は「スキルなしとの定量比較」だが、現状は質的検証（empirical-prompt-tuning）のみ。
**注意**: skill-creator eval は baseline 並列・複数回実行で dispatch 倍率が高く課金が跳ねる。導入時はコストを明示し、無料代替（empirical の構造審査モード / 静的 validate）を常に併記する（運用ルールとして固定）。

## 3. 改善の方向性（レイヤー分離の設計）

### 3-1. 前提の転換: スクラップ&リビルド → 複利資産 + 定期剪定

**「ルールファイルは都度スクラップ&リビルドするもの」という前提を正式に覆す。**

理由:
1. **効果検証が成立しない** — codify-log.md と review-result.md の突合による「昇格済みルールが効いているか（再発していないか）」の検知は、ルールの継続性が前提。スクラップするたびに検証履歴が消え、同じ失敗を再昇格するループに陥る
2. **説明責任がむしろ果たせない** — 懐疑派への回答は「このルールは過去のこの失敗から生まれ、以後再発していない」という追跡可能な因果。使い捨てルールにはこの物語がない
3. **スクラップ&リビルドが解こうとした問題（陳腐化・肥大化）は剪定で解ける** — Claude Code ベストプラクティスも「削除テスト」（このルールを消すと Claude が間違えるか？）による定期レビューを推奨しており、全捨てではなく選択的 GC が正攻法

ただしスクラップ&リビルドの健全な直感は残す: **「消すことを恐れない」**。rule-audit の削除テストがその受け皿になる。

### 3-2. 4 レイヤーモデル

エンジン＋カートリッジ契約を、スキル単位からワークフロー全体に拡張する。

```
Layer 0  普遍ワークフロー（マスター所有・全プロジェクト共通）
         design-doc / steering / impl-from-design / tdd / frontend-code-review
         / compound / knowledge-capture / feature-pipeline（フェーズ編成の型）
         / (新) rule-audit / (新) debug / (新) e2e
         → SKILL.md 本文 = スタック非依存の判断軸。再コピーで上書き

Layer 1  普遍レビュー軸 = 事実上の「普遍 Rules」（マスター所有）
         TypeScript / a11y / セキュリティ / パフォーマンス / テスト品質
         / correctness / UX状態網羅（review-* サブスキル + impl-review の軸）
         → 「ルール」を宣言的リストでなく実行可能なレビュー観点として持つ

Layer 2  プロジェクトカートリッジ（配置先所有・再コピーで上書きしない）
         references/（スタック固有 API・規約）/ compatibility frontmatter
         / CLAUDE.md（発動ポリシー・行動ルール）/ settings.json
         → 配置時にテンプレートから生成。デザイントークン・コンポーネント規約はここ

Layer 3  プロジェクト固有ナレッジ（配置先所有・持ち運ばない）
         .steering/（タスクコンテキスト）/ docs/knowledge/ / docs/decisions/(ADR)
         → compound / knowledge-capture の出力先。プロジェクトの複利資産
```

設計上の要点:

- **「普遍 Rules」はドキュメントではなくレビュースキルとして実装する**。宣言的なルールリスト（「XSS に注意せよ」等）は毎ターンのコンテキスト固定費になり読まれない。レビュー軸として実行時にだけ読み込まれる形が、コストと実効性の両面で優れる（progressive disclosure）。CLAUDE.md に載せる普遍ルールは「行動ルール（短い命令形）」のみに限定し続ける
- **feature-pipeline はワークフロー図の「実行可能な表現」として Layer 0 に置く**。フェーズ構成（何を・どの順で・どこに承認ゲートを置くか）は普遍、各フェーズが呼ぶサブスキルの存在確認とフォールバックは既にスキル側が持つ（skill-design-patterns.md の自己完結原則）。ワークフロー図を変えるときは feature-pipeline も同時に変える — 図とオーケストレーターの二重管理が本計画で最初に踏むドリフト地雷
- **Layer 3 の知見は compound を通じて Layer 0/1 に昇格しうる**（プロジェクトで得た普遍的パターンをマスターに還元）。逆方向の流路が複利の源泉
- **Layer 2 と Layer 3 の境界** = 「別スタックのプロジェクトに持っていったとき書き換えが必要か」。references は書き換える（カートリッジ）、ADR は持っていかない（固有）

### 4-2. 普遍だが新規設計が必要（Layer 0 追加候補）

| カテゴリ | 判定 | 根拠 |
|---|---|---|
| **E2E テスト** | 普遍（新スキル `e2e`、new-skills.md 設計案あり） | 「クリティカルパスに絞る」「1テスト1シナリオ」「明示的待機・テスト間独立」はテストピラミッドの普遍原則。Playwright API はカートリッジへ |

### 4-3. 普遍ではない / 条件付き

| カテゴリ | 判定 | 理由 |
|---|---|---|
| **i18n / l10n** | 条件付きオプトイン | 国際化しないプロジェクトでは誤検知ノイズになる（issues-and-plan.md 3-D の判断を維持）。オプション軸としてマスターに置き、配置先が compatibility で有効化する形 |

## 5. ワークフローの見直し案

### 5-1. 現行 8 ステップの評価

現行（設計→人間承認→実装→レビュー→修正→福利化→ナレッジ保存→アーカイブ）は Plan → Design → Implement → Review → Learn のフェーズ構造として既に成立しており、**骨格の変更は不要**。人間承認ゲート（design.md APPROVED）と自己改善ループ（compound）は他所にない強みなので維持する。feature-pipeline がこのフェーズ構造を一気通貫で駆動する形も既に存在する。

### 5-2. 変更点（5つ）

```
[0] 入口分岐（新設）
     新機能 → design-doc ／ バグ・障害 → debug（原因特定 → 小さければ即修正、
     大きければ design-doc に接続）
       ↓
[1] 設計 design-doc → [2] 人間レビュー（DRAFT → APPROVED）
       ↓
[3] 実装 impl-from-design ←→ tdd ／ クリティカルパスは e2e（新設）
       ↓
[4] コードレビュー frontend-code-review
     フル: 6 エージェント並列（review-ui 追加後）+ correctness（担い先は Research で確定）
       ↓
[5] 指摘修正 → 差分再レビュー
       ↓
[6] PR / 統合（新設・図に明記）: pr-create → CI 確認 → マージ
       ↓
[7] 福利化 compound → [8] ナレッジ保存 knowledge-capture → [9] アーカイブ

     定期（フェーズ外）: rule-audit — CLAUDE.md・ルールの削除テスト・統合・GC
     一気通貫実行: feature-pipeline（上記フェーズを承認ゲート付きで編成）
```

1. **入口分岐の新設**: design-doc の description から「障害調査」を外し、`debug` に委譲（new-skills.md の決定方針どおり）。バグ修正が新機能と同じ入口を通る現状の歪みを解消
2. **PR / 統合フェーズを図に明記**: 変更を世に出すステップの不在（課題1-C）を、新スキルなしで pr-create の位置づけにより解決
3. **E2E の位置づけ**: 実装フェーズ [3] に「クリティカルパスは e2e」の分岐を明記
4. **rule-audit を定期メンテとして併走**: フェーズの中ではなく、compound がルールを増やすことへのカウンターとして定期実行（増やす→埋もれる→刈るのループを閉じる）

## 6. 他プロジェクトへの持ち運び実装案

### 6-1. 現行 ADR の維持と、再検討条件の明記

手動コピー ADR（誤発動防止のガードレール・人が完全把握）は**個人利用の範囲では維持**する。ただし社内展開という新しい文脈に対し、段階基準を定める:

| 段階 | 条件 | 配布方式 |
|---|---|---|
| 現在（個人・数プロジェクト） | 配置先 ≤ 3 程度 | 手動コピー + source-commit 記録 |
| 拡大（個人・多数 or チーム試験導入） | 配置先が増えドリフト管理が手に余る | バージョンタグ付きスターターキット + 配置スクリプト（選択は人・記録は自動） |
| チーム標準化 | 複数メンバーが同じスキルセットを使う | プラグイン化 or テンプレートリポジトリ（ADR を正式に改訂） |

ADR の「プラグイン化は個人用途には過剰」という判断は正しいが、**チーム展開では前提が変わる**ため、その時点で ADR 改訂をトリガーする（今は改訂しない）。

### 6-2. 機構の実装（3点）

1. **`metadata.source-commit` の導入（4-B）** — 全スキルの frontmatter に version / source-commit を持たせ、配置時に記録。ドリフト検知が `git diff <hash>` 一発になる
2. **`skills-ref validate` の CI 組み込み（4-C）** — frontmatter・命名・行数（<500行 / <5000トークン）の機械検証をマスター側の品質ゲートに。手動目視を削減
3. **スターターキットの整備** — 新規プロジェクト配置を「考える作業」から「選ぶ作業」にする:
   - 最小推奨セット（例: design-doc + frontend-code-review + サブスキル + knowledge-capture）と拡張セットの推奨構成表。feature-pipeline は「フルワークフローを回すプロジェクト」向けの拡張セット側（依存サブスキルが揃っていることが前提のため最小セットには含めない）
   - references 再生成テンプレート（現 React/Vitest 版を「example — 自分のスタック用に再生成せよ」と明記して同梱。issues-and-plan.md「マスターが同梱するもの」の具体化）
   - CLAUDE.md 雛形（発動ポリシー節のみ。行動ルールは配置先が育てる）

### 6-3. 社内の懐疑派への説明責任

「維持コストは見合うのか」への回答を構造で持つ:

- **コストの上限を構造で保証**: CLAUDE.md は行動ルールのみ・≤200行（毎ターン固定費の抑制）、知識は docs/knowledge/ へ逃がして必要時のみ @参照、ルールは rule-audit で定期 GC — 「維持コストが単調増加しない」設計であることを示せる
- **効果の追跡可能性**: codify-log.md による「このルールはこの失敗から生まれ、以後再発していない」の因果追跡。定量が要る場面では skill-creator の baseline 比較（スキルあり/なし）を**コスト明示のうえ選択的に**実施（常用しない。軽い検証は empirical の構造審査モード = ほぼ追加コストゼロ）
- **導入の低リスク性**: スターターキットは最小セットから始められ、スキルは自己完結（CLAUDE.md・docs/ が無くても動く）なので、試験導入の初期コストが小さい
