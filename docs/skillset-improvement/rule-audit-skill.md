# 新スキル設計メモ — `rule-audit`（CLAUDE.md / ルールの継続的見直し）

作成日: 2026-06-13
ステータス: **設計案（実装前）**
出典: [Claude Code ベストプラクティス](https://code.claude.com/docs/ja/best-practices)「効果的な CLAUDE.md を書く」節

---

## 背景・動機

プロジェクトで継続的に使うと、CLAUDE.md やルールは放置すると**肥大化・陳腐化**する。
ベストプラクティスは明確に警告している:

> 肥大化した CLAUDE.md ファイルは Claude があなたの実際の指示を無視するようにします。
> CLAUDE.md をコードのように扱う：物事がうまくいかないときにレビューし、定期的に削除する。

→ ルールを**定期的に剪定・監査するスキル**が必要。

---

## 既存 `compound` との棲み分け（最重要）

| | `compound`（既存） | `rule-audit`（新規） |
|---|---|---|
| 方向 | **追加・昇格**（学びを新ルールに） | **剪定・整理**（既存ルールの健全性監査） |
| 入力 | review-result.md / decisions.md / skill-issues.md | CLAUDE.md / rules / docs/knowledge/ そのもの |
| 出力 | 新ルール・知識・スキルのドラフト | 各ルールの「保持/削除/統合/移動/明確化」判定 |
| 再発検知 | ○（codify-log と突合） | ✕（compound に委譲、再実装しない） |

**両輪の関係**: compound がルールを増やす → CLAUDE.md 肥大化 → ルールが埋もれる →
rule-audit が刈り取る。**セットで初めて健全**。

---

## 監査基準（ベストプラクティスから抽出）

### 1. 削除テスト（各ルールに適用）
> 「このルールを削除すると Claude が間違いを犯すか？」→ No なら削除候補

### 2. 症状ベースの診断
| 症状 | 示唆 | 対応 |
|---|---|---|
| ルールがあるのに守られない | ファイルが長すぎてルールが埋もれている | 削除 or フック化 |
| CLAUDE.md で答えられる質問をしてくる | 表現が曖昧 | 具体例を追加して明確化 |

### 3. 含める/除外する判定
**除外候補（削除対象）**:
- Claude がコードを読めば分かること
- 標準的な言語規約（Claude が既に知っている）
- 「きれいなコードを書く」等の自明なプラクティス
- 頻繁に変わる情報
- ファイルごとのコードベース説明・長い説明/チュートリアル

**保持すべきもの**:
- 推測できない Bash コマンド / 必須環境変数
- デフォルトと異なるコードスタイル
- テスト指示・推奨ランナー
- リポジトリのエチケット（ブランチ命名・PR 規約）
- プロジェクト固有のアーキテクチャ決定
- 一般的な落とし穴・明白でない動作

### 4. 昇格先の振り分け（CLAUDE.md から出すべきもの）
- **例外なく毎回起きるべき** → フック（決定論的）へ
- **ドメイン知識・たまにしか使わない** → スキルへ（オンデマンド読み込み）
- **詳細な説明** → docs/knowledge/ へ移して `@参照`

### 5. 構造制約（このリポジトリ固有）
- CLAUDE.md は ≤200行・行動ルールのみ（知識の倉庫にしない）
- 重複ルールの統合
- このリポジトリの既存ナレッジ保存先ルール（行動ルール/経験/ADR/タスク固有）との整合

## スキル仕様（ドラフト）

```
name: rule-audit
description: CLAUDE.md / ルールファイルを定期監査し、肥大化・陳腐化・曖昧・重複・
             効果のないルールを検出して剪定する。「ルールを見直して」「CLAUDE.md を
             整理して」が対象。compound（ルール追加）と対をなす剪定スキル。
```

### 手順案
1. **入力収集** — CLAUDE.md（無ければ AGENTS.md 等を確認）・`~/.claude/CLAUDE.md`・docs/knowledge/ を読む。`.steering/` があれば codify-log.md も参照（過去の昇格履歴）
2. **各ルールを5基準で判定** — 保持 / 削除 / 統合 / 移動（フック・スキル・docs） / 明確化
3. **行数・重複チェック** — ≤200行制約、同義ルールの検出
4. **スキル frontmatter の機械検証** — `.claude/skills/` がある場合は `skills-ref validate ./<skill>` を各スキルに実行し、命名規約・description ≤1024文字・本文 ≤500行（progressive disclosure 推奨値）違反を検出。ツール未導入なら手動で同等チェック（name=ディレクトリ名一致 / 文字数 / 行数）
5. **監査レポート提示** — 各ルール・各スキルに判定＋理由。承認制
6. **承認分のみ適用** — 削除・統合・移動を実行。移動先（フック/スキル）が必要なら骨組みも生成
7. **（任意）effectiveness テスト案内** — 変更後に挙動が変わるか観察するようユーザーに促す

> agentskills.io 仕様の詳細活用（compatibility / metadata 等）は [20260613-improvement-plan.md](./20260613-improvement-plan.md) の論点4 を参照。

### 自己完結のためのフォールバック
- CLAUDE.md が無いプロジェクト → 監査対象（AGENTS.md・.cursorrules 等）をユーザーに確認
- `.steering/` が無い → codify-log 突合はスキップ（その旨レポートに明記）

## 運用（定期実行）

「継続的見直し」が主眼なので、単発実行だけでなく定期実行と相性が良い:
- `/loop` で自己ペース実行
- `/schedule`（cron）で週次など定期監査

→ ルールが増えすぎる前に定期的にガベージコレクションする運用が組める。

---

## 検証

新規スキルなので作成後に `empirical-prompt-tuning` でフレッシュな subagent に実行させ、
- 監査基準が曖昧でないか
- compound との役割混同が起きないか
を両面評価する。
