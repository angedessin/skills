## `e2e`（Playwright E2E）

### 背景
スタックに `Playwright` が明記され `tdd/references/patterns.md` に「E2E」節もあるが、E2E を主役にしたスキルが無い。`tdd` は Vitest + RTL + MSW 専用、`test-review` は Playwright 設定の監査を「対象外」と宣言。結果 E2E は付録扱いで、いつ・どの粒度で書くか、どの軸でレビューするかをワークフロー上で誰も担っていない。認証・チェックアウト等のクリティカルパス品質がワークフローの外にこぼれる。

### 決定方針（要詳細設計）
- `e2e` スキル新設を第一候補とする（`tdd` / `test-review` への E2E 軸拡張は副案）
- 担うべき判断軸（叩き台）:
  - **何を E2E にするか**: クリティカルパス（認証・決済・主要導線）に絞る。ユニット/インテグレーションで足りるものは E2E にしない（テストピラミッド）
  - **粒度**: ページ横断のユーザーシナリオ単位。1テスト1シナリオ
  - **安定性**: ロケータ優先順位（role/label > test-id > CSS）、待機は明示的（auto-wait 活用、固定 sleep 禁止）、テスト間独立
  - **レビュー軸**: flaky の温床（暗黙待機・順序依存・共有状態）、実ユーザー視点の検証になっているか
- references/ に Playwright API 具体例を集約（本文はツール非依存の判断軸に保つ＝課題2の教訓）

### 未決
- 単独スキルか `tdd`/`test-review` 拡張か（工数とトリガー設計次第）
- ワークフロー図での位置づけ（実装フェーズ [3] のテスト群に E2E をどう並べるか）

## `debug`（障害調査）

### 背景
`design-doc` は description で「障害調査に使う」と謳うが、実体は設計ドキュメント作成スキルで調査手順を持たない。看板と中身が乖離している。バグ修正は新機能とフローが逆（設計より先に原因特定が要る）なのに専用手順がない。

### 決定方針
「障害調査」と「コード探索」は別の関心。分離して独立スキル化する。
- フロー: 再現確認 → 仮説立案 → 切り分け（二分探索的に） → 根本原因特定 → 修正方針
- 設計（design-doc）とは順序が逆（原因特定が先）なので別スキルが妥当
- 記録先: `.steering/[task]/investigation.md`（無ければ会話内）
- **`design-doc` の description から「障害調査」を外し、`debug` へ委譲**（この description 修正もこのスキル実装とセットで行う）

## `explore`（コード探索）

### 役割
既存コードの構造・依存・データフロー・命名規約を把握する。**障害調査・新機能実装・リファクタすべての共通基盤**になる。

### ★要確認: ビルトインとの重複
ビルトインの `Explore` エージェント / `feature-dev:code-explorer` と役割が重複する。
- 案A: 独自スキルを新設（このリポジトリの規約・出力形式に最適化）
- 案B: ビルトインを使う「使い方ガイド」薄いスキルに留める
- 案C: `impl-from-design` が既に参照している "code-explorer" の実体を確認し、それを正式化

**暫定推奨: まず案C で現状の実体を確認 → 不足なら案A**。実装着手前に `impl-from-design` の "code-explorer" 参照先を実機確認すること。

## `rule-audit`（CLAUDE.md / ルールの継続的見直し）

出典: [Claude Code ベストプラクティス](https://code.claude.com/docs/ja/best-practices)「効果的な CLAUDE.md を書く」節

### 背景・動機
継続運用すると CLAUDE.md やルールは放置で**肥大化・陳腐化**する。ベストプラクティスは明確に警告:
> 肥大化した CLAUDE.md ファイルは Claude があなたの実際の指示を無視するようにします。CLAUDE.md をコードのように扱う：物事がうまくいかないときにレビューし、定期的に削除する。

→ ルールを**定期的に剪定・監査するスキル**が必要。

### 既存 `compound` との棲み分け（最重要）
| | `compound`（既存） | `rule-audit`（新規） |
|---|---|---|
| 方向 | **追加・昇格**（学びを新ルールに） | **剪定・整理**（既存ルールの健全性監査） |
| 入力 | review-result.md / decisions.md / skill-issues.md | CLAUDE.md / rules / docs/knowledge/ そのもの |
| 出力 | 新ルール・知識・スキルのドラフト | 各ルールの「保持/削除/統合/移動/明確化」判定 |
| 再発検知 | ○（codify-log と突合） | ✕（compound に委譲、再実装しない） |

**両輪の関係**: compound がルールを増やす → CLAUDE.md 肥大化 → ルールが埋もれる → rule-audit が刈り取る。**セットで初めて健全**。

### 監査基準（ベストプラクティスから抽出）
**1. 削除テスト**: 「このルールを削除すると Claude が間違いを犯すか？」→ No なら削除候補

**2. 症状ベースの診断**
| 症状 | 示唆 | 対応 |
|---|---|---|
| ルールがあるのに守られない | ファイルが長すぎてルールが埋もれている | 削除 or フック化 |
| CLAUDE.md で答えられる質問をしてくる | 表現が曖昧 | 具体例を追加して明確化 |

**3. 含める/除外する判定**
- 除外候補（削除対象）: Claude がコードを読めば分かること / 標準的な言語規約 / 「きれいなコードを書く」等の自明なプラクティス / 頻繁に変わる情報 / ファイルごとのコードベース説明・長いチュートリアル
- 保持すべきもの: 推測できない Bash コマンド・必須環境変数 / デフォルトと異なるコードスタイル / テスト指示・推奨ランナー / リポジトリのエチケット（ブランチ命名・PR 規約） / プロジェクト固有のアーキテクチャ決定 / 一般的な落とし穴・明白でない動作

**4. 昇格先の振り分け（CLAUDE.md から出すべきもの）**
- 例外なく毎回起きるべき → フック（決定論的）へ
- ドメイン知識・たまにしか使わない → スキルへ（オンデマンド読み込み）
- 詳細な説明 → docs/knowledge/ へ移して `@参照`

**5. 構造制約（このリポジトリ固有）**
- CLAUDE.md は ≤200行・行動ルールのみ（知識の倉庫にしない）/ 重複ルールの統合 / 既存のナレッジ保存先ルールとの整合

### スキル仕様（ドラフト）
```
name: rule-audit
description: CLAUDE.md / ルールファイルを定期監査し、肥大化・陳腐化・曖昧・重複・
             効果のないルールを検出して剪定する。「ルールを見直して」「CLAUDE.md を
             整理して」が対象。compound（ルール追加）と対をなす剪定スキル。
```

### 手順案
1. **入力収集** — CLAUDE.md（無ければ AGENTS.md 等を確認）・`~/.claude/CLAUDE.md`・docs/knowledge/ を読む。`.steering/` があれば codify-log.md も参照（過去の昇格履歴）
2. **各ルールを5基準で判定** — 保持 / 削除 / 統合 / 移動（フック・スキル・docs） / 明確化
3. **行数・重複チェック** — ≤200行制約、同義ルールの検出
4. **スキル frontmatter の機械検証** — `.claude/skills/` がある場合は `skills-ref validate ./<skill>` を各スキルに実行し、命名規約・description ≤1024文字・本文 ≤500行違反を検出。ツール未導入なら手動で同等チェック（name=ディレクトリ名一致 / 文字数 / 行数）
5. **監査レポート提示** — 各ルール・各スキルに判定＋理由。承認制
6. **承認分のみ適用** — 削除・統合・移動を実行。移動先（フック/スキル）が必要なら骨組みも生成
7. **（任意）effectiveness テスト案内** — 変更後に挙動が変わるか観察するようユーザーに促す

> agentskills.io 仕様の詳細活用（compatibility / metadata 等）は [issues-and-plan.md](./issues-and-plan.md) の論点4 を参照。

### 自己完結のためのフォールバック
- CLAUDE.md が無いプロジェクト → 監査対象（AGENTS.md・.cursorrules 等）をユーザーに確認
- `.steering/` が無い → codify-log 突合はスキップ（その旨レポートに明記）

### 運用（定期実行）
「継続的見直し」が主眼なので単発実行だけでなく定期実行と相性が良い。`/loop`（自己ペース）/ `/schedule`（cron で週次など）でルールが増えすぎる前に定期 GC する運用が組める。

### 検証
新規スキルなので作成後に `empirical-prompt-tuning` でフレッシュな subagent に実行させ、監査基準が曖昧でないか / compound との役割混同が起きないかを両面評価する。

### 未決事項
1. スキル名: `rule-audit` / `claude-md-review` / その他
2. 監査対象スコープ: CLAUDE.md のみ / docs/knowledge/ も含む / スキルの description・frontmatter も含む
3. 定期実行を前提に組み込むか（`/schedule` 連携の手順をスキルに含めるか）
4. `skills-ref validate` の導入要否（CLI インストールするか、手動同等チェックで済ませるか）

## `prompt-lint`（プロンプト静的レビュー）

追記日: 2026-06-17 / ステータス: **設計案（議論中）**
出典: [Claude prompting best practices](https://platform.claude.com/docs/ja/build-with-claude/prompt-engineering/claude-prompting-best-practices)

### 動機
Anthropic の prompting best-practices doc に照らして**プロンプトを静的にレビューする**スキル。会話中に手で「このプロンプト何点？」を評価した作業（doc 項目との照合）を反復可能な形に昇格させる。

### 既存3層との関係（重要 — 混同防止）
このスキルは**スキル評価ではなくプロンプト検証**。[evaluation-system.md](./evaluation-system.md) の3層（①②③）はいずれも *skill* が対象だが、`prompt-lint` は **プロンプト全般**（再利用プロンプト / SKILL.md / slash command / 会話の一発メッセージ）が対象。

`empirical-prompt-tuning`（①）との違いは**手法だけ**で、両方とも「プロンプトを検証する」点では同じ:
| | `prompt-lint`（静的） | `empirical-prompt-tuning`（①・動的） |
|---|---|---|
| 手法 | doc のチェックリストに**読んで照合** | 実行者に**走らせて**挙動を観測 |
| 分かること | 書き方の曖昧さ・不足 | 動かして初めて出る意図とのズレ |
| コスト | 軽い・即時 | 重い（dispatch） |

→ 連結（hard handoff）はしない。**独立スキル**とし、末尾で「より厳密には empirical もある」と**軽い see-also** に留める。③ validate との違いも明確: ③は frontmatter/命名/行数の**構造**チェック、`prompt-lint` はプロンプト**本文の内容品質**チェック。

### 確定した方針
- **位置づけ**: 独立スキル（① empirical とは別物、相互参照は see-also のみ）
- **対象スコープ**: 両方（再利用プロンプト＋会話の一発メッセージ）。**最初にプロンプト種類を判定**して基準を変える
  - 会話の一発に「単独可搬性（黄金律）」を厳しく求めても無意味 → 種類で合格ラインを分ける
- **doc の扱い**: 要点を `references/checklist.md` に**蒸留同梱**。ライブ fetch しない（ネットワーク依存を避け配置先でも動く）。doc はモデルバージョン依存記述を含むため**最終同期日を記録**して陳腐化を検知する

### スキル像（叩き台）
```
トリガー: 「このプロンプトをチェックして」「プロンプトをレビュー」
入力: 貼り付け / ファイルパス / SKILL.md
Step1: プロンプト種類を判定（会話一発 / 再利用システム / コード生成 / agent タスク）
Step2: 種類に応じた doc 項目で照合
  - 明確さ・出力形式の指定 / コンテキスト・動機 / 例(multishot)
  - 構造化(XML・番号) / 役割付与 / 「やるな」でなく「やれ」
  - (agent系のみ) ツール明示 / 過剰設計ガード / ハルシネーションガード
  - 単独可搬性（黄金律）
Step3: 項目ごとに pass/warn/fail ＋ 具体的な書き換え案
  → 重大な曖昧さが残れば empirical-prompt-tuning を see-also で案内
```
- スコアは**単一点数より項目ごとの pass/warn/fail**（点数はノイズが大きい。出すなら「参考値」明記）
