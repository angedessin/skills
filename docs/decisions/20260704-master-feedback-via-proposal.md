# Decision: マスターへの還元は提案渡しで行う（配置先セッションによる直接編集の禁止）

Date: 20260704
Status: Accepted

## Context

初回配置検証（_test）で、配置先プロジェクトのセッションで実行された compound が、スキル改善の還元としてマスターの SKILL.md 2 本を直接編集した。compound の承認ゲート（ユーザー承認）は通っていたが、追加されたメカニズム（会話内フォールバックの呼び出し契約）は実地で一度も動いていない推測ベースの設計で、マスター側の記録済み方針（指摘 8: .steering 強制)と方向が矛盾していた。マスターの作業ツリーに未レビューの変更が静かに混入した状態になり、後に revert した（文面は `.steering/archived/20260703-first-deployment/compound-proposal.patch` に保存）。

配布方式の大元は [ADR 20260612](20260612-manual-copy-skill-distribution.md)（手動コピー配布・改善はマスターに還元して再コピー）。本 ADR はその「還元」の運用を精緻化する。

## Decision

配置先プロジェクトのセッションはマスターのファイルを直接編集しない。還元は patch または skill-issues.md への記録として**提案の形で渡し**、マスター側のセッションでレビューして適用する。

## Rationale

- 配置先セッションでのユーザー承認は、マスターの作業ツリーの管理下にない（マスター側の git 履歴・レビュー・validate を通らずに変更が入る）
- 「実地で動いた実績のあるパターンの記録」と「未検証の新設計の提案」が区別されないまま契約として書き込まれる
- マスター側で適用すれば、validate・片側修正チェック（grep）・既存方針との整合確認が通常のフローで働く

## Consequences

- Good: マスターの変更が常にマスター側のレビューと検証を通る。未検証メカニズムの混入を構造的に防げる
- Bad: 還元に 1 手間増える（提案の受け渡し → マスター側セッションで適用）

## Alternatives considered

| Alternative | Reason rejected |
|-------------|-----------------|
| 配置先からの直接編集を許可し続ける（承認ゲートのみで防ぐ） | 今回の混入がまさに承認ゲートを通過して起きた。ゲートは「編集してよいか」しか見ず、「マスターの方針と整合するか」は見られない |
| マスターを常に読み取り専用にする（技術的強制） | 個人開発でファイルシステム的な強制は過剰。compound の手順への明記（20260704 適用済み）で十分 |
