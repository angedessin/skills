# ユーザーガイド — スキルの使い方

対象: これらのスキルが入ったプロジェクトで開発する人（このマスターリポジトリ・配置先の両方）。配置先の `docs/` にそのままコピーしてよい。スキルの一覧と配り方は、マスターリポジトリの README にある。

## スキルとは

特定の依頼で自動で発動し、その作業の手順と止まる場所に沿って Claude が動くプリセット。コマンドを覚える必要はなく、自然な日本語で頼めばよい。各スキルがいつ発動し、いつ発動しないかは、`SKILL.md` の冒頭（description・when_to_use）に書いてある。

スキルは、スキルなしの Claude より良い結果になることを評価で確かめたものを残すのが原則。例外は、同点でも残した design-doc・design-premortem と、評価していない pr-create。残っているのは、ユーザーに決めてもらうことを聞いて止まる・外に出る操作の前で止まる・決まった記録先を守る、といった役割のもの。

## 作業の大きさで変わる進め方

CLAUDE.md の「作業の進め方」による。Claude が段階を決めて宣言し、迷うときだけ聞く。「ちゃんと設計して」「直接やって」でいつでも変えられる。

| 段階 | 例 | 進め方 |
|---|---|---|
| 小さな作業 | typo・数行の修正・設定の変更・試作・調査だけ | 「小さな作業として直接進めます」と宣言して進める |
| 中くらいの作業 | 1 セッションで終わるが決めることがある | 会話の中で設計を示して止まる → OK で実装 |
| 大きな作業 | 複数セッションにまたがる・経緯を残したい | `.steering/[日付]-[名前]/` に design.md（DRAFT）を作って止まる → APPROVED で実装 |

## 自分から言うフレーズ

| 状況 | 言うこと | スキル | 何が起きるか |
|---|---|---|---|
| 新しい機能・変更を始める | 「〜を作りたい」「まず設計して」（仕様書や参考があれば貼る） | design-doc | ユーザーにしか決められないことを聞き、設計を示して**承認を求めて止まる** |
| 設計の穴を探したい | `/design-premortem [design.md のパス]` | design-premortem | 文脈を持たない攻撃役が design.md を読み、失敗の原因になる穴を追記する（手動で呼ぶときだけ動く） |
| 途中のタスクを再開する | 「〜の続きから」「〜を再開して」 | steering | design.md・tasklist.md・decisions.md を読み合わせ、次の項目を示す。DRAFT なら実装しない |
| 進行中のタスクを見る | 「進行中のタスクは？」 | steering | アクティブなタスクと進み具合の一覧 |
| タスクを終える | 「〜をアーカイブして」 | steering | 残りの項目を示し、確認を取ってから `.steering/archived/` へ移す |
| E2E テストを書く・見る | 「E2E テストを書いて」「この E2E をレビューして」 | e2e | 主要な流れに絞って書く。レビューでは直さずに指摘を返す |
| コードをレビューする | 「コードをレビューして」 | frontend-code-review | バグ担当・規約担当などが一次レビューし、検証役が確かめた指摘だけを返す。コードは直さない |
| PR を出す | 「PR を作って」 | pr-create | コミットとブランチを整え、タイトルと本文を示して **push の前に止まる**。マージはしない |
| セッションを振り返る | 「振り返りして」 | session-retrospective | 訂正・手戻り・拒否・曖昧さを `.steering/[task]/skill-issues.md` に記録する |

スキルの無い依頼（テストを書く・バグを調べる・知見を保存する・CLAUDE.md を見直すなど）は、スキルなしで普通に頼めばよい。評価で、スキルなしでも同じくらいできると分かったものは、原則として削除している。

## よくある疑問

**Q. スキルを使わずに開発できる？**
できる。普通の依頼にはスキルは発動しない。ただし CLAUDE.md の「作業の進め方」（大きな作業は design.md で止まる、など）はスキルとは関係なく効く。

**Q. 途中でやめられる？**
できる。止まる場所（設計の承認・push の前など）で「今日はここまで」と返せばよい。大きな作業は `.steering/[task]/` に状態が残るので、次のセッションで「〜の続きから」と言えば再開できる。

**Q. `.steering/` は git にコミットする？**
する。設計・決定・タスクの状態は、別のセッションで再開するときの入力になる。feature ブランチで始めたタスクは、develop へのマージ前にアーカイブまで済ませる。

## 使うときのコツ

- **止まったら、それは仕様。** 設計・レビュー結果・PR の内容を人が確かめるための停止点。内容を見て「OK」「直して」「後で」を返す
- **急ぎの小さな修正は、そのまま頼む。** typo・1 行の修正に設計は要らない
- **スキルが変な動きをしたら**「振り返りして」で記録しておく。たまったら「skill-issues を見て改善案を出して」と頼む
