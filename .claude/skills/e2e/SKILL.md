# E2E

エンドツーエンドテストの作成とレビュー。

このスキルは「エンジン＋カートリッジ」構成: 本文はツール非依存の判断軸、具体的な API・コード例は `references/patterns.md`（カートリッジ）に §名で置く。**`references/patterns.md` が無い場合**は、具体例は出せないが下記の判断軸はツール非依存なので**そのまま適用して続行する**（その旨を伝える）。

## When NOT to use

- ユニット/インテグレーションテストを書く → `tdd`
- ユニット/インテグレーションテストのレビュー → `test-review`
- E2E ランナーの設定・CI 整備の監査 → 本スキルの対象外（test-review がテストインフラを対象外とするのと同じ線引き）

## モード判定

依頼内容から判定する: 新しくテストを書く → **作成モード** / 既存 E2E テストの diff・指定ファイルを見る → **レビューモード**。判別できなければユーザーに確認する。

---

## 4つの判断軸（両モード共通のエンジン）

### 軸 1 — 対象選定: クリティカルパスに絞る

E2E はテストピラミッドの最上層 — 最も高価で遅く、flaky になりやすい。

- 対象: 認証・決済・主要導線など、**落ちるとビジネスが止まるユーザーフロー**
- 対象外: ロジックの分岐網羅（ユニットの仕事）、単一コンポーネントの振る舞い（インテグレーションの仕事）
- 常に問う: 「この確認はより下の層でできないか？」— できるなら E2E にしない（`tdd` に案内）

### 軸 2 — 粒度: 1 テスト 1 シナリオ

- ページ横断の**ユーザー行動単位**でシナリオを切る（例: ログイン → 商品選択 → 購入完了）
- 1 テストに複数シナリオを詰めない — 落ちたとき原因が特定できない
- シナリオ名はユーザーの語彙で付ける（実装の語彙ではなく）

### 軸 3 — 安定性: flaky の温床を作らない

- **ロケート**: ユーザー可視の意味（役割・アクセシブルネーム）> テスト専用属性 > CSS セレクタの順。優先順位ラダーの具体は `references/patterns.md §locators`
- **待機**: 明示的な条件で待つ。固定時間の sleep は禁止（ランナーの自動待機機構を活かす）。→ `§waiting`
- **独立**: テスト間の順序依存・共有状態を作らない。各テストが自分で前提を整える。認証など高価な前提は再利用の仕組みで共有する。→ `§auth`
- **テストデータ**: 並行実行・再実行で衝突しない一意なデータを使う。→ `§fixtures`

### 軸 4 — 実ユーザー視点の検証

- アサートするのは**ユーザーが観察できる結果**（画面表示・URL 遷移・通知）
- API レスポンスや内部状態のアサートで代用しない — それはインテグレーションの仕事で、E2E でやると「ユーザーには壊れて見えるのにテストは緑」を生む

## 作成モード

1. **対象選定** — 軸 1 で妥当性を確認する。下層のテストで足りる場合は `tdd` を案内して終了
2. **シナリオ分解** — ユーザー行動のステップと各ステップの期待結果をリスト化する（軸 2）
3. **実装** — 軸 3・軸 4 を適用する。具体 API は `§locators` / `§waiting` / `§auth` / `§fixtures`（references が無ければ判断軸のみ適用し、その旨を伝える）
4. **安定性確認** — 実行して緑を確認する。可能なら同一テストを複数回実行して flaky でないことを確かめる（実行コマンドは `§run`）
5. `.steering/[task]/` が存在する場合は tasklist.md の該当項目を更新する（無ければ会話内の報告のみ）

## レビューモード

スコープ: バージョン管理上で変更された E2E テストファイル、またはユーザー指定。E2E テストの識別方法は `§scope`（references が無ければテストディレクトリ名・ランナー設定から判断する）。スコープが空なら「E2E レビューの対象ファイルがありません」と伝えて終了する。

4 軸で審査して報告する:

```
## E2E Review: [スコープ]

### 軸 1 — 対象選定
- [file:line] ロジック分岐の網羅を E2E でやっている → ユニットへ移す

### 軸 2 — 粒度
（問題なし）

### 軸 3 — 安定性
- [file:line] 固定時間の sleep → 条件待機へ
- [file:line] 前のテストが作ったデータに依存 → テスト内で前提を整える

### 軸 4 — 実ユーザー視点
- [file:line] API レスポンスのみアサート → 画面表示の確認を追加

### サマリー
- 確認したファイル: N件
- 重要な問題: X件
```

**提案のみ。自動修正しない。**
