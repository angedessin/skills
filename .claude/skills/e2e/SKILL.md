# e2e

壊れたら困る流れだけを、壊れにくい形で確かめる。

- 書くときは、主要な流れに絞って、実行できるなら実行して確かめる。実行できないときは、そう伝えて「通った」と書かない
- レビューを頼まれたら、指摘を返すだけにする。直すのは頼まれたときだけ

## When NOT to use

- コンポーネント・関数単位のテスト → このスキルを使わず、単体テストとして書く
- E2E の実行環境や CI の整備 → このスキルの対象外
- E2E の spec を含む差分全体のレビュー（「この差分を見て」）→ `frontend-code-review`。このスキルは spec だけを見てほしいとき

## 書くときに決めること

| 観点 | 基準 |
|---|---|
| 対象 | 壊れたら利用者が困る流れ（検索して結果が出る・送信できる・エラーを知らされる）だけ。細かな表示の違いは下のテストに任せる |
| 粒度 | 1 テスト 1 シナリオ。1 つのテストで複数の流れを続けて確かめない |
| 独立 | 各テストが自分で画面を開き、必要なデータと応答を用意する。前のテストの状態に頼らない。順番に実行する設定（serial）や、テストをまたぐ変数を使わない |
| 探し方 | 役割とアクセシブルな名前 → ラベル → 表示文字列。CSS セレクタ・`nth-child`・DOM 構造に頼らない |
| 待ち方 | 表示を待つアサーション（`expect(...).toBeVisible()` など）で待つ。`waitForTimeout` のような固定の待ちを使わない |
| 確かめるもの | 画面に見えるもの。`page.evaluate` で内部の状態を読んで確かめない |
| API の応答 | 誰が用意するかを決める。開発サーバーに API が無い（単体テスト用のモックしか無い）なら、`page.route` などで応答を用意するか、動いているバックエンドを前提にすることをファイルの先頭に書く |

書いたら、実行できる環境なら実行して通ることを確かめ、可能なら同じテストを数回流して不安定でないかを見る。

## レビューするとき

上の表の観点で spec を読み、指摘を返す。ファイルは書き換えない。

各指摘に書くこと: 場所（ファイルと行）・何が問題か・どう壊れうるか（不安定になる・意図しない変更で落ちる・落ちるべきときに通る）・直し方。spec に書いてあることを読み違えて指摘しないよう、指摘の前に該当箇所を確かめる。

## 報告する

- 書いたファイルと、各テストが確かめる流れ（1 行ずつ）
- 実行したか・結果。実行していなければ「実行していない」と書き、実行に要るもの（インストール・設定・バックエンド）を挙げる
