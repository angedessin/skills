# Phase 3.5 / 3.7 の手順（PR 作成 → CI → 往復 → 状態の記録）

`SKILL.md` の Phase 3.5・3.7 から参照される詳細手順。**Gate 3.5（マージ判断・停止）の契約は SKILL.md 本文が正本**で、このファイルには書き写さない。

## 状態の記録（現在地判定の入力）

`tasklist.md` の「デプロイ」節にある固定キー 3 行が、SKILL.md の判定表（`P37` / `P35`）の入力になる。チェックボックスではなく状態の記録なので、**サブスキルの報告を受けるたびに呼び出し元（このスキル）が書き換える**。

| キー | 値 | 書き換えるとき |
|---|---|---|
| `PR:` | PR の URL / `none` | `pr-create`（または `gh pr create`）が PR を作った直後に URL を書く |
| `CI:` | `green` / `failing` / `none` | CI の結果を確認するたびに |
| `Feedback:` | `yes` / `no` | レビューコメントまたは CI 失敗が返ってきたら `yes`。`pr-feedback` が対応を終えたら `no` に戻す |

`Feedback:` を `no` に戻さないと、判定表の `P37`（PR 往復）から抜けられない。
記録が実態とずれているとき（`PR: none` なのに PR が実在する等）は、判定の前に実態（`gh pr view`・CI の状態）で書き直す。
「デプロイ」節が無い旧形式の `tasklist.md` では 3 行を新設せず、会話で状態を持ち回る。

## Phase 3.5 — PR / 統合

1. リポジトリの運用を確認する: PR ベース運用（リモート + CI あり）か、main 直コミット運用か
   - **直コミット運用・CI なし** → このフェーズはコミット済みであることの確認のみでスキップしてよい。`tasklist.md` の「デプロイ」項目に**チェック（`[x]`）を付け**、「スキップ（直コミット運用）」と注記して Phase 4（最終）へ。注記だけでは未チェックが残り、判定表が `P35` から抜けられない
2. PR ベース運用の場合: `pr-create` スキルで PR を作成する（未配置なら `gh pr create` で代替）。作成したら `PR:` に URL を書く
3. CI の結果を確認し `CI:` に記録する（グリーンになるまで Phase 4 へ進まない。失敗したら `Feedback: yes` にして Phase 3.7 へ。重い修正は Phase 2 の作法に戻る）

## Phase 3.7 — PR 往復（pr-feedback・フィードバックが返っている場合のみ）

PR にレビューコメント・CI 失敗が返っている場合（`Feedback: yes`）、`pr-feedback` スキルで対応する（未配置なら手動で: コメント/CI を収集 → トリアージ → 承認 → 修正 → 返信）。
pr-feedback は内部に 2 つの承認 STOP（対応計画・外向き操作）を持つので、そのゲートを尊重する。
対応が終わったら `Feedback:` を `no` に戻し、`CI:` を更新して Gate 3.5 へ。Gate 3.5 でマージするときも、`Feedback:` が `yes` のまま残っていれば `no` に戻す（デプロイ節が全チェック済みなら判定表は `P37` に入らないが、記録は実態に合わせる）。フィードバックが無ければこの Phase をスキップして Gate 3.5 へ。

CI 失敗の原因が PR の差分外にあると判明したら `debug` に接続する（pr-feedback の担当外）。
