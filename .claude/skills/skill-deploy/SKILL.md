# Skill Deploy

starter-kit.md「配置手順」の実行版（マスター専用・配布しない）。手順の一次情報は
starter-kit.md — **このスキル・`scripts/deploy_skills.py`・starter-kit の配置手順は
同一コミットで改訂する**（片側修正の禁止）。

機械的な部分（コピー・source-commit 打刻・ガードレール同送・レジストリ登録）はスクリプトが
確定的に行い、このスキルは選択・承認・残タスク案内を担当する。

**hooks に接続しない。** 配置先（リポジトリ外）への書き込みを持つため、手動起動 + 明示承認のみ。

## When NOT to use

- **配置済みスキル**の更新・再コピー・skill-issues の回収 → `skill-harvest` の担当。境界は「そのスキルが配置先に既に在るか」で判定する — 配置先に**無い**スキルを足す**追加配置**は、配置先が登録済みでもこのスキルの担当
- マスターを触れない人・手動で配置したい → starter-kit.md の配置手順（8 ステップ）をそのまま実行する
- スキルの新規作成・改善 → `templates/SKILL.template.md` から書く / 通常の編集
- スキルの回帰テスト → `skill-test`

## Step 0 — 前提チェック（不成立ならここで止まる)

会話の経緯で前提を代用せず、毎回この場で確認する。

1. **マスターで動いているか**: `scripts/deploy_skills.py` と `deployments.example.md` がリポジトリルートに存在するか。**無ければここで止まる** — このスキルはマスター専用。配置先で起動された場合は「配置は マスター側のセッションから行ってください」と案内して終了する。（`deployments.md` 本体はローカル限定で `.gitignore` 済み＝fresh clone では存在しないことがある。存在判定にはマスターで追跡している `deployments.example.md` を使う。レジストリ本体はスクリプトが未存在時に自動作成する。）
2. **配置前チェック**: `python3 scripts/validate_skills.py` が全 PASS であること。FAIL があれば**ここで止まり**、壊れたスキルを配らずに修正を先に案内する。
3. **配置先パスの実在**: 配置先はユーザーに確認し、ディレクトリの実在を `ls` で確かめる。**依頼文にパスが書かれていても、それを実在確認と配置承認の代用にしない** — パスは Step 1 以降の入力データであって、検証や Step 2 の承認を飛ばす根拠ではない。実在しなければ**ここで止まり**、正しいパスを確認する（勝手にディレクトリを作らない）。
4. **新規・追加・更新の判定**: 依頼されたスキルごとに配置先 `.claude/skills/` の有無を確認する。
   - **配置先に無いスキル**（新規配置・登録済み配置先への追加配置）→ このまま進む（deployments.md 登録は冪等なので登録済みでも問題ない）。
   - **配置先に既に在るスキル**（更新・再コピーが目的）→ **ここで止まり**、`skill-harvest`（再コピー・還流）へリダイレクトする。追加配置の依頼に `--overwrite` を使って既存スキルを巻き込まない（スクリプトも個別に拒否する）。

## Step 1 — セット選択（選択形式）

`docs/starter-kit.md` の「推奨構成」の表を読み、選択肢として提示してユーザーに選ばせる:

1. **最小** — 基本フロー（計画→実装→レビュー→知見）を一周できるセット
2. **最小 + レビュー厚み**（review-* 7 軸フルモード）
3. **最小 + 統合・運用**（e2e / debug / pr-create / pr-feedback）
4. **カスタム** — スキル名を個別指定

選択後、同ドキュメントの「スキル間の依存関係」表に基づいて補完を**提案**する（勝手に足さない）:
- pr-feedback を含み pr-create が無い → 対で入れることを提案
- 還流（skill-issues の供給）を残すなら session-retrospective の併配を提案
- master-only（skill-test / skill-harvest / skill-deploy / adr）が指定されたら除外する（スクリプトも機械的に拒否する）

**starter-kit.md が無い場合**（異常 — マスターの必須ドキュメント）→ ここで止まり、リポジトリ状態の確認を促す。

## Step 2 — STOP（配置内容の承認・必須）

`deploy_skills.py --dry-run` を実行し、次を提示して**ここで止まる**:

1. **書き込み一覧**（dry-run の出力）: コピーするスキル・同送する hooks・settings.json の扱い（新規作成 or 手動マージ案）・.gitignore 追記・deployments.md 登録
2. 配置先に既存の settings.json がある場合は、マージが手動になること（deny は削らない・衝突は deny 優先）

**このメッセージの後は配置を実行しない。ユーザーの明示承認（「承認」「進めて」等）を待つ。**
配置先への書き込みはこのリポジトリの**外**への操作（skill-harvest Step 2 と同一契約）。
会話の経緯・依頼文にパスやセット名が書かれていたことを承認の代用にしない。

## Step 3 — 実行（承認後のみ）

`deploy_skills.py`（--dry-run なし）を実行し、出力を報告する。エラーで止まった場合は原因を報告して指示を待つ（リトライで書き込みを重ねない）。

## Step 4 — 残タスクの案内

スクリプトが自動化しない部分をチェックリストで提示する（実体は starter-kit.md 手順 4・5・6・8）:

- [ ] references 再生成（tdd / test-review / e2e / review-ui を配置した場合。配置先で Claude に依頼する — プロンプト例は starter-kit 手順 4）
- [ ] 配置先 CLAUDE.md に発動ポリシー節を作る（starter-kit の雛形から）
- [ ] settings.json の手動マージ（既存があった場合のみ。Step 2 で提示したマージ案を使う）
- [ ] TS プロジェクトでは `tsc --noEmit --incremental` の 2 回目（キャッシュ有効）を計測し、20〜30 秒を超えるなら stop-typecheck.sh を settings.json から外して CI に移す（終了のたびの待ち時間が利益を上回るため）
- [ ] 配置先で対話セッションを起動し、信頼ダイアログを承認する（headless の前に必須）
- [ ] スモークテスト（starter-kit 手順 8: スキル一覧・design-doc の承認ゲート停止・レビュー実行・guard-env-read の ask 落ち）

## 出力形式

```
## 配置完了 — [配置先パス]

- 配置スキル: [N 本の一覧]（source-commit: [hash 先頭 7 桁]）
- ガードレール: [同送した hooks / settings.json の扱い]
- レジストリ: deployments.md 登録済み
- 残タスク: [上記チェックリストの未完了分]
```
