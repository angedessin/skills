# frontend-code-review

見つける役と確かめる役を分け、確かめられた指摘だけを返す。差分が大きいときは費用の目安を示してレビューの前に止まり、指摘を返したら止まる。直すのは頼まれたときだけ。

## When NOT to use

- PR に付いたレビューコメント・CI の失敗への対応 → このスキルを使わない
- 原因の分からないバグの調査 → このスキルを使わない
- E2E の spec だけを見てほしい依頼（「この E2E をレビューして」）→ `e2e`。E2E の spec を含む差分全体のレビューはこのスキル

## Step 1 — 対象を決める

- 指定が無ければ、未コミットの変更すべて（未追跡のファイルも含む）。`git status --short` と `git diff HEAD --stat` で確かめる。作業ブランチがベースより進んでいるなら、コミット済みも対象にするかを聞いて止まる
- パスを頼まれたら、`git diff` にパスを付けて絞る
- 「このブランチ」「PR の前に」と頼まれたら、ベースブランチとの差分にする。ベースは、頼まれた指定 → CLAUDE.md の規則 → リモートの既定の順に決め、決まらなければ聞く。`git diff <ベース>...HEAD --stat` で確かめる（未コミットの変更があれば、それも対象に入れるかを伝える）
- 変更が無い、または自明な変更（typo・コメントだけ・生成物だけ）なら、レビューせずにそう伝えて終わる
- 足したテストの免除を数える: このスキルのフォルダの `scripts/list-exemptions.sh` を、対象と同じ範囲の指定で `bash` で呼ぶ（ブランチなら `--base <ベース>`、未コミットの変更も入れるなら `--worktree` も。パスで絞っていても `-- <パス>` は付けない）。出力（`exemptions:` の行と、その下の 1 件ごとの行）は Step 4 でそのまま載せるので控える。免除の理由が妥当かは判断しない。git が動かずに失敗したら、下の `count-diff.sh` と同じく `GIT=<その git のパス>` を付けて呼び直す。スクリプトが無い・呼び直しても終了コードが 0 でないときは、止まらずに、Step 4 の「レビューできなかったもの」に書く
- 差分の大きさを数える: このスキルのフォルダの `scripts/count-diff.sh` を、対象と同じ指定で `bash` で呼ぶ（ブランチなら `--base <ベース>`、未コミットの変更も入れるなら `--worktree` も、パスで絞ったなら末尾に `-- <パス>`）。`files` がファイル数、`lines` が変更行（追加＋削除）で、どちらも未追跡のファイルを含む。`untracked` は対象に入る未追跡のファイル。git が動かずに失敗したら（`xcode-select` のエラーなど）、動く git を探し、`GIT=<その git のパス>` を付けて呼び直す。スクリプトが無い・呼び直しても終了コードが 0 でないときは、そう伝えて止まる。変更行が 1,000 行を超えるか、ファイルが 20 を超えるときは、次を示して**ここで止まる**。聞かずに進むのは、依頼の文に `--cost-ok` があるときだけ。「大きいけど全部見て」「費用は了承」などの言い回しでは止まる（数字を見ないまま数ドルかかるのを防ぐため）。基準以下なら止まらず、agent を起動する前に「差分 <lines> 行・<files> ファイル、費用の目安 <幅>（<測った年月> の実測）」を 1 行出す。目安は、このスキルのフォルダの `references/cost.md` を読んで、変更行に当たる行と測った年月を出す（モデルや料金で変わるので、本文に数字を書かない）。`references/cost.md` が無い・読めないときは、行数とファイル数だけを示して「費用の目安なし」と書く（基準を超えたら止まるのは変わらない）
  - 数えた値と、`dirstat` のディレクトリごとの内訳。生成物・評価の結果・ロックファイルなどが多ければ、除くパスの案
  - 足したテストの免除の件数（`list-exemptions.sh` の `exemptions:` の行）
  - 費用の目安（`references/cost.md` の、変更行に当たる行と測った年月。パスを絞る案があれば、絞った後の目安も）
  - 選ぶもの: このまま進める／パスを絞る／やめる。次からは依頼に `--cost-ok` を付ければここで止まらないことを 1 行添える（止まった後の「このまま進めて」は、数字を見た答えなので進む）
- 差分を作業ツリーの外の一意なファイルに書き出す: `P="$(mktemp "${TMPDIR:-/tmp}/review.XXXXXX")"` の後に `git diff HEAD > "$P"`（ブランチなら `git diff <ベース>...HEAD > "$P"`、未コミットの変更も入れるなら `git diff "$(git merge-base <ベース> HEAD)" > "$P"`。パスで絞ったなら末尾に `-- <パス>`）。agent は git を使えないので、このファイルと、`untracked` に出た未追跡ファイルのパスを渡す
- 規約の資料を集める: 変更ファイルに関係する CLAUDE.md（ルートと変更ファイルの上の階層）・`docs/knowledge/`・`.steering/` の design.md。無ければ「規約の資料なし」として進む

## Step 2 — 一次レビュー（並列）

agent を一度に起動し、**全員の結果がそろうまで次に進まない・報告しない**。

| agent | 起動する条件 | 渡す範囲 |
|---|---|---|
| `review-bug` | 常に | 差分だけ（patch と変更行） |
| `review-bug` | 常に | 差分と、変更コードの呼び出し元・呼び出し先・同じファイルの周辺 |
| `review-rules` | 常に | 差分と、Step 1 で集めた規約の資料 |
| `review-ui-a11y` | `*.tsx`・`*.jsx`・`*.css`・`*.scss` の変更があるとき | 変更した UI のファイル |
| `review-test` | テストファイルか実装ファイルの変更があるとき（テストファイルが変わっていなくても起動する） | 変更したテストとテスト対象のファイル。実装ファイルだけが変わったなら、変更した実装ファイルと、その近くにある既存のテスト |

- テストファイル: `*.test.*`・`*.spec.*`・`__tests__/` と `tests/`・`e2e/` の下
- 実装ファイル: テストファイル以外の `*.ts`・`*.tsx`・`*.js`・`*.jsx`（`*.mts`・`*.cts`・`*.mjs`・`*.cjs`・`*.vue`・`*.svelte` も）。`*.d.ts`・`*.d.mts`・`*.d.cts`・`*.config.*`・`*.stories.*` と、`.` で始まる名前（`.eslintrc.cjs` などの設定）は除く

依頼文には、patch のパス・未追跡ファイルのパス・渡す範囲・規約の資料のパスを書く。パフォーマンスとセキュリティは、バグ担当が該当する変更を見つけたときに扱う（担当を分けない）。

agent が使えないときは、汎用の subagent に agent の本文と同じ指示を渡す。subagent も使えないときは自分で行う。代替したことと、結果が返らなかった担当を報告に書く。

## Step 3 — 指摘ごとの検証

テストファイルの変更があれば、検証役に渡す前に、新しく書いたテスト（変える前の版に同じ名前のテストが無いもの）を変える前のコードで流す。このスキルのフォルダの `scripts/run-tests-on-base.sh` を、Step 1 と同じ範囲の指定で `bash` で呼ぶ（ブランチなら `--base <ベース>`、未コミットの変更も入れるなら `--worktree` も、パスで絞ったなら末尾に `-- <パス>`）。Bash の timeout は 180 秒にする（スクリプトは 90 秒で vitest を打ち切る）。git が動かなければ Step 1 と同じ `GIT=<パス>` を付ける。

- `passed-on-base` に出たテストは、新しい振る舞いを確かめていない候補。種類「形だけのテスト」を付け、根拠「変える前のコードで流して通った」を添えて検証役に渡す。変える前でも通るのが正しいテスト（新しい分岐の出ない側・変えていない振る舞いの回帰テスト・既存のテストを動かしただけ）もここに出るので、確定しない。`review-test` の同じテストへの指摘とはまとめる
- `broken-on-base` に出たファイルは、変える前のコードで読み込めずに判定できなかった（新しい部品への依存か、写しに無い生成物・依存）。「レビューできなかったもの」に書く
- 呼ばない: 依頼・コミットのメッセージ・design.md から、振る舞いを変えない変更（リファクタリング）と分かるとき。変える前でも通るのが正しい
- 終了コードが 2（vitest が無い・時間切れなど）なら、理由を「レビューできなかったもの」に書いて続ける

一次レビューの指摘を集め、同じ問題はまとめる。まとめた指摘の一覧と patch のパス・未追跡ファイルのパスを `review-verify` に渡し、1 件ずつ本当に問題かを確かめさせる（結果が返るまで報告しない）。`review-test` の指摘は、種類（テストが足りない・形だけのテスト・過剰）を付けたまま渡す。依頼文には、写しを作るスクリプト（このスキルのフォルダの `scripts/make-copy.sh` の絶対パス）と、Step 1 で git を差し替えたなら `GIT=<パス>` を書く。

- 検証役が「確かめられた」とした指摘だけを残す。「確かめられない」「問題ではない」は捨て、件数と理由を 1 行ずつ残す
- 検証役の結果が得られないときは、指摘を捨てず「未検証」として報告する
- 作業ツリーの見張り（`subagent-tree-guard`）から「検証役の間に作業ツリーが変わった」と知らされたら、**自分では戻さない**（`git restore`・`git checkout`・`git reset` を打たない。ユーザーが同時に編集した分を消しうる）。違いの一覧と、今も違うか戻ったかを Step 4 の警告に回し、レビューは続ける。「確かめていない」と知らされたら、Step 4 の「レビューできなかったもの」に書く。見張りが無い環境では知らせが来ないだけで、手順は変わらない
- 自分で再現を試すときは、このスキルのフォルダの `scripts/make-copy.sh` を `bash` で呼んで（一時リポジトリなら `--empty`。git を差し替えたなら `GIT=<パス>`）写しを作り、その後のコマンドは毎回 `cd <出たパス> && ...` で始める。スクリプトが 0 以外で終わったら再現をやめ、読みで判定する。リポジトリの中に一時ファイル・一時テストを作らない

## Step 4 — 報告して止まる

返答の先頭に、対象の範囲（ベース・未コミットの有無・絞ったパス）を書く。Step 3 で見張りから作業ツリーの違いを知らされていたら、範囲の行の直後に警告として、違いの一覧と今も違うかどうかを書き、「自分では戻していない。確かめて戻すかを決めてほしい」と添える。

残った指摘を**すべて**重要度順に書く（High・Medium・Low。件数だけにまとめない）。各指摘に書くこと:

- 場所（ファイルと行）・何が問題か・どう壊れうるか（具体的な入力と結果）・直し方の方向
- 確かめ方（再現した / コードを読んで確かめた）。形だけのテストの指摘は、実装をどう壊し、テストがどうなったか（通った / 流せず読みで示した）を必ず書く。変える前のコードで流して通ったものは、そう書く

続けて、「この差分で足したテストの免除」の節を**必ず**書く（指摘が 0 件でも書く）。Step 1 の `list-exemptions.sh` の出力をそのまま載せ、妥当かの判断は添えない（判断は人がする）。

- 1 件以上: 件数と、1 件ごとの行（節・パス・理由・免除ファイル。「閉じたタスク」の印も）をすべて
- `exemptions: 0`: 「なし」
- `exemptions: unknown (...)`: 「確かめられない」と、かっこの中の理由
- スクリプトが無かった・終了コードが 0 でなかった: 「確かめられない」と書き、「レビューできなかったもの」にも書く

その後に、捨てた指摘の件数、「規約が無い」と報告された観点、レビューできなかったもの（実行できなかったコマンド・読めなかったファイルや範囲・結果が返らなかった担当）を書く。

`.steering/` に変更に対応する作業のフォルダがあれば、同じ内容を `review-result.md` に書く（既にあれば上書きせず、末尾に日付の節を足す）。無ければ返答だけでよい。このファイルは次のレビューの対象に入れない。

報告を書き終えた後に見張りの知らせが届いたら（応答を終えようとしたときに差し戻される形で来る）、警告だけを返答し、`review-result.md` があれば末尾に同じ警告を足す。ここでも自分では戻さない。

**ここで止まる。** コードは直さない。直すかどうか・どれから直すかはユーザーが決める。

- `review-verify` — 指摘ごとの検証
