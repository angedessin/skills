# Impl Tournament

APPROVED な `design.md` から、**本質的に異なる** 2〜3 の実装アプローチを worktree 並列で作り、レビュースイートで採点して人間が勝者を選ぶ。アプローチ選択が結果を大きく左右するリスクの高いタスク専用。**常用しない。**

このスキルは「エンジン＋カートリッジ」構成: 本文はツール非依存の手順と判断、具体的な worktree コマンド・モデル振り分けの指定は `references/commands.md`（カートリッジ）に置く。**同ファイルが無い場合**は標準的な git worktree コマンドで実行し、モデル振り分けは「変種の実装は安価なモデル・採点/統合は上位モデル」の方針を口頭で適用して続行する（その旨を伝える）。

## When NOT to use

- 通常の 1 本の実装 → `impl-from-design` の担当。アプローチがほぼ自明なタスクにトーナメントは過剰。
- 設計そのものがまだ固まっていない → `design-doc` の担当（アプローチ以前の問題）。
- 設計の穴出し → `design-premortem` の担当。
- 実装済みコードのレビュー → `frontend-code-review` の担当。

---

## Step 0 — 前提チェック（不成立ならここで止まる）

会話の経緯（「さっき承認された」等）で代用せず、**成果物で**確認する。

1. `.steering/[task]/design.md` の Status が `APPROVED` であること。
   - **DRAFT / 不在**で、かつ `design-doc` スキルがある → **ここで止まり** design-doc へリダイレクトする。
   - **`.steering/` が無い**（配置先で単体利用）→ **ここで止まり**、承認済みの設計文書の所在をユーザーに確認する。それも無ければ「設計を先に固めてから」と案内して止まる。
2. git リポジトリであり、作業ツリーがクリーン（未コミット変更なし）であること。worktree を切るため。**不成立ならここで止まり**、コミット/退避を案内する。

---

## Step 1 — STOP（アプローチ提案とコスト承認・必須）

`design.md` の Alternatives considered を起点に、**本質的に異なる** 2〜3 のアプローチ（例: 状態機械 / リデューサー集約 / サーバー状態寄せ。**上限 3**）を選定し、次を提示して **ここで止まる**。

必ず両方を併記する:
1. **コスト見積** — 実装 N 回 + レビュー N 回分の課金。あわせて**モデル振り分け案**（変種の実装は安価なモデル・採点/統合は上位モデル等。具体的なモデル名と指定方法は references/commands.md）。
2. **無料代替** — アプローチ比較表だけを書いて 1 本に絞り、`impl-from-design` へ進む道。並列実装せずに済む。

**このメッセージの後は並列実装を開始しない。ユーザーの明示承認を待つ。** コストを伴う外向き寄りの操作のため、承認なしに subagent 並列を回さない。

---

## Step 2 — 並列実装

承認されたアプローチごとに:
1. worktree を切る（具体コマンドは references/commands.md）。
2. **フレッシュな subagent** に「`design.md` + 当該アプローチの brief」**だけ**を渡して実装させる。他アプローチを見せない（独立性の確保 — 互いに引きずられない）。
3. テストは `design.md` の Test strategy に従う。

subagent 並列を使えない環境では、アプローチを 1 つずつ順に実装してもよい（独立性のため各実装の前に前アプローチの文脈を持ち込まないよう留意する）。

---

## Step 3 — 採点

各 worktree の成果物を**同一基準**で採点する。

- `frontend-code-review` / `test-review` が**あれば**各変種に適用し、指摘数・重大度を採点材料にする。
- **無ければ**フォールバック基準でセルフレビューする: 正当性・単純さ（複雑度）・テスト品質・design.md との整合。各変種を同じ観点で相対評価する。

---

## Step 4 — STOP（勝者選定・必須）

比較表（基準 × 変種、各セルに根拠）と推奨を提示して **ここで止まる**。勝者の選定は人間の価値判断（保守性 vs 速度などのトレードオフ）。

提示文には「**承認された勝者をメインに統合し、敗者の worktree を削除する**（削除は不可逆）」ことを明記し、この統合＋削除の実行承認をこの STOP に含める。

**このメッセージの後はマージも worktree 削除もしない。ユーザーの応答を待つ。**

---

## Step 5 — 統合と後始末

承認後:
1. 勝者をメインの作業ツリーに統合する。
2. **敗者から得られた知見**（採用しなかった理由・敗者にだけあった良い部分）を `.steering/[task]/decisions.md` に記録する。worktree を消すと変種のコードは失われるため、**削除の前に**記録する。`.steering/` が無い場合は会話に要約を残す。
3. 敗者の worktree を削除する（Step 4 で承認済み）。

## 出力形式

```
## Tournament 比較（Step 4 で提示）

| 基準 | 変種A | 変種B | 変種C |
|---|---|---|---|
| 正当性 | ... | ... | ... |
| 単純さ | ... | ... | ... |
| テスト品質 | ... | ... | ... |
| 設計整合 | ... | ... | ... |

推奨: 変種X（根拠）。統合すると敗者 worktree は削除されます（不可逆）。承認をお願いします。
```

## Related skills

- `impl-from-design` — 通常の 1 本実装。Step 1 の無料代替はここへ合流する
- `design-doc` — 設計フェーズ。Step 0 の APPROVED 前提が満たされない場合の戻り先
- `frontend-code-review` / `test-review` — Step 3 の採点に使う（あれば）
- `design-premortem` — 設計段階でアプローチの穴を洗う（トーナメント前の代替検討）
