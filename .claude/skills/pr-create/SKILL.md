# PR Create

変更を PR として提出するフェーズ。ワークフローでは「レビュー対応済み → 統合」の橋渡し（Phase 3.5）に相当する。

このスキルは「エンジン＋カートリッジ」構成: 本文はツール非依存の手順と判断、具体的な git/gh コマンドは `references/commands.md`（カートリッジ）に §名で置く。**`references/commands.md` が無い場合**は、下記の手順はツール非依存なので**そのまま適用し、標準的な gh / git コマンドで実行して続行する**（その旨を伝える）。

## このスキルの境界（When NOT to use）

- **マージ**は行わない。マージは人間の判断（外向き・不可逆寄りの操作）で、このスキルの外。PR を作成し URL を報告するところまでが仕事。
- **PR 提出後**に返ってくるレビューコメント・CI 失敗への対応（トリアージ・修正・返信の往復）→ `pr-feedback` の担当。このスキルは PR の新規作成・初回プッシュまでで、往復には入らない。
- コードの実装・レビュー指摘の修正 → 各実装 / レビュースキルの担当。このスキルはコードを直さない。
- CI ワークフローの設定・整備 → 対象外。このスキルは既存 CI の結果を確認するだけ。
- 開発途中のこまめなコミット → 通常の開発フローの仕事。このスキルは「PR に載せる変更が確定しているか」だけを前提として確認する。

---

## Step 0 — 前提チェック（不成立ならここで停止する）

会話の経緯（「さっき PR 運用と言った」等）で前提を代用せず、毎回この場で確認する。

1. **リポジトリの運用を判定する。** PR ベース運用（リモート + PR ホストあり）か、デフォルトブランチ直コミット運用か。
   - **直コミット運用（リモートや CI が無い）** → PR は不要。変更がコミット済みであることだけ確認し、「このリポジトリは直コミット運用のため PR は作成しません」と報告して**停止する**。
2. **PR ホスト / リモートの有無を確認する。**
   - **リモートも PR ホストも無い** → PR は作成できない。ローカルでのコミット手順（と、後でリモートを追加した場合のプッシュ手順）を案内して**停止する**。ここで勝手にリモートを追加しない。

---

## Step 1 — 変更の確定（コミット状態の確認）

1. 作業ツリーに未コミットの変更があるか確認する。
2. **未コミットの変更がある場合** → 差分の要点とコミット計画をユーザーに提示する。停止するかは差分の曖昧さで分ける:
   - **全変更が明らかに対象タスクに属する場合** → 提示して承認を待たずにコミットし、先へ進む（コミットはプッシュ前なら git で巻き戻せる。外向きの防衛線は Step 4 の STOP が持つ。異議があればユーザーは提示を見て止められる）。
   - **無関係な変更が混在している・どれを PR に載せるか判断が割れうる場合** → **ここで止まって**「何を PR に載せるか」を確認してからコミットする。曖昧なまま一括コミットしない。迷ったら止まる側に倒す。
   - コミットメッセージは実行環境（ハーネス）の規約に従う（種別プレフィックスの慣行・末尾トレーラを含む）。規約が不明ならリポジトリの直近のコミット履歴のスタイルに合わせる。
3. 未コミットの変更が無ければ次へ。

---

## Step 2 — ブランチ衛生

1. 現在のブランチを確認する。
2. **デフォルトブランチ（main / master 等）上にいる場合** → PR 用のトピックブランチを作成してから進む。デフォルトブランチに直接コミット/プッシュしての PR は作らない（巻き戻しやすさと運用の安全のため）。
   - ブランチ名は変更内容が分かる短い名前にする（リポジトリの命名慣行があればそれに合わせる）。
3. 既にトピックブランチ上ならそのまま使う。

---

## Step 3 — PR 内容の作成

ベースブランチとの差分・コミット履歴を根拠に、PR のタイトルと本文を組み立てる。**憶測で機能や意図を書かない** — 差分に現れた事実に基づく。

- **タイトル**: 変更の要点を 1 行で。リポジトリのコミット規約（種別プレフィックス等）に合わせる。
- **本文**（最低限）:
  - Summary — 何を・なぜ変えたか
  - 主な変更点 — 変更したファイル/コンポーネントの箇条書き
  - テスト状況 — 追加/更新したテスト、確認した内容
  - レビュー観点 — 見てほしい点があれば
  - 末尾に実行環境（ハーネス）標準の生成トレーラを付す（規約がある場合）。
- `.steering/[task]/` があり `design.md` / `review-result.md` があれば、Goal と主要な設計判断・後回しにしたレビュー指摘を本文に反映する（無ければ差分と履歴だけで書く）。

---

## Step 4 — プッシュと PR 作成（外向き操作 — ここで必ず止まる）

プッシュと PR 作成は**外向きの操作**（内容が外部サービスに公開され、キャッシュ/インデックスされうる）。実行前に必ず承認を取る。

1. 作成する PR の **タイトル・本文・ベースブランチ・ヘッドブランチ**をユーザーに提示する。
2. **ここで止まり、ユーザーの明示承認を待つ。** 「進めて」等の明示的な応答を得るまでプッシュも PR 作成もしない。会話の経緯を承認の代用にしない。
3. 承認後 → トピックブランチをプッシュし、PR を作成する。
4. 作成された **PR の URL を報告する**。
   - **PR ホストのツール（gh 等）が使えない場合** → プッシュまで行い、PR を Web で作成するための手順（比較 URL など）を案内する。ここで停止してよい。

---

## Step 5 — CI 追跡（CI がある場合のみ）

1. PR 作成後、CI があれば結果を確認する。
2. CI が失敗した場合 → 失敗内容を報告する。**修正はこのスキルではしない** — 提出後の CI 失敗・レビューコメントへの対応は `pr-feedback`（あれば）に接続する。無ければ実装/レビューの担当スキル（または呼び出し元）に戻す。重い修正は設計フェーズに戻る判断をユーザーに仰ぐ。
3. CI が無いリポジトリではこの Step をスキップする。

---

## マージはしない（境界の再掲）

CI がグリーンでも、このスキルは**マージしない**。マージは人間の判断（feature-pipeline では Gate 3.5）であり、外向き・巻き戻しにくい操作。PR の URL 報告をもってこのスキルの仕事は完了。マージ可否はユーザーに委ねる。

## `.steering/` 連携（あれば使う、無ければ無いなりに動く）

`.steering/[task]/tasklist.md` に Deploy セクションがあれば、PR 作成の結果（PR URL・CI 状態・マージは人間判断待ち）を追記する。`.steering/` が無いプロジェクトでは何もしない（このスキルは `.steering/` に依存しない）。
