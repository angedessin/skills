# pr-create

push と PR の作成は外に出る操作なので、その前で必ず止まる。マージは人が決める。

## When NOT to use

- PR に返ってきたレビューコメント・CI の失敗への対応 → このスキルを使わない
- マージ → このスキルの対象外。PR の URL を報告し、Step 5 を済ませたら終わる

## Step 1 — 前提を確かめる

- `.steering/` に対象のタスクがあり、design.md の Status が `SPIKE`（探索）なら、PR を作らずに止まる。探索の成果は、破棄するか設計を承認してから PR にする
- `.steering/` にタスクがあるのに、どれの作業か特定できない、または design.md の Status が無い・不正なら、候補を示して聞いて止まる
- `git remote -v` でリモートを確かめる。リモートが無ければ PR は作れないので、コミットまでの状態を報告して止まる。勝手にリモートを足さない
- ベースブランチを決める: 頼まれた指定 → CLAUDE.md などの規則（git-flow なら develop やマージ用のブランチ）→ リモートの既定の順。決まらなければ聞く
- ベースが統合ブランチ（`git symbolic-ref --short refs/remotes/origin/HEAD` から `origin/` を外した名前と、`main`・`master`・`develop`）かを控える。大きなタスクの統合用 feature ブランチへの子ブランチの PR は、統合ブランチへの PR ではない

## Step 2 — コミットとブランチを整える

- `git status --short` で未コミットの変更を見る。どれも対象の作業に属するなら、そのファイルだけを `git add` してコミットする（`git add -A` で一括にしない。作業と関係ないファイルが混ざる）。関係ないものが混ざっていて、どれを載せるか決められないときは、ここで聞いて止まる
- デフォルトブランチ（main・develop など、リポジトリの運用で直接コミットしないブランチ）にいるなら、内容が分かる名前のブランチを切ってから進む
- コミットメッセージは、リポジトリの直近の履歴と実行環境の決まり（末尾の行など）に合わせる

## Step 3 — タイトルと本文を書く

ベースブランチとの差分とコミットの履歴から書く。差分に無いことを書かない。

- タイトル: 変更の要点を 1 行で（リポジトリの慣行の種別を付ける）
- 本文: 何を・なぜ変えたか／主な変更／確かめたこと（流したテストと結果。流していなければそう書く）／残っていること・見てほしい点
- `.steering/[task]/` に design.md や review-result.md があれば、目的と、後回しにした指摘を本文に入れる
- この PR で足したテストの免除を載せる: このスキルのフォルダの `scripts/list-exemptions.sh` を `bash` で `--base <ベース>` を付けて呼ぶ（Step 2 のコミットの後に呼ぶ。git が動かずに失敗したら、動く git を探し、`GIT=<その git のパス>` を付けて呼び直す）。免除の理由が妥当かは判断しない
  - 1 件以上: 本文に「テストの免除」の節を書き、出力の 1 件ごとの行（節・パス・理由・免除ファイル。「閉じたタスク」の印も）をすべて載せる
  - `exemptions: 0`: 節を書かない
  - `exemptions: unknown (...)`: 「テストの免除」の節に「確かめられない」と、かっこの中の理由を書く
  - スクリプトが無い・呼び直しても終了コードが 0 でない: 止まらずに、Step 4 でそう伝える

## Step 4 — 示して止まる

ベースブランチ・ヘッドブランチ・タイトル・本文を示す。対象のタスクの design.md が `DRAFT` なら、未承認の設計の実装であることを先頭に書く。

本文とは別に、足したテストの免除の件数を 1 行で添える（例: 「テストの免除: 2 件（本文に記載）」「テストの免除: なし」「テストの免除: 確かめられない（理由）」）。本文を読み飛ばしても目に入るようにするため。

ベースが統合ブランチで、対象のタスクがあるときは、PR の後にタスクをどうするかを 1 行で添える。tasklist の PR の項目にチェックを付けたと仮定して、Step 5 の「閉じてよい状態」に当てる:

- 閉じてよい状態になる: 「PR の後、タスク <名前> を閉じる確認を続けて出します」（この文言は変えない）
- APPROVED だが、閉じる項目のほかに未チェックが残る: 「タスク <名前> は未チェックの項目が残るため、PR の後も閉じません（残り: <項目>）」
- DRAFT で、差分が `.steering/` の下だけ: 「設計だけのため、タスク <名前> は閉じずに残します」
- DRAFT で、ほかの差分もある: 上の「未承認の設計の実装」の文だけ。閉じない

**ここで止まる。** 承認をもらうまで `git push` も PR の作成もしない。

承認をもらったら、push して PR を作り、URL を報告する。`git push` と `gh pr create` は、パイプや `cd` を付けずに 1 つずつ単独で呼び、本文は `--body-file` で渡す（sandbox の中に残ると TLS や SSH の検証で失敗する）。PR を作る道具（gh など）が使えなければ、push までして、Web で作る手順を伝える。CI があれば結果を見て報告する。失敗していても、このスキルでは直さない。

## Step 5 — PR を作った後にタスクを閉じる

タスクのフォルダを閉じずにマージすると、統合ブランチに `.steering/<タスク>/` が残る。ベースが統合ブランチで、対象のタスクがあるときだけ行う。それ以外は何もしない。

tasklist の行の見分け方と、閉じてよい状態:

- **PR の項目:** `pr-create` を含む行
- **閉じる項目:** バッククォートの中を除いた残りに、語としての `steering`（前後が英数字・`.`・`/`・`-` でない）と、`閉じ`・`アーカイブ`・`archive` のどれかを含む行
- **閉じてよい状態:** design.md の `Status:` が `APPROVED`、PR の項目にチェックと PR の番号（`#数字`）がある、未チェックの項目が 0 件かどれも閉じる項目

URL を報告した後に:

1. PR の項目にチェックを付けたと仮定して、閉じてよい状態かを確かめる
2. 閉じてよい状態なら、tasklist の PR の項目にチェックを付けて `PR #<番号>` を添え、**steering のスキルを呼んで**「閉じる」の手順 1〜3 で確認を出して止まる（手順をここに写して出さない）。索引の行には PR の番号を入れ、確認の文に「承認したら、tasklist の更新と閉じるのを 1 つのコミットにして push する」と書く
3. 閉じてよい状態でなければ、tasklist に触らない（触ると、PR に載せるための追加の push が要る）。閉じないことと残りの項目を伝える。PR の番号は、steering が次に tasklist を更新するときに付ける
4. steering のスキルが無ければ、タスクのフォルダが残っていることと、マージの前に閉じる（索引に 1 行残してフォルダを消し、PR に載せる）必要があることを伝えて終わる
