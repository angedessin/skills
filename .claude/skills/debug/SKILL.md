# Debug

障害調査の専用フロー。design-doc とは順序が逆 — **設計より先に原因特定**。
「証拠に基づいて仮説を絞る」を規律の核とし、症状のパターンマッチで直しに行かない。

**原因特定・修正方針の提示までは調査行為として承認不要。修正の適用は承認制。**

## When NOT to use

- 新機能・タスクの設計 → `design-doc`
- 原因が自明なテスト失敗・typo → そのまま修正する（このスキルは大げさ）
- コード構造・依存の把握だけしたい → ビルトインの Explore / code-explorer

## 調査ログの記録先

`.steering/[task]/` のタスクディレクトリが存在する場合は `investigation.md` に調査ログ（仮説・検証結果・棄却理由）を残す。複数のアクティブタスクがある場合は調査対象と最も関連するタスクを選ぶ（判断できなければユーザーに確認する）。**存在しない場合は会話内で完結してよい** — この調査のために `.steering/` を新規作成しない（修正が design-doc に接続された時点で、調査結果はそちらの design.md に引き継がれる）。

## Step 1 — 再現確認

- 報告された症状の再現手順を確立する: 入力・環境・操作・期待した結果と実際の結果
- 再現できたら**最小再現**に絞り込む（無関係な要素を削っても症状が残る最小の形）
- **再現できない場合（縮退動作）**: ログ・エラーメッセージ・コードリーディングベースの調査に切り替え、以降のレポートに「再現未確認 — 結論の確度は下がる」と明記する。あわせて再現に必要な情報（環境・発生頻度・直前の操作）をユーザーに確認する

## Step 2 — 仮説立案

- 原因の仮説を**可能性順に複数**列挙する。最初の 1 つに飛びつかない
- 各仮説に「何を確認すれば裏付け / 棄却できるか」を付ける（確認手段のない仮説は仮説ではない）

## Step 3 — 切り分け（二分探索的に）

- **時間軸**: 直近の変更 diff・`git bisect` で「いつから壊れたか」を絞る
- **空間軸**: レイヤーで分割（データ取得 / 状態管理 / 描画、フロント / API）し、問題の在り処を半分ずつ潰す
- **最小再現**: 要素を削って症状が消えた瞬間、直前に削ったものが容疑
- 検証のたびに仮説リストを更新し、**棄却した仮説と棄却理由を残す**（同じ道を二度調べない）

## Step 4 — 根本原因の特定

- **症状ではなく原因を特定する**。「null で落ちる」は症状。「API が 0 件時に空配列でなく null を返すケースが型に表現されていない」が原因
- 証拠を明示する: 原因箇所（file:line）と、それが症状を引き起こす機序
- パターンマッチの罠に注意: 既知の失敗に似た信号でも原因は別のことがある。証拠が同じ原因を支持するか確認してから断定する

## Step 5 — 修正方針の提示と出口分岐

```
## Investigation Report

- 症状: [観測された事象]
- 再現: 確認済み（最小再現: ...）/ 未確認（コードリーディングベース）
- 根本原因: [file:line] — [機序]
- 棄却した仮説: [仮説] → [棄却理由]
- 修正方針: [案。複数あればトレードオフ付き]
```

出口は二方向:

- **小さい修正** — 次の 3 条件を**すべて**満たす: (1) 影響がファイル数件に閉じる (2) git で巻き戻し容易 (3) テストで再発防止できる → **承認を得て**その場で修正し、再発防止テストを追加する（テストパターンは `tdd` スキルを参照。無いプロジェクトでは通常の手段でテストを書く）
- **構造に触る修正** — 3 条件のいずれかを満たさない → `design-doc` に接続して通常フロー（設計 → 承認 → 実装）に合流する。調査結果（根本原因・棄却仮説）を design.md の Research セクションに引き継ぐ。design-doc スキルが無いプロジェクトでは、修正方針の提示で終了し実装判断をユーザーに委ねる
