# 方針転換の手順（分類と、契約コア変更 / APPROVED 追認の手順）

`SKILL.md` の「方針転換が起きた場合」節から参照される手順の詳細。
**Status や契約コアを書き換える前に必ず全文を読む。** 分類の要点と「迷ったらコア」は SKILL.md 本文にも書いてある。

契約コアの正本は次の全見出し（部分集合を別定義しない）: 目的・スコープ・制約・完了条件・アプローチ・主要コンポーネント・未解決の論点。

### 分類（迷ったらコア）

| 区分 | 例 | 結果 |
|------|-----|------|
| 契約コア変更 | 目的の書き換え、スコープ対象/対象外の追加削除、制約の追加、完了条件の追加/削除/意味変更、アプローチの技術選択変更、主要コンポーネント行の追加削除・責務変更、未解決の論点の実質追加 | `Status: **DRAFT**` に戻し Phase 3 再承認。APPROVED のままコアを書かない |
| APPROVED 追認 | 誤字・表現の整理、tasklist のチェック/順序の実態追従、付録のみの追記、主要コンポーネントの「場所」パス表記ゆれ（責務不変） | APPROVED 維持。design/tasklist 更新＋`decisions.md` に 1 エントリ |
| 迷ったら | どちらとも言える変更 | **契約コア変更扱い** |

### 契約コア変更の手順

1. 契約コアを実態に合わせて更新。肥大しうる調査・代替案は**付録側**へ
2. `tasklist.md` の未完了タスクを実態に合わせて追記・削除
3. `Status: **DRAFT**` に戻す（`Approved:` 行があれば削除）
4. 既存の `review-result.md` があれば**破棄**する（SPIKE 出口と同型。古い設計整合 High の汚染防止）
5. 作業ツリーは**残置前提**（SPIKE 並の残す/捨てるゲートは設けない。破棄が必要ならユーザーが明示する）
6. Phase 3 の人間レビューへ戻る（再承認まで実装入口は DRAFT 停止）

### APPROVED 追認の手順

1. 該当箇所（表現・tasklist・付録等）だけ更新する。契約コアの意味を変えない
2. `decisions.md` に 1 エントリ（何を追認したか）
3. Status は **APPROVED のまま**

**更新しないと `.steering/` と実際の作業が乖離し、セッションをまたいだ再開時に混乱する。**
