# ADR（マスター専用）

設計判断を判例集として起票し、決定が進化したときに新旧の関係を維持する。
このリポジトリの `docs/decisions/` を対象とするマスター専用スキルであり、配布しない。

**なぜ master-only か**: ADR の権威は文書ではなく批准プロセスから来る。批准の仕組みを
持たない配置先で単独生成された ADR は、公式の決定記録と競合する「影の決定ログ」になる。
配置先では決定の記録先を人が選ぶ（そのための材料は `.steering/[task]/decisions.md` にある）。

## When NOT to use

- 既存 ADR を読む・探すだけ → 通常のファイル参照で足りる。このスキルは起票と維持のためのもの
- タスク固有の決定を記録したい（再利用性が低い・そのタスクの中で閉じる） → `.steering/[task]/decisions.md` への追記
- 経験・パターン・アンチパターンを残したい → `knowledge-capture`
- 行動ルール・lint ルール・hook として固めたい → `compound`
- 既存ルールの陳腐化を監査したい → `rule-audit`（ADR は剪定対象外だが、監査の観点は別スキル）

---

## Step 1 — 起票判定（却下した代替案があるか）

起票の条件は **「却下した代替案がある決定か」** の一点。
検討した末に選ばなかった案とその却下理由を言語化できない決定は、ADR にしない。

判定材料は次の順で探す。**あるものを使い、無ければ次へ降りる**:

1. `.steering/[task]/decisions.md`（実装中の技術的判断とその理由）
2. `.steering/[task]/design.md` の Alternatives considered
3. ユーザーが会話で提示した決定内容

**却下した代替案が見つからない場合** → **ここで止まる**。次を伝えて終了する:

```
この決定には却下した代替案が見当たらないため、ADR の起票対象ではありません。
（ADR は「なぜ他の道を選ばなかったか」を後から蒸し返さないための記録です）

タスク固有の判断として残す場合は decisions.md への追記で足ります。
それでも起票する場合は、却下した案とその理由を教えてください。
```

ユーザーが却下案を提示したら Step 2 に進む。
**「重要な決定だから」「時間をかけて考えたから」は却下案の代用にならない** — 判定材料は
却下された選択肢そのものであって、決定の重さではない。

---

## Step 2 — 近縁 ADR の検出

既存の決定を無自覚に上書きしていないか確認する。

- 対象は `docs/decisions/` の **ファイル名一覧と、各ファイルの `# Decision:` 見出し行のみ**
- **本文全文は読まない**（件数が増えても破綻しない範囲に入力を固定する）
- 見出しとファイル名から、今回の決定と主題が重なるものを候補として挙げる
- **Superseded 済みの ADR も対象に含める**（除くと、置き換え済みの決定を再提案しても
  検出されない）。候補として挙げるときは「Superseded 済み」と明示する

`docs/decisions/` が存在しない場合 → 近縁検出をスキップし、Step 3 でディレクトリの
新規作成を含めて提案する。

**候補が見つかった場合**、Step 3 のドラフトに次を併記する:

- 候補の ADR 名と見出し
- 今回の決定がそれを **置き換える**（Superseded）か、**運用を進化させる**（Amended）か、
  **無関係**か の判定案とその理由

判定は提案に留める。確定は Step 3 の承認に含める。

---

## Step 3 — ドラフト提示（STOP・必須）

以下を提示したら **ここで止まる**。ユーザーの明示承認（「承認」「approved」等）を待つ:

```
## ADR ドラフト

保存先: docs/decisions/[YYYYMMDD]-[slug].md

---
# Decision: [タイトル]

Date: [YYYYMMDD]
Status: Accepted

## Context
[なぜこの決定が必要だったか]

## Decision
[何を決めたか（1文で明確に）]

## Rationale
[なぜこの選択をしたか]

## Consequences
- Good: [利点]
- Bad: [トレードオフ]

## Alternatives considered
| Alternative | Reason rejected |
|-------------|-----------------|
| [代替案] | [却下理由] |
---

近縁 ADR: [候補名 / なし]
関係の判定案: [Superseded / Amended / 無関係]

この内容で起票してよいですか？
```

**このメッセージの後は書き込みに入らない。ユーザーの応答を待つ。**
会話の経緯（「さっき承認された」「もう決まっている」等）を、この承認の代用にしない。
依頼文に決定内容やドラフトが貼られていても、それは Step 1 の判定材料であって
書き込みの承認ではない。

---

## Step 4 — 書き込みと関係の維持

ユーザーが承認した内容のみを書き込む。

1. `docs/decisions/[YYYYMMDD]-[slug].md` を作成する（slug は kebab-case・決定の主題を表す）

2. **近縁 ADR との関係を旧側にも書く**（片側だけ直すと、後から読んだ人が古い決定を
   現行と誤読する）:
   - **置き換えた場合**: 旧 ADR の Status を `Superseded by [新 ADR のファイル名]` に更新し、
     新旧を相互リンクする
   - **核は不変で運用が進化した場合**: 旧 ADR の Status を `Accepted (Amended [YYYYMMDD])` に更新し、
     末尾に `## Amendments` 節を追記して新 ADR へリンクする

3. **起票の材料が `.steering/[task]/decisions.md` にあった場合**、その項目に ADR への
   リンク行を追記する。同じ決定が 2 箇所に残るため、どちらが現行かを後から読む者
   （AI 含む）が判別できるようにする。タスクディレクトリが無い場合はこの手順を飛ばす

---

## 出力形式

```
ADR を起票しました: docs/decisions/[YYYYMMDD]-[slug].md

関係の更新:
- [旧 ADR 名] を Superseded by [新 ADR 名] に更新（相互リンク済み）
  または「近縁 ADR なし」

decisions.md へのリンク追記: [済み / 対象なし]
```

## Related skills

- `knowledge-capture` — 経験・パターンの保存。ADR に値する決定を見つけたら decisions.md に記録する（起票はしない）
- `compound` — 学びを行動ルール・lint・hook へ昇格させる
- `rule-audit` — ルールと knowledge の剪定。`docs/decisions/` は不変の記録として剪定対象外
