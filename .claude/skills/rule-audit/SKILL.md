# Rule Audit

ルールを増やす仕組み（compound）だけでは、CLAUDE.md は放置で肥大化・陳腐化する。
肥大化したルールファイルは実際の指示を無視させる。このスキルは既存ルールの健全性を
監査し、**保持 / 削除 / 統合 / 移動 / 明確化** を判定して剪定する。

**レポート提示までは承認不要。適用（ファイルへの書き込み）は承認制。**

## When NOT to use

- 学び・パターンを新ルールに昇格したい → `compound`
- ドキュメント（ADR・パターン集）として保存したい → `knowledge-capture`
- スキル本文の内容品質・挙動を検証したい → `empirical-prompt-tuning`（本スキルが見るのは frontmatter・構造・規約まで）

## compound との棲み分け

| | `compound` | `rule-audit`（このスキル） |
|---|---|---|
| 方向 | **追加・昇格**（学びを新ルールに） | **剪定・整理**（既存ルールの健全性監査） |
| 入力 | review-result.md / decisions.md / skill-issues.md | CLAUDE.md / docs/knowledge/ / スキル frontmatter そのもの |
| 出力 | 新ルール・知識・スキルのドラフト | 各ルールの「保持/削除/統合/移動/明確化」判定 |
| 再発検知 | 担当（codify-log と突合） | しない（compound に委譲、再実装しない） |

**両輪の関係**: compound がルールを増やす → 埋もれる → rule-audit が刈る。セットで初めて健全。

---

## Step 1 — 入力収集

以下を読む。**あるものだけ使い、無いものはスキップして Step 5 のレポート冒頭に「対象外: [理由]」と明記する**:

1. プロジェクトの `CLAUDE.md` — **存在しない場合**: `AGENTS.md`・`.cursorrules` 等の相当ファイルを探し、見つかればそれを監査対象にしてよいかユーザーに確認する。相当ファイルも無ければ「監査対象のルールファイルがありません」と伝え、スキル frontmatter 検証（Step 4）のみ実施するか確認する
2. `~/.claude/CLAUDE.md`（グローバルルール。読めない場合はスキップ）
3. `docs/knowledge/` 配下（あれば。CLAUDE.md からの `@参照` の整合確認に使う）
4. `.claude/skills/*/SKILL.md` の frontmatter（あれば。Step 4 の機械検証対象）
5. `.steering/**/codify-log.md`（あれば。ルールの由来＝どの失敗から昇格したかの突合に使う。無ければ由来突合をスキップ）

```bash
find .steering -name "codify-log.md" 2>/dev/null
ls .claude/skills/*/SKILL.md 2>/dev/null
```

## Step 2 — 各ルールを 5 基準で判定

CLAUDE.md（および相当ファイル）の各ルールに以下を順に適用する:

### 基準 1 — 削除テスト（最重要）

「このルールを削除すると Claude が間違いを犯すか？」→ **No なら削除候補**。
codify-log.md に由来がある場合は「元の失敗が再発しうるか」で判断する。

### 基準 2 — 症状ベースの診断

| 症状 | 示唆 | 対応 |
|---|---|---|
| ルールがあるのに守られない | ファイルが長すぎてルールが埋もれている | 削除 or フック化（決定論的に強制） |
| ルールに書いてあることを質問してくる | 表現が曖昧 | 具体例を追加して明確化 |
| 同義のルールが複数ある | 追加時の重複チェック漏れ | 統合 |

### 基準 3 — 含める / 除外する判定

**除外候補（削除対象）**: コードを読めば分かること / 標準的な言語規約 / 「きれいなコードを書く」等の自明なプラクティス / 頻繁に変わる情報 / ファイルごとのコードベース説明・長いチュートリアル

**保持すべきもの**: 推測できないコマンド・必須環境変数 / デフォルトと異なるスタイル / テスト指示 / リポジトリのエチケット（ブランチ命名・PR 規約） / プロジェクト固有のアーキテクチャ決定 / 明白でない落とし穴

### 基準 4 — 昇格先の振り分け（CLAUDE.md から出すべきもの）

- 例外なく毎回起きるべき → **フック**（決定論的）へ移動
- ドメイン知識・たまにしか使わない → **スキル**（オンデマンド読み込み）へ移動
- 詳細な説明 → **docs/knowledge/** へ移して `@参照` に置き換え

### 基準 5 — 構造制約

配置先プロジェクトの運用ルール（CLAUDE.md の行数上限・ナレッジ保存先ルール等）が明文化されていればそれに従う。**明文化された上限が無ければ**「読まれる長さに保つ」を目安とし、基準 2 の埋もれの兆候（守られないルール）を優先指標にする。

---

## Step 3 — 行数・重複・参照整合チェック

- ルールファイルの行数を構造制約と突き合わせる
- 同義・近縁ルールの統合候補を挙げる
- `@docs/...` 参照の**参照切れ**（ファイルが存在しない）と、docs/knowledge/ 側の**孤立ファイル**（どこからも参照されず存在も知らされない）を検出する

---

## Step 4 — スキル frontmatter の機械検証

`.claude/skills/` がある場合のみ。**検証スクリプト → skills-ref CLI → 手動の順で、あるものを使う**:

```bash
# 1. 検証スクリプトがあれば使う（このマスターには scripts/validate_skills.py がある）
python3 scripts/validate_skills.py 2>/dev/null

# 2. 無ければ skills-ref CLI
skills-ref validate ./.claude/skills/[skill] 2>/dev/null

# 3. どちらも無い場合の手動同等チェック（各スキルに対して）
# - name がディレクトリ名と一致するか
# - description が引用符付き 1 行で 1024 文字以内か
# - 本文が 500 行以内か / アストラル面絵文字が無いか / metadata.version があるか
```

違反はレポートの「スキル構造」節に列挙する。`.claude/skills/` が無ければこの Step をスキップし、その旨をレポートに明記する。

---

## Step 5 — 監査レポート提示

```
## Rule Audit Report

対象: CLAUDE.md（N 行・ルール M 件）/ ~/.claude/CLAUDE.md / スキル K 個
対象外: [スキップした入力と理由]

### ルール判定
| ルール（要約） | 判定 | 理由 |
|---|---|---|
| [ルール] | 保持 | [削除テスト: 消すと X で間違える] |
| [ルール] | 削除候補 | [コードから分かる / 自明] |
| [ルール] | 移動（フック） | [毎回強制すべき → 決定論化] |
| [ルール] | 明確化 | [曖昧。具体例案: ...] |

### 参照整合
- [参照切れ・孤立ファイル]

### スキル構造
- [violation または「全スキル準拠」]

### サマリー
- 保持 X / 削除 Y / 統合 Z / 移動 W / 明確化 V
```

**判定理由は必ず付ける**（判定だけのレポートは承認判断ができない）。

---

## Step 6 — 承認分のみ適用

ユーザーが承認した項目のみ実行する:

- 削除・統合・明確化 → 対象ファイルを直接編集
- 移動 → 移動先（フックスクリプト / スキル / docs/knowledge/）の**骨組みも生成**し、元のルールを削除または `@参照` に置き換える

変更履歴は git が持つ（専用のログファイルは作らない）。適用後にコミットを提案する。

---

## Step 7 — 効果観察の案内（任意）

適用後に以下を案内する:

- 削除・明確化したルールについて、以後のセッションで挙動が変わるか（間違いが増えないか / 質問が減るか）を観察する
- 再発した場合は compound の効果検証（codify-log 突合）が検知するので、`.steering/[task]/skill-issues.md` か decisions.md に記録を残す
- 定期 GC は `/loop` や `/schedule` と相性が良い（セットアップはユーザーが明示的に行う。このスキルは自動登録しない）
