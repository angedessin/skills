# design-premortem

「この設計で作って 3 か月後に失敗した。なぜか」を先に考え、穴を design.md に書き足す。人が `/design-premortem` で呼んだときだけ動く（Claude が自分の判断では呼ばない）。

- 攻撃は文脈を持たない subagent に任せ、出てきた所見は自分で裏取りしてから採る
- 所見は design.md の末尾に追記し、Status は変えない。**追記したらここで止まり**、人間のレビューに戻す

## When NOT to use

- 設計がまだ無い → `design-doc`
- 実装済みのコードのレビュー → コードレビューのスキル
- 設計の承認 → 人間が行う。このスキルは承認しない

## 1. 対象を決める

引数にパスがあればその design.md を、無ければ会話の流れに合う `.steering/[task]/design.md` を読む。候補が複数あれば聞く。設計が会話の中にしか無いときは、その内容を対象にし、所見は会話に出す（ファイルは作らない）。

Status が `APPROVED` の設計は、人間がすでに承認している。そう伝えて、それでもかけるかを聞いて**ここで止まる**（かけるなら所見は追記するだけで、Status は変えない）。

## 2. 攻撃させる

`premortem-attacker` agent に、design.md のパスと「リポジトリを読んで裏取りしてから攻撃する」ことを渡す。会話の経緯や自分の意図は渡さない（甘くなるため）。agent が使えないときは、汎用の subagent に agent の本文と同じ指示を渡す。subagent が使えないときは自分で行い、その旨を回答に書く。

攻撃の観点（agent にも同じものがある）:

- **書かれていない振る舞い:** 0 件・エラー・読み込み中・空の入力・既存の状態との組み合わせ（選んでいた値が新しいデータに無いなど）
- **時間と順序:** 連続操作で古い応答が新しい結果を上書きする・二重送信・途中でのキャンセル
- **完了条件:** 確かめられない文（「使いやすい」）・スコープや設計に無いことを要求している
- **前提:** 設計が頼っている API・型・データが実在するか（コードで確かめる）
- **スコープ:** 大きすぎる・対象外にすべきものが混ざっている・テストの方針が無い

## 3. 裏取りして選ぶ

所見ごとに design.md と関係するコードを読み、次の 3 つに分ける。

- **採る:** 設計の本文やコードで確かめられた穴
- **捨てる:** 設計に書いてあるのに「無い」と言っている・コードと食い違う・好みの問題。所見と捨てた理由を 1 行ずつ残す（裏取りが正しかったかを人が確かめられるように）
- **人が決める:** どちらとも言えない。論点として渡す

## 4. 追記する

design.md の末尾に次の節を足す（既にあれば日付つきで追記）。本文の設計は書き換えない（直すかは人が決める）。Status 行には触らない。

```markdown
## プレモータム所見（YYYYMMDD）

### 採った穴
1. [穴] — 根拠: [設計のどこに無いか / コードのどこ] — 提案: [直し方]

### 人が決める論点
- [論点] — 選択肢と推奨

### 捨てた所見
- [所見] — 理由: [設計の該当箇所 / コードと食い違う / 好み]
```

## 5. STOP

回答に、採った穴を重要な順に短く並べ、人が決める論点を示して**ここで止まる**。設計の修正や実装には進まない。修正を頼まれたら design.md を直し、Status は DRAFT のまま人間のレビューに戻す。APPROVED の設計を直すときは、先に DRAFT に戻すかを聞く。
