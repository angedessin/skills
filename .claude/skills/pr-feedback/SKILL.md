# PR Feedback

提出済み PR に返ってきたレビューコメント・CI 失敗を処理し、修正 → 差分再レビュー → 返信までの往復を駆動する。ワークフローでは pr-create（提出）と統合（マージ）の間の Phase 3.7 に相当する。単独利用・feature-pipeline からの呼び出しの両対応。

このスキルは「エンジン＋カートリッジ」構成: 本文はツール非依存の手順と判断、具体的な git / PR ホストのコマンドは `references/commands.md`（カートリッジ）に §名で置く。**`references/commands.md` が無い場合**は、下記の手順はツール非依存なのでそのまま適用し、標準的な gh / git コマンドで実行して続行する（その旨を伝える）。

## When NOT to use

- PR の新規作成・初回プッシュ → `pr-create` の担当。このスキルは既に提出済みの PR を前提とする。
- ローカルの未提出 diff のレビュー → `frontend-code-review` の担当。
- PR に紐づかないバグ・障害の原因調査 → `debug` の担当。CI 失敗でも原因が PR の差分外にあると判明したら debug へ接続する（このスキルは差分起因の失敗を扱う）。
- CI ワークフロー自体の設定・整備 → 対象外。

---

## Step 0 — 前提チェック（不成立ならここで止まる）

会話の経緯（「さっき PR を出した」等）で前提を代用せず、毎回この場で確認する。

1. **対象 PR を特定する。** 引数で PR 番号/URL が渡されていればそれ。無ければ現在のブランチに紐づく PR を探す（具体コマンドは references/commands.md）。
2. 次のいずれかなら **ここで止まり**、案内して終了する:
   - **PR ホストの CLI が使えない / 未認証** → 手動でコメント・CI を確認する手順を案内して止まる。
   - **リモートが無い** → このリポジトリは PR 運用ではない。`pr-create` の Step 0（直コミット運用の判定）を案内して止まる。
   - **現在ブランチに紐づく PR が存在しない** → まだ提出していない。`pr-create` を案内して止まる。ここで勝手に PR を作らない。

---

## Step 1 — 収集

対象 PR について次を取得する（具体コマンドは references/commands.md の §1）:
- レビューコメント（インライン・全体レビュー本文の両方）
- レビュー状態（approved / changes_requested / commented）
- CI の失敗ジョブ名と、失敗ログの要点

**取得結果がすべてゼロ（コメントも失敗ジョブも無い）の場合** → 「未対応のフィードバックはありません」と報告して終了する。

---

## Step 2 — トリアージ

各指摘・失敗を分類する。

- **レビューコメント** を 3 分類:
  - **must-fix** — 正当で修正必須（バグ・仕様違反・明確な品質問題）
  - **要議論** — 設計判断が絡む・反論の余地がある。**この分類には反論または代替案の下書きを必ず添える**（AI の判断を人間が見て決められる形にする）
  - **nit** — 任意の好み・軽微な指摘
- **CI 失敗** を原因別に 3 分類:
  - **コード起因** — PR の差分が原因。must-fix として修正対象に入れる
  - **flaky** — 再実行で解消する見込み
  - **インフラ起因** — 環境・依存の問題で差分と無関係

**flaky / インフラ起因と判定した CI 失敗の再実行は外向き操作**（PR ホストのジョブを起動する）。Step 4 で勝手に再実行せず、Step 5 の承認範囲に含めて提示する。CI 失敗の原因が PR の差分外にあると判明した場合は、その旨を報告し `debug` への接続を提案する（このスキルでは差分外の原因調査をしない）。

---

## Step 3 — STOP（対応計画の承認・必須）

トリアージ表と対応計画を提示して **ここで止まる**。ユーザーの明示承認（「承認」「進めて」等）を待つ。

提示する内容:
- 分類済みの指摘一覧（must-fix / 要議論〔反論・代替案つき〕/ nit）
- CI 失敗の分類（コード起因 / flaky / インフラ）
- 対応計画（どれを直す・どれは議論に委ねる・どの CI を再実行提案にするか）

**このメッセージの後は修正に入らない。ユーザーの応答を待つ。** 会話の経緯を承認の代用にしない。

---

## Step 4 — 修正適用

承認された must-fix / nit を修正する。

- 修正後、**`frontend-code-review` スキルが存在すれば、指摘があった軸のみの差分再レビュー**に接続する（全軸を回さない — 往復のコストを抑える）。
- **`frontend-code-review` が無い場合**（配置先で単体利用）→ 自分で修正 diff をセルフチェックする: 指摘が実際に解消されたか・修正が新たな不整合を生んでいないか・テストが必要なら追加したかを差分で確認する。
- 要議論に分類した指摘はここでは直さない（Step 3 で承認された対応方針に従う。人間の判断に委ねた分は返信で反論・代替案を伝える）。

---

## Step 5 — STOP（外向き操作の承認・必須）

次の下書きを提示して **ここで止まる**。プッシュ・返信投稿・CI 再実行はいずれも外向き操作（内容が外部サービスに公開され、ジョブが起動される。pr-create と同じ契約）。

- コミット内容（修正のコミットメッセージ）
- 各コメントへの返信文の下書き（must-fix は対応内容、要議論は反論・代替案）
- 再実行を提案する CI ジョブ（flaky / インフラ起因）

**このメッセージの後はプッシュも返信投稿も CI 再実行もしない。ユーザーの明示承認を待つ。** 承認後にプッシュ・返信・再実行を行い、CI を追跡して結果を報告する。

---

## 出力形式

```
## PR #<番号> フィードバック対応

### トリアージ（Step 3 で提示）
| 指摘 | 分類 | 対応 |
|---|---|---|
| ... | must-fix / 要議論 / nit | 修正 / 議論に委ねる |

### CI 失敗
| ジョブ | 原因分類 | 対応 |

### 対応後（Step 5 で提示）
- コミット: <メッセージ>
- 返信下書き: <各コメントへの返信>
- 再実行提案: <CI ジョブ>
```

## Related skills

- `pr-create` — 前フェーズ。PR の新規作成・初回プッシュはそちら（このスキルは提出後の往復を担当）
- `frontend-code-review` — Step 4 で指摘軸の差分再レビューに接続する
- `debug` — CI 失敗の原因が PR の差分外にあると判明したら接続する
- `feature-pipeline` — このスキルを Phase 3.7 として呼ぶオーケストレーター
