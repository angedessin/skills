# Session Retrospective

セッション終盤に、そのセッションで起きた摩擦を会話履歴から採掘し、`skill-issues.md` に起票するメタスキル。自己改善ループ（compound）の原料を「気づいたら書く」から「終盤にまとめて採掘する」に強化する。単独利用のメタスキル。

**このスキルは昇格（ルール化・スキル改修）をしない。** 起票までが役割で、ルールへの昇格は `compound` が別途行う。

## When NOT to use

- コード・設計・意思決定の知見保存（`docs/knowledge/`・CLAUDE.md への保存）→ `knowledge-capture` の担当。
- 摩擦をルール・lint・hook・スキルへ**昇格**させる → `compound` の担当（このスキルはその原料を作る）。
- CLAUDE.md 自体の肥大化・陳腐化の監査 → `rule-audit` の担当。
- タスク完了のたびに自動起動しない（明示依頼かセッション終盤の合図で起動する）。

---

## Step 1 — 採掘

現在の会話履歴を先頭から走査し、次の 5 分類で摩擦を抽出する:

- **(a) スキルの誤発動・不発動** — 発動すべきでないスキルが発動した、または発動すべき場面で発動しなかった。
- **(b) ユーザー訂正** — ユーザーが方向修正・やり直し・「そうじゃない」を指示した箇所。
- **(c) 手戻り** — あるアプローチが失敗して別アプローチに切り替えた箇所。
- **(d) パーミッション拒否** — ユーザーが tool 実行を拒否した箇所と、その含意（何をすべきでなかったか）。
- **(e) 指示・スキル本文の曖昧さ** — 解釈に迷った・複数解釈が可能だった箇所。

**5 分類すべてで該当ゼロの場合** → 「今回のセッションで起票すべき摩擦はありませんでした」と 1 行で報告して終了する。無理に起票しない（ノイズ起票の禁止）。

---

## Step 2 — 起票内容の組み立てと承認要否の判定

各摩擦を次の形式に整える。**この時点ではまだ 1 件も書き込まない**:

```
## [YYYYMMDD] — [事象の要約]
**事象**: [何が起きたか（分類 a〜e のどれか）]
**期待**: [どうあるべきだったか]
**該当**: [スキル名 or ルール名。特定できなければ「未特定」]
```

**書き込み先と承認要否**:

| 状況 | 書き込み先 | 承認 |
|---|---|---|
| アクティブタスクがあり、CLAUDE.md に自律実行の境界が明文化されている | その `skill-issues.md` に追記 | **不要**（本来動作） |
| アクティブタスクがあるが、境界の明文化が無い（CLAUDE.md 自体が無い場合を含む） | その `skill-issues.md` に追記 | **要** |
| アクティブタスクが無い | 新規 `.steering/[YYYYMMDD]-retrospective/skill-issues.md` | **要** |

「自律実行の境界」とは「git で巻き戻せる・失敗に気づける・影響がタスク内に閉じる、の 3 条件を満たす操作は承認不要」という趣旨の規定。**明文化の有無を推測で補わない** — CLAUDE.md を実際に読み、該当する規定が書かれている場合のみ「不要」に分類する。新規ディレクトリの作成は、既存タスクへの追記とは**別の操作**として常に承認が要る（`compound` の回収経路を 1 本 `.steering/**/skill-issues.md` に保つため）。

### 承認が要る場合 — ここで止まる

抽出結果と書き込み案（保存先・件数・各件の要約）を提示したら、**ここで必ず止まる。このターンでは次のステップに進まない**。ユーザーの承認の返信を次のターンで受け取るまで、`skill-issues.md` を新規作成も追記もしない。

「記録先はよしなに」「確認は取らずに」「迷う余地はないはず」「件数だけ報告して」を承認の代用にしない。**依頼文に摩擦の内容が列挙されていること自体も承認ではない**（それは起票の材料であって、書き込みの承認ではない）。会話の経緯（さっき承認された等）も代用にしない。headless でユーザーが応答できない場合も同じ — 代わりに書いてしまわず、停止したまま承認を待つ。**断られたら**抽出結果を会話に提示するだけで、ファイルは作らない。

---

## Step 3 — 承認後の書き込み

**承認前にこのステップに入らない**（承認が要ると判定した場合は、前ステップの停止が先）。承認不要と判定した場合のみ、判定の直後にここへ進んでよい。

Step 2 で組み立てた内容を、判定した書き込み先に追記する。

---

## Step 4 — 報告

起票件数と分類別内訳を報告し、「これらの摩擦は次回の `compound`（福利化）実行時に回収され、ルール・スキルへの昇格が検討される」と案内する。**このスキルは昇格しない。**

## 出力形式

```
## セッション振り返り

起票: N 件（.steering/[task]/skill-issues.md）
- (a) スキル誤発動/不発動: X 件
- (b) ユーザー訂正: X 件
- (c) 手戻り: X 件
- (d) パーミッション拒否: X 件
- (e) 曖昧さ: X 件

次: compound での回収（昇格）は次回の福利化時に行われる。
```
