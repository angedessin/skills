# Design Premortem

`design.md` を人間レビューに出す**前**に敵対的レビューをかけ、人間の承認ゲートに届く設計の質を上げる。単独利用・design-doc の Phase 3 STOP 直前からの呼び出しの両対応。

**このスキルは設計を承認しない。** 人間の承認ゲート（design-doc の Phase 3）は維持される。役割は「人間が承認判断する前に、穴を洗い出して設計者に返す」こと。

## When NOT to use

- 実装コードのレビュー → `frontend-code-review`（および各 `review-*`）の担当。
- 既に動いているコードのバグ・障害の原因調査 → 本スキルの対象外（攻撃対象は設計文書であってコードではない）。
- 設計そのものの作成・執筆 → `design-doc` の担当（このスキルは書かれた設計を攻撃する）。
- ルールや CLAUDE.md の監査 → `rule-audit` の担当。

---

## Step 0 — 対象特定（不成立ならここで止まる）

1. 引数で design.md のパスが渡されていればそれを対象にする。無ければアクティブな `.steering/[task]/design.md` を探す。
2. **`.steering/` が無いプロジェクト** → 対象ファイルのパスをユーザーに確認する。パスが得られなければ**ここで止まる**（攻撃対象が無い）。
3. 対象 design.md の Status を確認する。**すでに `APPROVED` の場合は ここで止まり**、「承認済み設計への遡及的なプレモータムでよいか」をユーザーに確認する（本来の使いどころは承認**前**）。承認済みを勝手に攻撃・改変しない。会話の経緯を代用にしない。

---

## Step 1 — 敵対的レビュー

フレッシュな subagent に design.md を渡し、次の固定チェックリストで攻撃させる。

**渡す情報の切り分け**: 遮断するのは**会話履歴・セッションの文脈**（設計に関与した文脈が
攻撃の甘さになるため）。**リポジトリの参照は許可する** — 設計に書かれた前提（パス・
スクリプトのオプション・既存の運用方針）の裏取りができないと、前提が誤った所見が混ざり、
呼び出し側がその選別に手間を取られる。「design.md 以外を読ませない」は過剰な制約で、
バイアス排除には寄与しない。

1. **見落とされたエッジケース・異常系** — 入力の境界・失敗経路・並行操作で design が沈黙している箇所。
2. **状態管理・データフローが複雑化する未来** — 状態の持ち方・同期・単一情報源の崩れ。
3. **テスト容易性** — 「完了条件」は機械検証可能な形か。検証手段が曖昧なものはどれか。
4. **スコープ妥当性** — 「対象」に紛れた YAGNI（過剰）と、「対象外」に漏れた必須項目。
5. **3ヶ月後に後悔する理由** — 拡張・保守・引き継ぎの視点で将来コストを生む決定。
6. **「未解決の論点」の網羅性** — 人間が判断すべき論点で design が挙げていないもの。

**subagent を起動できない環境** → 自分で同じチェックリストを design.md に適用する。ただし**セッションのバイアスが残る**旨を出力の冒頭に注記する（設計に関与した文脈が攻撃の甘さになりうるため）。

---

## Step 2 — 反映

所見を design.md の `## プレモータム所見` セクションに追記する（無ければ作成する）。各所見は 3 行構成:

```
- 攻撃: [何が問題になりうるか]
  影響: [顕在化したときに何が壊れる・どれだけ後悔するか]
  提案: [設計をどう直すか / 人間の判断に委ねるか]
```

- 設計者として**反論できる**攻撃には反論を併記する（人間が両論を見て決められる形にする）。
- **設計本文を直すべき**攻撃は本文を直したうえで所見に「プレモータム反映済み」と記す。
- `.steering/` 配下（design.md 含むタスクディレクトリ）への追記は承認不要。`.steering/` が無く単体の design.md を対象にした場合は、追記内容を提示してから書き込む。

---

## Step 3 — 報告

修正した点・人間の判断に委ねる点を要約して報告し、`design-doc` の Phase 3 STOP（人間レビュー）へ戻す。**このスキル自体は設計を承認しない** — 承認は人間が行う。

---

## design-doc との連携（相互明記）

このスキルは `design-doc` の **Phase 2 と Phase 3（人間レビュー STOP）の間**に、任意ステップとして呼ばれることを想定する（design-doc 側にも同じ連携が明記されている）。小さなタスクではプレモータムは重いので必須にしない。**単独でも使用可**（既存の design.md に後からかけられる）。

## 出力形式

```
## プレモータム所見（design-premortem）

反映済み（設計本文を修正）: N 件
- [攻撃の要約] → [どう直したか]

人間の判断に委ねる: M 件
- [攻撃] / [反論] / [判断が要る論点]

（このスキルは設計を承認しない。design-doc の Phase 3 STOP に戻る）
```
