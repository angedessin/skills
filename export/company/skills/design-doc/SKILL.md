# Design Doc

新しいタスクの `.steering/` コンテキストをブートストラップし、設計ドキュメントを作成する。
**design.md 作成後は必ず止まって人間のレビューを待つ。実装には入らない。**

## When NOT to use

- 現在のタスクの `.steering/` ディレクトリがすでに存在する → `steering`（resume モード）を使う
- **1セッションで完了する見込みのタスク** → 自分の見積もりで `.steering/` の省略を確定しない。見積もりと理由を提示して「会話内設計で進めるか、`.steering/` を作るか」をユーザーに確認し、**回答を得るまで止まる**。依頼文に「小さい作業」「1セッションで終わる」等と書かれていても、それをこの確認の回答の代用にしない（規模の申告は見積もりの材料であって、縮退への同意ではない。見積もりを確認の代用にして縮退し、実際は複数セッションに及んだ実例がある）。ユーザーが会話内設計を選んだ場合のみ `.steering/` を作らず、会話内で設計方針（目的 / アプローチ / 完了条件）を提示する。設計方針を組み立てる**前**に、この分岐でも Phase 1.5 の決定インタビュー（軽量デフォルト）を行う（質問の 2 規律も同様に適用する）。**提示したらここで止まる — ユーザーの明示承認（「承認」「approved」等）を得るまで実装ファイルに触れない**（Phase 3 の STOP と同じ契約。この分岐で承認を待たず実装が始まった実例があるため、停止は省略不可）。`.steering/` が選ばれたら Phase 1 から通常どおり進める。複数セッションにまたがる見込みのタスクにはこの確認は不要 — そのまま Phase 1 → Phase 2 で作成する（作成する側が安全なデフォルト。次セッションの自分が読まないファイルを作らない、が縮退の趣旨）
- **例外: 複数フェーズを通して回すオーケストレーターから呼ばれた場合**は、タスク規模によらず上の会話内分岐を使わず、必ず Phase 2 で `.steering/` を作成する。オーケストレーターの現在地検出・承認ゲート・フラグ（`.codify-needed` / `.capture-needed`）は `design.md` 等の成果物に依存しており、会話内設計で進むとそれらが全て失われる
- **環境構築・ツール導入・設定ファイル整備のタスク**（例:「lint を導入したい」「開発環境を整えたい」「フックの動作確認」）→ 機能設計のフローに乗せない。design.md も設計前提の質問（スタック選定・設計対象の確認等）もせず、会話内でセットアップ計画（導入するツール・手順・完了の確認方法）を短く確認して進める。設計かセットアップか曖昧な依頼では、設計前提の質問より先に「今回は機能設計か、環境セットアップか」を切り分ける（環境構築の依頼に対して技術選定を質問し、機能開発の依頼だという誤った前提で進めた実例がある）
- 設計フェーズが不要な 30 分以内のバグ修正 → そのまま実装
- バグ・障害の原因調査 → 設計フローに乗せない。再現確認と原因特定を先に行い、構造に触る修正が必要と分かった時点でこのスキルに戻る
- テスト追加のみ → `tdd` スキルを直接使う

作業の途中で複数セッションにまたがると判明した場合は、その時点で Phase 2 を実行し、会話内の設計内容を design.md に転記する。

## 質問の 2 規律（このスキルの全質問に適用）

ユーザーへの質問は、この Phase 1 以降どの場面でも次の 2 規律に従う:

1. **fact / decision を分離する** — 環境（ファイル・設定・git 履歴・依存関係）を調べれば分かる**事実**はユーザーに聞かず自分で調べる。ユーザーに聞くのは**決定**（トレードオフの選択・スコープの線引き・優先順位・好み）だけ
2. **推奨案を添える** — 決定を聞くときは必ず推奨案とその理由を添え、ユーザーが「Yes / No / 修正」で返せる形にする。白紙の質問（「どうしますか？」）を投げない

---

## Phase 1 — コンテキストを確認する

**先に設計かセットアップかを切り分ける**: リクエストに環境構築・ツール導入・設定整備の要素が見える（または設計と混在している）場合は、以下の判断や設計前提の質問に入る前に「今回は機能設計か、環境セットアップか」をユーザーに確認する。セットアップなら When NOT to use の分岐に従い、この Phase には進まない。

1. ユーザーのリクエストから以下を判断:
   - **種別**: 新機能 / インシデント調査 / リファクタリング / その他
   - **タスク名**: kebab-case、≤5 words（例: `user-auth-refresh-flow`）
   - **日付**: 今日（YYYYMMDD 形式）

2. 仕様書・参考資料の有無を確認する: 依頼に仕様書・要件メモ・参考 URL・関連ファイルの指定が含まれていなければ、「仕様書や参考資料はありますか？あれば design.md に織り込みます」と一度だけ確認する。提供されたら Phase 2 の design.md（目的 / スコープ / アプローチ / 制約）に反映する。「ない」なら依頼文だけで進む（資料なしを理由に止まらない）

3. `.steering/` の既存アクティブタスクを確認:
   ```bash
   find .steering -maxdepth 1 -mindepth 1 -type d ! -name "archived" 2>/dev/null
   ```
   アクティブタスクがあれば「既存タスク [name] があります。新しいタスクとして続けますか？」と確認。
   - ユーザーが **Yes** → Phase 2 に進み新しいタスクを初期化する
   - ユーザーが **No** → `steering` スキルの resume モードで既存タスクを再開するよう案内して終了する

---

## Phase 1.5 — 決定インタビュー（design.md を書く前に決定を通す）

design.md をドラフトする**前**に、設計の骨格を決める決定をユーザーに通す。完成した文書を前にすると承認バイアスがかかる（直すより承認する方が楽になる）ため、文書化の前に聞くこと自体に価値がある。会話内設計の分岐でも、設計方針の提示前にこのフェーズを同様に行う。

1. Phase 1 の情報と環境調査から、設計への影響が最大の**決定**を **2〜3 個**選ぶ（デフォルトの深さ。それ以上は聞かない）。依存順に並べる: 目的 / スコープの線引き → アプローチの技術選択 → 構成・テスト方針。質問の 2 規律に従い、調べれば分かる事実は質問にしない
2. **1 問ずつ提示し、提示したらここで止まる** — 回答を得るまで、次の質問にも `.steering/`（design.md・tasklist.md）の作成にも進まない（複数の質問を同時に出さない — 一括提示は回答の質を下げる）。各質問には推奨案と理由を添える。依頼文の「質問はまとめて出して」「返事を待つ間にドラフトを作っておいて」等は、この停止を飛ばす承認の代用にならない — インタビュー前のドラフトは承認バイアスを生むという本フェーズの趣旨そのものに反するため、依頼されても作らず、その旨を一言添えて 1 問目で止まる。headless 等でユーザーが応答できない場合も同じ（仮置きドラフトで先に進まない）
3. 回答は Phase 2 で design.md の該当セクションに反映する。却下された案は「検討した代替案」に、先送りされた決定は「未解決の論点」に書く（**決定を会話の中に置き去りにしない** — 次セッションの自分は会話を読めない）
4. **打ち切りの脱出口**: ユーザーが「残りは推奨案で」「おまかせ」等でインタビューを打ち切ったら、残りの決定は推奨案で埋めて進み、design.md の「未解決の論点」に「推奨案で仮置き」と明記する
5. **フルグリル（明示要求時のみ）**: ユーザーが「徹底的に聞いて」「フルグリルで」等と明示的に求めた場合のみ、2〜3 個の制限を外し、決定木の各枝を共通理解に達するまで 1 問ずつ降りる。デフォルトでは行わない（毎回のフル実施は質問疲れで空返事を誘発し、逆に質を下げる）

聞くべき決定が実質ない場合（依頼文と資料で全て確定している等）は、「設計上の決定は依頼内容で確定しているため質問はありません」と一言添えてこのフェーズをスキップしてよい。ただし省略の判断を急がない — 迷ったら 1 問は聞く。

## Phase 2 — .steering/ を初期化する

`.steering/[YYYYMMDD]-[task-name]/` ディレクトリと以下の2ファイルを作成する。
テンプレートの全文は `references/templates.md` を参照。ファイルが存在しない場合は、以下の各ファイルの説明に従って合理的に生成してよい（参照不要）。

### 作成するファイル

**`design.md`** — 要求の整理 + 実装アプローチ（Status: DRAFT）
セクション見出しは日本語で書く。`Status:` 行のキーと値（DRAFT / APPROVED）は英語のまま維持する
（`impl-from-design` の前提チェックが照合する契約値）。
- 目的: 何を達成するか・なぜ必要か（1段落）
- スコープ: 対象 / 対象外
- 制約: スタック・制約事項
- 完了条件: 完了の判定基準（チェックボックス）
- アプローチ: 核となる技術判断（2〜4文）
- 主要コンポーネント: 変更対象のファイル一覧テーブル。各行には、その変更が制約に照らして
  妥当か**原本を開かずに判定できる情報**を書く（変更後のシグネチャ・追加する公開 API・
  文書なら変更後の記述など）。「◯◯を修正」とだけ書くと、制約違反していてもレビューで気づけない
- データフロー: データ・イベントの流れ
- テスト方針: Unit / Integration の方針
- 未解決の論点: 人間のレビューが必要な質問（重要）。Phase 1.5 で先送り・仮置きした決定もここに含める
- 検討した代替案: 却下した代替案

**`tasklist.md`** — design.md から導出したタスクのチェックリスト
- 実装タスク（チェックボックス）
- TDD / コードレビュー / knowledge-capture の実行チェック

### design.md を書くときの 2 つの規律

**固有名は書く時点で実在確認する** — パス・ディレクトリ名・ブランチ名・行番号・既存の運用方針を
design.md に書くときは、その場で実物を確認する。会話の早い段階で見た情報や記憶にある情報を
そのまま転記しない（リネーム・移動・方針変更が起きている可能性がある。実際に、同日リネーム済みの
旧パスを別ブランチのものと知らずに書き、既に変更されていた運用方針にも反した設計を書いた事例がある）。

**主要コンポーネントは暫定として扱い、実装前に確定させる** — 同じ情報・契約が複数箇所にあるとき、
表に挙げ漏れた箇所は片側修正として残る。表を作ったら、変更対象を表す語で全文検索して
対象を機械的に洗い出す手順を tasklist.md の先頭に入れる（この確定作業を実装の一部にする）。

### インシデント・未知領域の場合

インシデントや不明な技術が含まれる場合は Phase 2 の前に調査を行う:
- 「実装前に調査しますか？関連するファイルや情報を教えてください」と確認
- 調査結果は `design.md` の `## 調査結果` セクションに記載

## Phase 2.5 — プレモータムの提案（任意・必須にしない）

`design.md` を人間レビュー（Phase 3）に出す前に、`design-premortem` スキルが**存在すれば**敵対的レビューの実行を**提案する**。ユーザーが望めば起動し、所見を `design.md` の `## プレモータム所見` に反映してから Phase 3 に進む。

- **小さなタスクでは重い**ので必須にしない。提案だけして、断られたらそのまま Phase 3 へ。
- `design-premortem` が配置されていないプロジェクトではこの Phase を黙ってスキップする。
- プレモータムは設計を**承認しない**（承認は Phase 3 の人間ゲート）。設計の穴を洗い出して質を上げるだけ。

---

## Phase 3 — STOP（必須）

`design.md` を作成したら必ず以下のメッセージを表示して止まる:

```
設計ドキュメントを作成しました。

.steering/[date]-[task]/design.md

**実装に入る前に design.md をレビューしてください。**
特に「未解決の論点」セクションの確認をお願いします。

承認する場合は「承認」または「approved」と入力してください。
修正がある場合はその内容を教えてください。
```

**このメッセージの後は何も実装しない。ユーザーの応答を待つ。**

---

## Phase 4 — 承認後の処理

ユーザーが承認したら:

1. `design.md` の Status を更新:
   ```
   Status: **APPROVED**
   Approved: [YYYYMMDD]
   ```

2. 次のステップを案内:
   ```
   設計が承認されました。

   次は `impl-from-design` スキルで実装を開始できます。
   TDD モード（推奨）と Impl-first モードを選べます。
   ```

---

## セッション継続の場合

`.steering/` がすでに存在するタスクを再開するとき:
1. `design.md`・`tasklist.md` を読む（旧構造のタスクに `requirements.md` があればそれも読む）
2. 現状をユーザーに要約して伝える
3. 「何から続けますか？」と確認

---

## 方針転換が起きた場合

実装中にスコープや技術選択が大きく変わったとき（採用ライブラリの変更・別スキルへの置き換え・スコープの追加・削除など）は `design.md` を実態に合わせて更新する:

1. `design.md` の「アプローチ」「主要コンポーネント」「検討した代替案」を修正
2. `design.md` の「スコープ」「完了条件」を修正
3. `tasklist.md` の未完了タスクを実態に合わせて追記・削除

**更新しないと `.steering/` と実際の作業が乖離し、セッションをまたいだ再開時に混乱する。**

## Related skills

- `steering` — `.steering/` のライフサイクル全体（resume / archive / status）
- `design-premortem` — Phase 3 の前に任意で挟む敵対的レビュー（設計の穴出し・承認はしない）
- `impl-from-design` — 設計承認後の実装フェーズ
- `knowledge-capture` — セッション終了時の知見保存
