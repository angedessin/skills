# .steering/ ファイルテンプレート集

`design-doc` スキルが `.steering/[YYYYMMDD]-[task]/` を初期化する際に使うテンプレート。

---

## design.md テンプレート

要求の整理（目的 / スコープ / 完了条件）と実装アプローチを1ファイルにまとめる。

```markdown
# 設計: [task-name]

Created: [YYYYMMDD]
Status: **DRAFT — awaiting review**

## 目的

[一段落: このタスクが達成することと、なぜ必要か]

## スコープ

### 対象
- [項目]

### 対象外
- [項目]

## 制約

- Stack: Angular / TypeScript / Jasmine
- [その他の制約]

## 完了条件

- [ ] [基準1]
- [ ] [基準2]

## アプローチ

[2〜4文: 核となる技術的な判断と理由]

## 主要コンポーネント

| コンポーネント | 場所 | 責務 |
|---------------|------|------|
| [name] | `src/...` | [役割] |

## データフロー

[テキストまたは ASCII ダイアグラムでデータ・イベントの流れを説明]

## 影響範囲

[この変更が波及する範囲を書く。特にない場合は「なし」と書く]
- システム / 外部連携: [影響するAPI・サービス。なければ「なし」]
- データ: [スキーマ・保存データへの影響。なければ「なし」]
- 他チーム / 利用者: [調整が必要な相手・ユーザー体験への影響。なければ「なし」]
- リグレッション懸念: [これまで正常だった箇所が壊れうる点。なければ「なし」]

## テスト方針

- Unit: [何をユニットテストするか、Jasmine]
- Integration: [HTTP モックの方針（HttpTestingController 等）]

## 未解決の論点

- [ ] [人間のレビューが必要な質問や不明点]
- [ ] [決定インタビュー（Phase 1.5）で先送りした決定・推奨案で仮置きした決定（「推奨案で仮置き」と明記）]

## 検討した代替案

| 代替案 | 却下理由 |
|--------|----------|
| [代替案] | [却下理由] |

## 調査結果

[インシデントや未知の技術を調査した場合、その結果をここに記載]
```

承認後の Status 表記:

```markdown
Status: **APPROVED**
Approved: [YYYYMMDD]
```

## tasklist.md テンプレート

```markdown
# タスクリスト: [task-name]

Last updated: [YYYYMMDD]

## 実装

- [ ] [design.md の主要コンポーネントから導出したタスク]
- [ ] [タスク2]
- [ ] テスト作成（TDD Red フェーズ）
- [ ] 実装（TDD Green フェーズ）
- [ ] リファクタリング（TDD Refactor フェーズ）

## レビュー

- [ ] コードレビューの実施（実装コード・テストコードの両方）
- [ ] レビュー指摘の修正（review-result.md があれば参照）
- [ ] 修正後の差分再レビュー

## デプロイ
<!-- git push してブランチを MR に出すフェーズ。 -->
<!-- この節はスキルが自動で進めない（担当スキルなし）。人が実施してチェックする。 -->

- [ ] MR（マージリクエスト）の作成
- [ ] CI グリーン確認
- [ ] レビュー承認
- [ ] マージ

## 福利化
<!-- レビュー・実装で発見したパターンをルール・知識・スキルに昇格するフェーズ。 -->
<!-- knowledge-capture の完了時に .codify-needed が立ち（compound 未実行の場合）、 -->
<!-- 次セッション開始時に compound が再提案される。 -->

- [ ] compound スキルの実行（パターンをルール・知識に昇格）

## 知見保存
<!-- セッションの知見を docs/ に永続保存するフェーズ。 -->
<!-- .capture-needed フラグが次セッション開始時のリマインダーになる。 -->

- [ ] knowledge-capture スキルの実行
- [ ] steering archive モードでアーカイブ
```

## decisions.md テンプレート（任意ファイル）

タスク固有の決定事項を記録する。

```markdown
# 決定事項: [task-name]

## [YYYYMMDD] — [短いラベル]

**決定**: [決定内容]
**理由**: [なぜこの決定をしたか]
**影響**: [今後に影響すること]
```

## skill-issues.md テンプレート（任意ファイル）

セッション中に気づいたスキル自体の不具合（誤発動・指示の曖昧さ・裁量補完が必要だった箇所）を記録する。
`compound` スキルがこれを入力として読み、スキル改善の候補にする。

```markdown
# スキル課題: [task-name]

## [YYYYMMDD] — [skill-name]

**事象**: [何が起きたか（誤発動 / 指示が曖昧 / 手順が実行不能 など）]
**期待**: [本来どう動くべきだったか]
```

## review-result.md テンプレート（任意ファイル）

コードレビューの指摘とその修正状況を追跡する。**コードレビューはこれらのスキルの担当外** —
レビューはレビュー用のプラグイン・人間のレビュー等で行い、その結果をここに残しておくと
`compound` / `knowledge-capture` が知見抽出の入力として読む。
レビュー手段が独自の出力形式を持つ場合はそちらを優先してよい（このテンプレートは、
決まった置き場が無い場合の受け皿）。

```markdown
# レビュー結果: [task-name]

Date: [YYYYMMDD]
Status: PENDING | IN_PROGRESS | RESOLVED

## 指摘

| 観点 | 指摘 | ファイル | 修正状況 |
|------|------|----------|----------|
| [観点: 正当性 / テスト品質 / セキュリティ / パフォーマンス / アクセシビリティ / UI など] | [内容] | [file:line] | [ ] |

## サマリー

- 重要な問題: N件
- 修正完了: 0/N件
```

## blockers.md テンプレート（任意ファイル）

未解決の問題・依存待ちを記録する。

```markdown
# ブロッカー: [task-name]

## [YYYYMMDD] — [ブロッカーの内容]

**Status**: OPEN
**待ち先**: [誰・何を待っているか]
**解決**: [解決したら記入]
```
