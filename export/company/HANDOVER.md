# 引き継ぎプロンプト — スキルセット導入（会社側 AI に渡す）

> **この節（区切り線まで）は人が読む部分。AI に貼るのは下の「貼る範囲」だけ。**

## 使い方

1. `export/company/` を丸ごと会社リポジトリのどこかに置く（例: `_handoff/company/`）
2. **会社リポジトリのルートで** Claude Code を起動する（セットのディレクトリではなく、導入先のリポジトリで起動する）
3. 下の「貼る範囲」をコピーして貼る。**`[セットのパス]` を手順 1 で置いた実際のパスに置き換える**

## 貼る前に知っておくこと

- **手順 8 で必ず止まる。** Claude Code の再起動と信頼ダイアログの承認は人がやる必要があるため、
  貼りっぱなしで完了しない。止まったら再起動して「続けて」と伝える
- **ask（確認プロンプト）が出たかの判定は人がやる。** AI 側からは観測できないので、
  手順 9 のスモークテストは画面を見ている人が合否を判断する
- **このプロンプト自体は通しで実行した実績が無い。** 初回は横で見て、詰まった点・手順の誤りが
  あれば `.steering/[task]/skill-issues.md` に控える（セットの改訂に使える）
- **install 系が拒否されるのは仕様。** 「エラーが出た」と報告されても不具合ではない（手順 3 参照）

## この AI が触るファイル

`.claude/skills/`（新規）・`.claude/hooks/`（新規）・`.claude/settings.json`（**手動マージ**）・
`CLAUDE.md`（追記）・`.gitignore`（3 行追記）・`.npmrc`（1 行）。
既存の設定を丸ごと上書きする手順は無い。各ステップで内容を提示して承認を求めるようになっている。

このリポジトリに、外部で作成された Claude Code スキル一式を導入してください。
セットは `[セットのパス]/` にあります。中身は次の 5 点で、これがすべてです:

- `skills/` — 同梱スキル 10 ディレクトリ
- `claude-config/` — `hooks/`（6 本）と `settings.example.json`
- `MANIFEST.md` — 配置手順の一次情報
- `HANDOVER.md` — この依頼文
- `MIGRATION-GUIDE.md` — 導入判断者向け（配置作業では読まなくてよい）

**テストスクリプト・検証ツールの類は同梱していません。** 「テストを回して確認する」手順は
存在しないので、探さないでください。動作確認は下のスモークテスト（手順 9）で行います。

**まず `MANIFEST.md` の冒頭「このセットの現在の中身」と「配置先（会社）でやること」を読んでください。**
それが手順の一次情報で、この依頼文は要約です。食い違ったら MANIFEST が正です。

**MANIFEST 末尾の「変更履歴」節は読まなくて構いません。** 過去の経緯であって現在の仕様ではなく、
そこに書かれている hook の本数・スキル数・設定値は**その時点の値**です（現在の値は冒頭の表にあります）。
除外理由の背景を知りたくなったときだけ参照してください。

## 前提（このセットの性質）

- 対象プロジェクトは Angular / TypeScript / Jasmine。スキル本文はこのスタック向けに調整済み
- **コードレビューのスキルは含まれていない**。レビューはこの組織のレビュープラグインで行う前提。
  スキル本文にレビュー用スキルの名前は出てこない（「コードレビューを実施する」等の一般記述）。
  レビュー結果を `.steering/[task]/review-result.md` に置いておくと、knowledge-capture / compound
  が知見抽出の入力として読む（無ければ会話の文脈で代替するので、置かなくても動く）
- このセットは元リポジトリ（マスター）への還流経路を持たない**独立フォーク**として運用する。
  改善はこのリポジトリで直接編集してよいが、編集したスキルの frontmatter `metadata:` に
  `modified: "YYYY-MM-DD 変更概要"` を追記し、`source-commit` は消さない（MANIFEST
  「独立運用（還流なし）のルール」参照）。**ただしスキルの停止契約（承認前に書き込まない等の
  ハードストップ）は独自に書き換えないこと** — その部分の正本はマスター側にあり、再持ち込みの
  たびにマスター本文で置き換わる。停止契約に不備を見つけたら、書き換えずに
  `.steering/[task]/skill-issues.md` へ起票する
- **npx は使用禁止**（settings で deny 済み）。ローカル導入済みバイナリは
  `./node_modules/.bin/<bin>` の直接実行か `npm run` 経由で呼ぶ
- 導入作業中に新しいパッケージのインストール・外部 URL の取得はしない
- スキルが `.steering/` に作る成果物（design.md・tasklist.md）の**セクション見出しは日本語**。
  ただし `Status:` 行のキーと値（`DRAFT` / `SPIKE` / `APPROVED` の 3 値）は英語のまま扱う
  （impl-from-design の前提チェックが照合する契約値のため、日本語化・言い換えをしない）。
  `SPIKE` は破棄前提のローカル探索レーンで、push / MR / マージを行わない。
  `SPIKE` から `APPROVED` への直接昇格は禁止（一度 `DRAFT` に戻す）
- 設計・アーキテクチャの決定は `.steering/[task]/decisions.md` に「決定・理由・却下した代替案」
  の 3 点で記録する。**スキル側は決定記録の定型フォーマット（ADR 形式等）を生成しない** —
  この組織に決定記録の様式があれば、その 3 点を元に人が起票する

## 保証していないこと（作業前に把握してください）

このセットは「機械的に完全にゲートされている」わけではありません。次を前提に使ってください。

- **承認制パスへのゲートは「書き込み」と「素の rm / mv」までが対象です。** `sed -i`・任意
  インタプリタ経由・`cd … && rm` のような連鎖は塞いでいません。脅威モデルが「敵対者」ではなく
  「停止契約を滑った善意のエージェント」であるため、意図的にこの線で止めています
- **削除ゲート（`guard-gated-delete.sh`）は python3 に依存し、無い環境では黙って無効化されます。**
  python3 が見つからない・JSON 抽出に失敗した場合、この hook は沈黙して素通りします
  （フェイルオープン。警告は出ません）。配置後に `python3 --version` が通ることを**人間が**
  確認してください。通らない環境では、`rm docs/knowledge/x.md` が素通りする前提で運用します
- **PreToolUse の hook は、配置したセッション中は発火しないことがあります。** 効いているかの
  確認は Claude Code を再起動してから行ってください
- **確認プロンプト（ask）の発火はあなたからは観測できません。** 確認は人間が行います。
  「hook は効いていますか」と聞かれても、あなたには判定できないことを伝えてください
- **非対話モードでは hook の `ask` は deny に落ちます。** CI で `docs/knowledge/` 配下へ
  書き込むワークフローがあると止まる可能性があります

## 手順（MANIFEST「配置先（会社）でやること」に対応）

1. `skills/` 配下の 10 ディレクトリを `.claude/skills/` にコピーする
2. `claude-config/hooks/` の **6 本**を `.claude/hooks/` にコピーする（settings の登録は
   `$CLAUDE_PROJECT_DIR` 起点なのでパス書き換え不要）
   - 6 本中 5 本は POSIX 標準ユーティリティのみで動く。**追加のツールをインストールしない**
   - **`guard-gated-delete.sh` だけ python3（標準ライブラリのみ）に依存する。**
     `python3 --version` が通るかを確認し、結果を報告する。通らない場合でも hook の配置は行う
     （沈黙して素通りするだけで、他の hook の妨げにはならない）。ただし
     「削除ゲートが無効な状態である」ことを明示して報告する
   - **PreToolUse(Bash) の 3 本（delete / env-read / gated-write）は 1 つの matcher にまとめて
     登録する。** matcher を分けて並べると後段の hook が実行されない。`settings.example.json` は
     まとめた形になっているので、手動マージのときに分割し直さない
   - `guard-gated-write.sh` / `guard-gated-delete.sh` は PreToolUse なので、**配置したセッション中は
     発火しないことがある**。効いているかの確認は Claude Code を再起動してから行う
     （手順は MANIFEST の配置手順 2）
   - **`session-start-check.sh`（読む側）と `session-stop.sh`（書く側）は必ず対で配置する。**
     書く側だけを配ると `.capture-needed` は毎セッション立つのに拾う主体が居らず、
     knowledge-capture / compound の「セッション開始時にフラグがあれば起動」が永久に発火しない
3. `claude-config/settings.example.json` を `.claude/settings.json` に**手動マージ**する。
   既存の settings を丸ごと上書きしない。既存 allow と deny が衝突したら deny を優先。
   **マージ結果の全文を提示して、承認を得てから書き込む**
   - **`CLAUDE.md` / `docs/knowledge/**` / `docs/decisions/**` への書き込みの ask は外さない。**
     knowledge-capture は本文のハードストップで「承認前に書き込まない」を担保しているが、
     締めを尽くした状態でも承認前の書き込みが 1/4 の頻度で再現した実測がある。ask は最後の防波堤
   - **その ask と `guard-gated-write.sh` / `guard-gated-delete.sh` は 3 点セットで維持する。**
     ask はファイル編集ツールにしか掛からないため、`Bash(git show*)` のような前置一致 allow が
     あると `git show HEAD:x > CLAUDE.md` で迂回でき、`rm docs/knowledge/x.md` も素通りする。
     どれか 1 つでは防波堤にならない
   - **パッケージインストールの全面 deny はこの組織の方針として維持する。** 別の配布経路
     （install の deny を配らない構成）が存在するが、それは配布先ごとにセキュリティルールが
     異なるという方針の結果であって、こちらが漏れているのではない。**緩めない**
4. tdd のカートリッジを作る（任意 — 無くても tdd は動く）:
   - 先に**このリポジトリの実際のテスト環境を調べる**（テストの実行コマンド・Jasmine の
     実行基盤（Karma か jest-preset-angular か等）・TestBed の使い方・既存 spec の慣習）
   - 調べた結果に合わせて `.claude/skills/tdd/references/patterns.md` を**新規作成**する
     （同梱していない。誤ったスタックの例を持ち込まないため意図的に外してある）。
     見出しは SKILL.md が参照する §名（§run / §config / §setup / §unit / §component /
     §query-ladder / §network / §state / §api-layer / §coverage）に合わせ、
     Angular に対応物が無い節は省く。**SKILL.md 本文は変更しない**
5. `CLAUDE.md` に発動ポリシー節を追加する（MANIFEST の「CLAUDE.md 雛形（発動ポリシー節）」を
   ベースに、このプロジェクトの運用に合わせて調整。**追加内容を提示して承認を得てから書き込む**）
6. `.gitignore` に次の 3 行を追加する:
   `.steering/**/.capture-needed` / `.steering/**/.codify-needed` / `.steering/**/capture_done`
7. `.npmrc` に `ignore-scripts=true` を設定する（既存の .npmrc がある場合は追記。
   ビルドに postinstall が必要なパッケージが既にあるか先に確認し、あれば個別許可の
   方法を提示する）
8. ここで一度停止し、ユーザーに対話セッションの再起動と信頼ダイアログの承認を依頼する
   （未信頼ワークスペースでは permissions.allow が無効のため）
9. スモークテストを実行する:
   - 「どのスキルが使える？」で 10 スキルが一覧に出ること
   - 小さなタスク依頼で design-doc が設計提示後に**承認待ちで停止する**こと
     （勝手に実装が始まったら FAIL — 結果を報告する）
   - **`head .env.local`** の実行依頼が確認（ask）に
     落ちること。**`cat .env` では検証にならない**（settings の deny だけで止まるため、hook が
     動いていなくても同じ結果になる）
   - `.claude/hooks/` のファイルを編集 → settings の `ask` により確認が出ること
     （hook 登録が効いていることの確認）
   - **削除ゲートの確認**（python3 がある環境のみ）: `docs/knowledge/_probe.md` を作ってから
     `rm docs/knowledge/_probe.md` の実行を依頼 → **拒否（deny）される**こと。
     素通りしたら削除ゲートが効いていない。人間に報告し、`python3 --version` を再確認する
   - **開発フローが回ること** — `npm run test` / `npm run build`、および
     `./node_modules/.bin/` 経由のバイナリ実行が通ることを確認する。
     **`npm install` 等の install 系が拒否されるのは仕様であり FAIL ではない**
     （手順 3 のとおり、このセットは install を全面 deny している）。
     **拒否されたことを不具合として報告したり、deny を外して「直す」ことをしない**
   - **確認プロンプト（ask）が出たかの判定は人間に委ねる。** あなたは「実行を依頼した」ところまでを
     担当する（上の「保証していないこと」参照）

## 進め方の規律

- 各ステップで、何をどう変更するかを先に提示し、ユーザーの承認を得てから適用する
- 判断に迷ったら MANIFEST を参照し、それでも不明ならその場で停止して質問する
- 手順を飛ばさない。特に手順 4 は「実際のテスト環境を調べてから書く」の順序を守る
- 手順 8 の停止を省略しない。信頼ダイアログの承認前にスモークテストを走らせても
  `permissions.allow` が無効なので、結果が本番の挙動と一致しない
