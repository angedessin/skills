# 移行ガイド — 会社ワークフローへのスキルセット導入判断と進め方

対象読者: このセットを会社に入れるかを判断する人／実際に配置するエンジニア。
前半は「入れる価値があるか」の判断材料、後半は「どう配置するか」の手順。

## この文書の位置づけ（3 文書の役割）

同梱の 3 文書は読み手と目的が違う。**技術詳細と AI への指示は重複させず、この文書からは委譲する**（片側修正でドリフトさせないため）。

| 文書 | 読み手 | 何が書いてあるか |
|---|---|---|
| **MIGRATION-GUIDE.md**（この文書） | 導入判断者・配置エンジニア | 入れる価値・課題との対応・変更ファイル量・進め方 |
| `MANIFEST.md` | 配置エンジニア | 一次情報。セットの中身・除外理由・設定・配置先でやること全手順 |
| `HANDOVER.md` | 配置作業を代行する Claude | そのまま会社の Claude セッションに貼る導入プロンプト |

食い違ったら **MANIFEST が正**。この文書は判断と導線に徹し、細部は MANIFEST を指す。

# 第 1 部 — 移行する価値はあるか（意思決定者向け）

## 結論

**価値はある。ただし全社一括ではなく、まず 1 案件でパイロットする。**

理由は 2 つ。(1) 会社が挙げている 3 つの課題は、いずれもこのセットの設計思想が正面から解く構造になっている。(2) まだ案件に導入していない今が、習慣が固まる前に置き換える最も安い timing。腰の重さの主因である「レビュー済みスキルの書き直し」は、**このセットには発生しない**（後述）。

## 会社の 3 課題 → このセットがどう解くか

| 会社の課題 | このセットの解き方 |
|---|---|
| **1. 承認ゲートが無い**（人間が止めて確認する地点がない） | design-doc は設計提示後に**必ず停止**して人間のレビューを待つ（実装に入らない）。impl-from-design は `design.md` が `APPROVED` でなければ実装を開始しない前提チェックを持つ。これらは「説明文」ではなく**手順のハードストップ**として書かれ、フレッシュなエージェントで停止が守られることを実地検証済み。承認ゲートが規律ではなく構造になっている |
| **2. 中断・再開ができない**（単一セッション前提） | 各スキルは進行状態を `.steering/[task]/`（design.md・tasklist.md・decisions.md）に**ファイルとして残す**。次のセッションは SessionStart hook が未処理フラグとアクティブタスクを検出して現在地を復元する。オーケストレーターに閉じ込めず、成果物から途中フェーズを再開できる |
| **3. 知見管理が compound に集中**（記録とルール昇格を一手に） | 役割を 3 つに分離。**knowledge-capture**＝記録（docs/knowledge・decisions.md への保存）、**compound**＝昇格（CLAUDE.md ルール・スキル・lint への格上げ）、**rule-audit**＝剪定（肥大化・陳腐化したルールの棚卸し）。「貯める」「上げる」「削る」が別スキルなので、片方に負荷が偏らず、昇格が記録に埋もれない |

3 課題すべてが、このセットの中核的な設計判断（ハードストップ・`.steering/` によるステートレス化・知見スキルの分業）にそのまま対応している。偶然ではなく、これらは同種のワークフローで踏んだ痛点から作られている。

## dev-workflow との差分 — 何を得て、何を手放すか

会社の `dev-workflow`（implementation-plan → implementation → code-review → compound を直列実行）を、この形に置き換える:

```
design-doc（計画＋設計承認ゲート）→ 〔人間の承認〕
  → impl-from-design（実装、APPROVED 前提チェック）＋ tdd（テスト）
  → 会社のコードレビュープラグイン（そのまま）→ review-result.md に結果を置く
  → knowledge-capture（記録）／ compound（昇格）／ rule-audit（定期剪定）
```

**得るもの**: 各工程間の人間承認ゲート、セッションをまたぐ再開、知見管理の分業。

**手放すもの**: 「1 コマンドで最初から最後まで」の全自動オーケストレーション。このセットは**オーケストレーターを同梱しない**（feature-pipeline はレビューフェーズを含むため、レビュー系除外に伴って外した）。工程は各スキルを**順に呼ぶ**運用になる。

これは損失に見えて、実は課題 1・2 の裏返し。全自動の一気通貫は「承認ゲートが無い」「中断できない」と同じコインの表裏で、会社が今まさに困っている点。ゲートと再開を得る代わりに全自動を手放すのは、**課題に対する正しいトレードオフ**。将来レビュー系スキルを追加すれば feature-pipeline を戻して半自動オーケストレーションを復活させることも可能（MANIFEST「同梱しなかったもの」参照）。

## 「腰が重い」への回答 — 書き直しは発生しない

migration の主な躊躇は「レビュー済みスキルを書き直す手間」と聞いている。ここは誤解を解いておく:

- **会社のコードレビュー資産は書き直さない**。このセットは**レビュー系 8 スキルと feature-pipeline を意図的に除外**している。コードレビューは会社の既存レビュープラグインをそのまま使う前提。残るスキルからはレビュー用スキル名への参照も除去済みで、「コードレビューを実施する」等の一般記述になっている。
- **このセットのスキルも書き直さない**。同梱 10 スキルは既に Angular / TypeScript / Jasmine 向けに調整済みで、静的検証 10/10 PASS ＋第三者視点の敵対レビューを通している。あなたが本文を書く作業は無い。
- **唯一の任意作業**は tdd のカートリッジ（`references/patterns.md`）を会社の実テスト環境に合わせて新規作成すること。**無くても tdd は動く**（本文は言語非依存の判断軸のみ）。急がなくてよい。

つまり migration の実体は「**書き直し**」ではなく「**追加コピー＋設定マージ**」。既存の dev-workflow プラグインもレビュープラグインも壊さず、共存させたままパイロットできる。

## コストとリスク

- **コスト**: 配置作業は 1 セッション（コピー＋設定マージ＋スモークテスト）。新規パッケージのインストールや外部通信は不要。
- **リスク（低）**: 既存資産への破壊的変更が無く、パイロットは 1 案件に閉じる。合わなければ `.claude/skills/` から外すだけで戻せる。
- **注意点**: このセットは元リポジトリ（マスター）への還流経路を持たない**独立フォーク**。改善は会社リポジトリで直接編集してよいが、編集したスキルの frontmatter に `modified:` を残す運用が要る（MANIFEST「独立運用（還流なし）のルール」）。

# 第 2 部 — どのスキルが何を置き換えるか

会社の各工程と同梱スキルの対応（MANIFEST「会社ワークフローとの対応」の再掲・判断用）:

| 会社の工程 | 置き換える／担うスキル | 備考 |
|---|---|---|
| 1. 計画 | **design-doc** / design-premortem / steering | design-doc が設計承認ゲートの本体。design-premortem は人間レビュー前の穴出し（任意）。steering はセッション再開の管理 |
| 2. テスト計画・実装 | **impl-from-design** | `APPROVED` 前提チェックで承認前の実装を止める |
| 3. テスト実装 | **tdd** | カートリッジは任意（無くても動く） |
| 4. コードレビュー | **同梱なし**（会社のレビュープラグイン） | 結果を `.steering/[task]/review-result.md` に置くと 5. が知見の入力に読む。無ければ会話文脈で代替 |
| 5. 知見記録 | **knowledge-capture**（記録）／ **compound**（昇格） | 会社の compound 1 本を 2 スキルに分離 |
| （横断）摩擦の起票 | **session-retrospective** | セッションの引っかかりを skill-issues.md に起票（会社内の改善ループ用） |
| （定期）ルール剪定 | **rule-audit** | compound で増えるルールを剪定する対の役割 |

同梱 10 スキル: design-doc / design-premortem / steering / impl-from-design / tdd / knowledge-capture / compound / session-retrospective / rule-audit / debug。

# 第 3 部 — 配置手順（エンジニア向け）

## 変更するファイル量（先に全体像）

破壊的変更は無く、**追加とマージが主**。既存の dev-workflow／レビュープラグインはそのまま残せる。

| 操作 | 対象 | 量 |
|---|---|---|
| 追加コピー | `.claude/skills/` に 10 ディレクトリ | 10 スキル |
| 追加コピー | `.claude/hooks/` に 5 本 | session-start-check / session-stop / guard-env-read / guard-gated-write / post-edit-lint |
| **手動マージ** | `.claude/settings.json`（permissions ＋ hooks 登録） | 既存があれば丸ごと上書きせずマージ。allow と deny が衝突したら deny 優先 |
| 追記 | `CLAUDE.md` に発動ポリシー節 | 数行〜十数行 |
| 追記 | `.gitignore` | 3 行（フラグファイル除外） |
| 追記 | `.npmrc` | 1 行（`ignore-scripts=true`） |
| 任意・新規作成 | `.claude/skills/tdd/references/patterns.md` | 無くても動く。後回し可 |

## 進め方の 2 通り

**A. Claude に代行させる（推奨）** — `HANDOVER.md` の本文を会社の Claude Code セッションに貼り、`[セットのパス]` を実際のパスに置換する。HANDOVER は MANIFEST を一次情報として読ませ、各ステップで承認を取りながら配置する導入プロンプトになっている。あなたは各ステップの提示を承認していくだけ。

**B. 手動で配置する** — `MANIFEST.md`「配置先（会社）でやること」の手順に沿って自分でコピー・マージする。A と同じ手順の一次情報。

どちらでも、設定マージと CLAUDE.md 追記は**必ず全文を確認してから書き込む**（既存設定を壊さないため）。

## 設定マージの要点（settings.json）

`claude-config/settings.example.json` を既存 `.claude/settings.json` に手動マージする。主な内容:

- **permissions.deny**: パッケージインストール全般（npm/pnpm/yarn/bun/pip/brew）・`npx`（会社方針で ask から deny に強化）・`.env`／鍵ファイルの読み取り・破壊的コマンド（`rm -rf`・`git push --force`・`git reset --hard` 等）
- **permissions.ask**: `git push`・`rm -r`・settings.json／hooks 自身の編集・**`CLAUDE.md` / `docs/knowledge/**` / `docs/decisions/**` への書き込み**（ディレクトリ配下は `*` / `**` / `**/*` の 3 形式を Edit / Write 分だけ並べる — 単一形式では直下のファイルを取りこぼす）
- **hooks 登録**: SessionStart（フラグ・タスク注入）・PreToolUse/Bash（.env 読み取りガード + **承認制パスへの Bash 経由の書き込みガード**）・PostToolUse/Edit|Write（lint 差し戻し）・Stop（`.capture-needed` 生成）

既存 allow とマスター由来 deny が同じ操作で衝突したら **deny を優先**（安全側）。hook 5 本は POSIX 標準ユーティリティのみで動き、**追加インストール不要**（jq 依存は撤廃済み）。

> **パッケージインストールの全面 deny はこのセット固有の判断であって、マスターとの食い違い（漏れ）ではない。** マスターから新規プロジェクトへ配る経路（`deploy_skills.py`）では、この deny は**配らない**設定になっている（配置先の通常の依存インストールを止めてしまうため）。セキュリティルールは配布先に依存するのが正しく、この組織は npx 全面禁止・`ignore-scripts=true` と併せて意図的に強めている。**外して緩めないこと。**

## スモークテスト（配置後・必須）

配置先で対話セッションを起動し（**先に信頼ダイアログを承認する** — 未信頼だと permissions.allow が無効）:

1. 「どのスキルが使える？」→ **10 スキルが一覧に出る**（出なければ配置パス・frontmatter 破損を疑う）
2. 小さなタスク依頼 → design-doc が設計提示後に**承認待ちで停止する**（勝手に実装が始まったら FAIL）
3. `head .env.local` の実行依頼 → 確認（ask）に落ちる（**`cat .env` では検証にならない** — deny だけで止まり hook 動作を確認できないため）

## つまずきどころ

- **福利化ループが回らない** → hooks を 5 本すべて配置したか確認。`session-stop.sh`（書く側）だけでは `.capture-needed` が溜まるだけで拾われない。`session-start-check.sh`（読む側）が対で要る。
- **テストが 1 件も実行されず緑** → tdd カートリッジのテストファイル命名が会社のランナー収集パターンと不一致の可能性。既存 spec を 1 つ開いて命名規則を確認してから作る。
- **`Status:` を日本語化してしまう** → `.steering/` 成果物の見出しは日本語だが、`Status:` の値（`DRAFT`／`APPROVED`）は impl-from-design が照合する契約値。英語のまま扱う。

## 導入後の運用

- 独立フォークなのでマスターへの還流は無い。改善は会社リポジトリで直接編集してよいが、frontmatter に `modified: "YYYY-MM-DD 変更概要"` を残す（MANIFEST 参照）。
- レビュー系・feature-pipeline・e2e・pr 系 等が必要になったら、方針を確認のうえマスターから追加コピーする（MANIFEST「同梱しなかったもの」に追加時の注意あり）。debug は 2026-07-23 に同梱済み。

## パイロットの薦め（意思決定者への一言）

「まだ案件に導入していない・改善の余地がある」という現状は、移行の追い風。全自動から承認ゲート付きの手動フローへの切り替えは運用習慣に触るので、**まず 1 案件で dev-workflow と並走させて比較**し、承認ゲートと再開が実際に効くかを体感してから広げるのが安全。合わなければ `.claude/skills/` から外すだけで戻せる。
