# Design Doc

新しいタスクの `.steering/` コンテキストをブートストラップし、設計ドキュメントを作成する。
**design.md 作成後は必ず止まって人間のレビューを待つ。実装には入らない。**

## When NOT to use

- 現在のタスクの `.steering/` ディレクトリがすでに存在する → `steering`（resume モード）を使う
- **1セッションで完了する見込みのタスク** → 自分の見積もりで `.steering/` の省略を確定しない。見積もりと理由を提示して「会話内設計で進めるか、`.steering/` を作るか」をユーザーに確認し、**回答を得るまで止まる**。依頼文に「小さい作業」「1セッションで終わる」等と書かれていても、それをこの確認の回答の代用にしない（規模の申告は見積もりの材料であって、縮退への同意ではない。20260714 に WebGL 環境構築を 1 セッションと誤見積もりして確認なしで縮退した実例がある）。ユーザーが会話内設計を選んだ場合のみ `.steering/` を作らず、会話内で設計方針（Goal / Approach / 完了条件）を提示する。**提示したらここで止まる — ユーザーの明示承認（「承認」「approved」等）を得るまで実装ファイルに触れない**（Phase 3 の STOP と同じ契約。この分岐で承認を待たず実装が始まった実例があるため、停止は省略不可）。`.steering/` が選ばれたら Phase 1 から通常どおり進める。複数セッションにまたがる見込みのタスクにはこの確認は不要 — そのまま Phase 1 → Phase 2 で作成する（作成する側が安全なデフォルト。次セッションの自分が読まないファイルを作らない、が縮退の趣旨）
- **例外: `feature-pipeline` 等のオーケストレーターから呼ばれた場合**は、タスク規模によらず上の会話内分岐を使わず、必ず Phase 2 で `.steering/` を作成する。オーケストレーターの現在地検出・承認ゲート・フラグ（`.codify-needed` / `.capture-needed`）は `design.md` 等の成果物に依存しており、会話内設計で進むとそれらが全て失われる
- **環境構築・ツール導入・設定ファイル整備のタスク**（例:「lint を導入したい」「開発環境を整えたい」「フックの動作確認」）→ 機能設計のフローに乗せない。design.md も設計前提の質問（スタック選定・設計対象の確認等）もせず、会話内でセットアップ計画（導入するツール・手順・完了の確認方法）を短く確認して進める。設計かセットアップか曖昧な依頼では、設計前提の質問より先に「今回は機能設計か、環境セットアップか」を切り分ける（20260713 に環境構築の依頼へ描画スタック選定を質問して誤前提になった実例がある）
- 設計フェーズが不要な 30 分以内のバグ修正 → そのまま実装
- バグ・障害の原因調査 → `debug` を使う（原因特定が先。構造に触る修正が必要になったら debug からこのスキルに接続される）
- テスト追加のみ → `tdd` スキルを直接使う

作業の途中で複数セッションにまたがると判明した場合は、その時点で Phase 2 を実行し、会話内の設計内容を design.md に転記する。

## Phase 1 — コンテキストを確認する

**先に設計かセットアップかを切り分ける**: リクエストに環境構築・ツール導入・設定整備の要素が見える（または設計と混在している）場合は、以下の判断や設計前提の質問に入る前に「今回は機能設計か、環境セットアップか」をユーザーに確認する。セットアップなら When NOT to use の分岐に従い、この Phase には進まない。

1. ユーザーのリクエストから以下を判断:
   - **種別**: 新機能 / インシデント調査 / リファクタリング / その他
   - **タスク名**: kebab-case、≤5 words（例: `user-auth-refresh-flow`）
   - **日付**: 今日（YYYYMMDD 形式）

2. `.steering/` の既存アクティブタスクを確認:
   ```bash
   find .steering -maxdepth 1 -mindepth 1 -type d ! -name "archived" 2>/dev/null
   ```
   アクティブタスクがあれば「既存タスク [name] があります。新しいタスクとして続けますか？」と確認。
   - ユーザーが **Yes** → Phase 2 に進み新しいタスクを初期化する
   - ユーザーが **No** → `steering` スキルの resume モードで既存タスクを再開するよう案内して終了する

---

## Phase 2 — .steering/ を初期化する

`.steering/[YYYYMMDD]-[task-name]/` ディレクトリと以下の2ファイルを作成する。
テンプレートの全文は `references/templates.md` を参照。ファイルが存在しない場合は、以下の各ファイルの説明に従って合理的に生成してよい（参照不要）。

### 作成するファイル

**`design.md`** — 要求の整理 + 実装アプローチ（Status: DRAFT）
- Goal: 何を達成するか・なぜ必要か（1段落）
- Scope: In / Out of scope
- Constraints: スタック・制約事項
- Acceptance criteria: 完了条件（チェックボックス）
- Approach: 核となる技術判断（2〜4文）
- Key components: コンポーネント・ファイル一覧テーブル
- Data flow: データ・イベントの流れ
- Test strategy: Unit / Integration の方針
- Open questions: 人間のレビューが必要な質問（重要）
- Alternatives considered: 却下した代替案

**`tasklist.md`** — design.md から導出したタスクのチェックリスト
- 実装タスク（チェックボックス）
- TDD / test-review / knowledge-capture の実行チェック

### インシデント・未知領域の場合

インシデントや不明な技術が含まれる場合は Phase 2 の前に調査を行う:
- 「実装前に調査しますか？関連するファイルや情報を教えてください」と確認
- 調査結果は `design.md` の `## Research` セクションに記載

## Phase 2.5 — プレモータムの提案（任意・必須にしない）

`design.md` を人間レビュー（Phase 3）に出す前に、`design-premortem` スキルが**存在すれば**敵対的レビューの実行を**提案する**。ユーザーが望めば起動し、所見を `design.md` の `## Premortem` に反映してから Phase 3 に進む。

- **小さなタスクでは重い**ので必須にしない。提案だけして、断られたらそのまま Phase 3 へ。
- `design-premortem` が無いプロジェクト（配置先で単体利用）ではこの Phase を黙ってスキップする。
- プレモータムは設計を**承認しない**（承認は Phase 3 の人間ゲート）。設計の穴を洗い出して質を上げるだけ。

---

## Phase 3 — STOP（必須）

`design.md` を作成したら必ず以下のメッセージを表示して止まる:

```
設計ドキュメントを作成しました。

.steering/[date]-[task]/design.md

**実装に入る前に design.md をレビューしてください。**
特に「Open questions」セクションの確認をお願いします。

承認する場合は「承認」または「approved」と入力してください。
修正がある場合はその内容を教えてください。
```

**このメッセージの後は何も実装しない。ユーザーの応答を待つ。**

---

## Phase 4 — 承認後の処理

ユーザーが承認したら:

1. `design.md` の Status を更新:
   ```
   Status: **APPROVED**
   Approved: [YYYYMMDD]
   ```

2. 次のステップを案内:
   ```
   設計が承認されました。

   次は `impl-from-design` スキルで実装を開始できます。
   TDD モード（推奨）と Impl-first モードを選べます。
   ```

---

## セッション継続の場合

`.steering/` がすでに存在するタスクを再開するとき:
1. `design.md`・`tasklist.md` を読む（旧構造のタスクに `requirements.md` があればそれも読む）
2. 現状をユーザーに要約して伝える
3. 「何から続けますか？」と確認

---

## 方針転換が起きた場合

実装中にスコープや技術選択が大きく変わったとき（採用ライブラリの変更・別スキルへの置き換え・scope の追加・削除など）は `design.md` を実態に合わせて更新する:

1. `design.md` の Approach / Key components / Alternatives considered を修正
2. `design.md` の Scope / Acceptance criteria を修正
3. `tasklist.md` の未完了タスクを実態に合わせて追記・削除

**更新しないと `.steering/` と実際の作業が乖離し、セッションをまたいだ再開時に混乱する。**
