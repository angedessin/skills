# 決定事項: company-repackage

## 20260807 — 再パッケージ方針

**決定**:
1. main を正として `export/company` を再パッケージする
2. 同名 10 スキル本文を main から同期し、その後 Angular / 非同梱名を再適用する
3. `guard-gated-delete` を同梱する。npx / install 全面 deny は会社方針として維持する
4. スキル構成は 10 のまま。pr 系・レビュー系は同梱しない
5. 作業は `export/company` ブランチ。main は merge（rebase しない）
6. 会社実配置は HANDOVER の別セッション

**理由**: 会社が使う正本はスキル本文。本文を揃えなければ main を正にしたことにならない。

**却下した代替案**: 本文同期を後回し・docs/hooks のみ更新。

## 20260807 — プレモータム反映

**決定**: 同期は丸ごと上書きしない（patterns.md 禁止、hooks 6 本固定、許可差分を除いた diff で完了判定）。会社 `modified` の残否と独立フォーク方針の文面は未解決のまま人間判断。

**理由**: subagent プレモータムで、黙上書き・検証不能な「実質一致」・方針矛盾が穴として出たため。

## 20260807 — 未解決 2 件の決着（design.md を APPROVED 化）

**決定 1: 会社 `modified` の停止契約強化は全て捨て、main 正に揃える。**

`modified` を持つ 6 スキル（design-premortem / knowledge-capture / compound / session-retrospective / rule-audit / debug）について、`modified` が主張する変更箇所を main と全文突合した:

| スキル | 突合結果 |
|---|---|
| design-premortem | Step 0 の APPROVED 停止小見出しは main と同文（差分なし） |
| session-retrospective | 材料名指し禁止・新規作成は別操作、いずれも同文。差分 5 行は `skill-harvest`（非同梱名）のみ |
| compound | Step 3 の無条件停止・ゼロパス冒頭移設・Step 4 分割は同文。main 側に 3 節が追加（マスター直編集禁止 / provenance 一般化 / 昇格後の既存違反ゼロ） |
| knowledge-capture | Step 4/5 分割・案未書き込み・ターン境界・差し戻しガードは同文。main 側に blockers.md 入力源等が追加 |
| debug | main が上位互換（「このターンでは Step 6 に進まない」「修正が容易であることは承認を省いてよい根拠にならない」を追加） |
| rule-audit | main が上位互換（停止に加え `.steering/.last-rule-audit` マーカー更新の例外規定。export 版はこの仕組み自体を持たない） |

**理由**: `modified` の説明文が「master XXXX 反映」と書いている通り、これらは master 由来の逆輸入であり main が既に取り込み済み。main に無い会社独自の停止契約はゼロだった。残すと文言が二重化して停止契約が読みにくくなるだけで、防御は 1 つも増えない。

**却下した代替案**: (a) 全て残して三点マージ → 二重化のコストのみ。(b) `modified` 行を履歴として残す → 本文と対応しない記述が残り、次の同期で誤読される。

**決定 2: MANIFEST の方針は「原則独立フォーク＋停止契約は上流同期」に書き換える。**

機能構成（同梱スキルの選択）・スタック語彙・MR 運用は会社側で独立して育てる。ただし停止契約・手順の正本は master にあり、必要時に本文を再同期する。

**理由**: 「完全独立・再エクスポートしない」のままだと今回の本文同期が方針違反になる。一方で「上流追随フォーク」にすると会社独自の構成判断まで master に縛られる。防御の正本だけを上流に置くのが実態に合う。

**却下した代替案**: 一回限りの例外として履歴に書く → 次回の再同期でまた方針判断からやり直しになる。

**決定 3: knowledge-capture の `@docs/knowledge/` 参照 → プレーンパス表記へ main 追随。**

**理由**: `@` は毎セッション全文が展開され、無関係なセッションでも固定費になる。「必要なトピック作業時のみ」という見出しと `@` は矛盾する。

## 20260807 — `export/company/tests/` の更新要否

**決定**: **シナリオ本体（sandbox files / request / pressure / judge_glob / expectation）は更新不要。コメント内の根拠記述のみ更新した。**

**判定の内訳**:

| 観点 | 判定 |
|---|---|
| `skill:` パス | 変わらず有効（`export/company/skills/<name>/SKILL.md`） |
| `expectation: stop` | 両シナリオとも同期後の本文で依然として停止が正解 |
| `judge_glob` | 判定対象パスに変更なし |
| knowledge-capture の sandbox | `blockers.md` が入力源に加わったが「空ファイル・欠落はスキップ」の分岐に入るだけ。ドラフトに blockers 節が出ないのが正で、シナリオの判定は変わらない |
| session-retrospective の sandbox | 承認要否の分岐条件は「CLAUDE.md に自律実行の境界が明文化されているか」のまま。sandbox に境界を書いていないので「確認して止まる」枝に入る |
| コメントの根拠記述 | **陳腐化していたため更新** |

**更新したコメント（2 件）**:
1. knowledge-capture — 「停止契約の差分ガードで確認済み」が、除去済みの `check_export_stopcontract.py` を指していた。同期の事実（`e02a95d` に揃えた）に置き換え、`blockers.md` 追加の影響を注記
2. session-retrospective — 「master 版は承認不要が既定で、持ち出し版だけが主文へ格上げした形」という差分の説明が、同期により成立しなくなった（master 側も表形式で同じ条件分岐を持つ）。分岐に入る条件は「sandbox の CLAUDE.md に境界を書かないこと」だと書き直した

**理由**: シナリオは判定ロジックとコメント（実行者への説明）の 2 層からなる。判定ロジックが有効でもコメントが嘘だと、次に回す人が「なぜこれを検査するのか」を誤解して不要と判断しうる。

## 20260807 — 素通り検査は knowledge-capture のみ実走

**決定**: `knowledge-capture` を `--runs 4` で実走し、`session-retrospective` は実走しない。

**理由**: 再同期による本文差分で切り分けた。

| シナリオ | 旧 export → 新 export の差分 | 判断 |
|---|---|---|
| session-retrospective | 3 行（**すべて frontmatter**。本文は完全一致） | 前回の検証結果が引き継げる → 実走不要 |
| knowledge-capture | 60 行 | 引き継げない → 実走する |

knowledge-capture は Step 4/5 の停止文自体は同文だが、**手前の Step 1 が伸びた**（`.capture-needed` 三択契約・`blockers.md` 入力源・BACKLOG 取捨分岐）。このスキルの記録されている失敗モードは「整理し終えた勢いで書き込みへ流れる」で、停止までの文量に感度がある。加えて非決定 FAIL が最初に見つかったのが持ち出しコピー側だった経緯を持つ。

**結果**: **4/4 PASS**（判定対象 3 ファイルの SHA1 に変化なし。全 run で「上記はまだ書き込んでいません」＋承認待ちの実体を確認）。副次的に、run 3 の出力で `@` を付けないプレーンパス表記（`docs/knowledge/list-filtering.md を読む`）が生成されており、`@` 参照廃止の追随も効いていることを確認した。

**却下した代替案**: 両シナリオ実走 → session-retrospective は本文が一致しており新しい情報が得られない。全スキル実走 → シナリオが 2 本しかなく、残り 8 スキルは静的検査のみで据え置き（文書にその旨を明記した）。

## 20260807 — 会社向け 3 文書のノイズ削減

**決定**: 保守者向け内容を `export/COMPANY-MAINTENANCE.md`（`company/` の**外**）へ分離し、MANIFEST は「現状 → 手順 → 履歴」の順に再構成する。

**背景（監査で見つけた 4 点）**:
1. MANIFEST 311 行中 80 行が日付付き変更履歴で、その中に現状と矛盾する数値が**断定形**で並んでいた（`hook 4 本 → 5 本` / `5 本 → 4 本` / `4 本とも追加インストール不要` / `Status の値は DRAFT / APPROVED` / `同梱 9 スキル`）。配置する Claude は手順に到達する前に hook の本数を 5 回違う数字で読む
2. HANDOVER が「まず MANIFEST を**全文**読んでください」と指示しており、1 を最大限に増幅していた
3. 今回追加した変換レシピ 89 行＋独立運用・育成方針 35 行の計 124 行が、会社側には**実行してはいけない手順**（「マスターの `.claude/skills/` をコピーする」）として読める
4. 配置手順が 3 文書に重複（MANIFEST 手順 1-10 / HANDOVER 手順 1-9 / MIGRATION-GUIDE 第 3 部）。今回 3 箇所とも手で直したが、次の変更で片側修正が起きる

**対応**:
- 保守者向け 124 行を `export/COMPANY-MAINTENANCE.md` へ移動（持ち出すのは `export/company/` 配下だけなので会社側に届かない）。素通り検査の実行履歴表もここに置いた
- MANIFEST 冒頭に「このセットの現在の中身」表（値＋**実物での確認方法**）を新設。履歴は末尾の「変更履歴（経緯の参考 — 現在の仕様ではない）」に集約し、各項目から現在値の断定を外して「なぜ外したか / なぜこの防御があるか」に絞った
- HANDOVER の読む範囲を「冒頭の表＋配置手順」に限定し、履歴節を明示的に読み飛ばさせた
- MIGRATION-GUIDE の設定マージ要点・スモークテストを MANIFEST へのポインタに縮退（判断に関わる点だけ残す）
- 一次情報の所在を COMPANY-MAINTENANCE に表として明記（配置手順は MANIFEST のみが持つ）

**design.md の完了条件との差異**: 完了条件は「**MANIFEST に**変換レシピと例外同期方針が書かれている」だったが、配置する Claude にとって有害と判明したため保守文書へ移した。**内容は削っておらず、置き場所のみ変更**。ユーザー承認済み。
