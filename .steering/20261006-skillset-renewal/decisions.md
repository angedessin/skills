## 20261013 — スキルのテストを必須にする

**決定**: 残したスキルはすべてテストケースを持ち、刷新の後も回帰テストとして回す。層ごとに回す時期を分ける（静的検査は毎コミット、発動テストは説明文の変更時、効果の評価は作成時と大きな書き直し時）。刷新の判定の評価は現行の設計（3 条件・自作の実行スクリプト）のまま進め、`claude plugin eval` に変えるのは B の再現・停止契約の判定・隔離を満たせると確認できた場合だけにする
**理由**: ユーザーの判断（テストは必須）。刷新の評価は判定に 1 回使うだけで、スキルの振る舞いの定義が後に残らない。`plugin eval`（Claude Code 2.1.296 で確認）は形式が標準で回帰テストに向くが、刷新の評価の明確さは設計側（条件・採点基準・判定ルール・歪みの対策）で決まり、道具を変えても上がらない
**影響**: 完了条件に 1 行、tasklist の 5 に 1 項目を足した。課金を伴う実行は毎回見積もって承認を取る（課金ループを避ける方針は維持）

## 20261013 — 評価の道具を `claude plugin eval` にする

**決定**: 刷新の評価（A・B・C の 3 条件）も回帰テストも、Claude Code 公式の `claude plugin eval` で行う。自作の評価スクリプトは作らず、自作の passthrough（`passthrough_check.py`・`tests/passthrough/`）も停止のケースに置き換えて削除する。skill-test は静的検査と `plugin eval` をまとめる薄い入口に作り直す。機能がサーバー側で止められた場合に限り、自作の実行スクリプトで代える
**理由**: ユーザーの判断（公式のほうが長く運用できる）。自作の Python の保守は刷新の理由の一つで、CLI の変化への追従も自分の負担になる。公式ドキュメント（2026-10-13 取得）で、隔離（ユーザー設定・hooks・CLAUDE.md・メモリを読み込まない）・素のモデルとの自動比較・3 回の試行・`tool_used` による停止の判定・会話の再開（`history_file`）・費用の上限を確認した。隔離は自作の想定より強い
**却下した案**: 自作の実行スクリプト（同日の「スキルのテストを必須にする」の時点の案）。刷新の判定には十分だが、回帰テストとして残す形式を別に持つことになり、保守も自分で負う
**影響**: B はプロジェクトの CLAUDE.md を読み込めないため `append_system_prompt` で近似する（B に不利な方向の差として判定時に考慮）。複数ターンの台本は書けないため、対話が要る課題は 1 ターンの区切りに分ける。サンプルアプリは `node_modules` ごと準備スクリプトで複製する。design.md の「スキルの評価」・停止契約・テスト方針、tasklist の 4・5・8 を改訂した
