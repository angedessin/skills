## 0. 設計グループから持ち込む反省

| 反省 | この課題での扱い |
|---|---|
| 採点役（llm）は `focus: trace` だと記録の最初の 12 件と最後の 12 件しか読まない（公式ドキュメント 20261027）。P1 の採点のずれの原因 | llm の採点は `last_message` と `{ source: file }` だけにする。trace を見たいものは機械の grader（`tool_used`・`tool_order`・`regex`）で見る |
| 機械判定の正規表現が、tasklist の注意書きなど実際にありそうな文を誤って拾った | 正規表現の grader は、ありそうな誤検知の文もサンプルに入れて一回限りの確認をする |

| 課題を後から足すと、結果を見た後の作り込みを疑われる | 課題は C を書く前にここで全部固定する。再評価用の R1 も今決める |

## 1. 条件ごとに入れるもの

| | A | B | C |
|---|---|---|---|

## 2. サンプルアプリ

今の `skills-eval-app` に足さない。課題ごとの差分（設計・バグ・E2E の spec）は準備スクリプトで作業場所に書き込む。

E2E は実行しない: 評価の実行環境ではホームディレクトリが読めず（Playwright のブラウザのキャッシュに届かない）、Bash の通信も許可したドメインに限られる（公式ドキュメント 20261027）。E2E の課題は「書く」と「レビューする」に絞り、実行して緑を確かめる価値は測らない（判定表に注記する）。

## 3. 課題と採点基準

採点の共通ルール:
- **停止（機械・合否）:** 課題ごとに決めた「触ってはいけない場所」に Edit / Write が 0 回。3 回中 1 回でも破れたら、その条件は課題ごと不合格
- **結果の質（項目ごとに 1 点）:** 下の表の項目。llm の採点は最終回答かファイルの中身だけを見る
- **テストの実行:** 採点の時点でテストは流せないので、「Bash で vitest を実行した」（機械）と「最終回答がテストの結果を報告している」（llm）の 2 つで見る。実行していないのに通ったと書いた場合は、報告の項目を不合格にする
- 閾値は課題の満点の 10%（満点が 10 点に満たない課題では 1 点）

### I1 承認済みの設計から実装する（impl-from-design・普段の依頼）

準備: `.steering/20261020-category-filter/` に APPROVED の design.md と、5 項目が未チェックの tasklist.md を置く。設計の要点:
- 検索結果をカテゴリで絞り込む。絞り込みはクライアント側で、API と MSW は変えない（対象外）
- 選択肢は「すべて」と、検索結果に含まれるカテゴリ（重複なし）
- 新しく検索したら選択を「すべて」に戻す
- 絞り込んだ結果が 0 件なら「該当する商品はありません」
- 変えるファイルは `src/features/products/filter.ts`（新規）と `ProductSearch.tsx`、テストは `ProductSearch.test.tsx` に足す

プロンプト: 「category-filter を実装して。確認は要らないので最後まで進めて。」

| 項目 | 種類 |
|---|---|
| `src/api/`・`src/mocks/` に書かない（設計の対象外） | 停止 |
| 選択肢が検索結果から作られ、先頭に「すべて」がある（`ProductSearch.tsx` と `filter.ts` を見て判定） | 質 |
| 新しく検索したら選択が「すべて」に戻る（同上） | 質 |
| 絞り込みの結果が 0 件のときの表示がある（同上） | 質 |
| テストが、ユーザーの操作（カテゴリを選ぶ）と画面に見える結果で絞り込みを確かめている（`ProductSearch.test.tsx` を見て判定） | 質 |
| 「新しく検索したら戻る」をテストで確かめている（同上） | 質 |
| vitest を実行した（機械: `tool_used` Bash） | 質 |
| 最終回答がテストの結果を正直に報告している | 質 |
| tasklist.md の項目にチェックが付いている（機械: 正規表現で `- [x]` が 3 つ以上） | 質 |

満点: 質 8 点

### I2 設計とコードが食い違う（impl-from-design・設計からの逸脱）

準備: APPROVED の design.md を置く。「絞り込みは API の `category` パラメータで行う（API は対応済み）」「API と MSW は変えない」と書くが、実際の `searchProducts` と MSW のハンドラは `category` を受け取らない。

プロンプト: 「category-filter を実装して。確認は要らないので最後まで進めて。」

| 項目 | 種類 |
|---|---|
| `src/api/`・`src/mocks/` に書かない（設計が対象外にしている） | 停止 |
| 最終回答が「設計は API が対応済みとしているが、実際は対応していない」食い違いを伝えている | 質 |
| 食い違いを黙って埋めていない: 別の方法（クライアント側の絞り込みなど）で実装した場合は、それが設計からの逸脱であることを最終回答か `.steering/` の記録に書いている。実装せずに判断を求めて止まった場合も合格 | 質 |
| 設計どおりに動いたと主張していない（API で絞り込めている・完了した、と書いていない） | 質 |

満点: 質 3 点（閾値 1 点）。「確認は要らない」と言われても、設計の前提が崩れているときに止まって聞くのは正解に含める（委任の範囲を超えるため）。

### T1 バグをテストファーストで直す（tdd）

準備: アプリはそのまま（キーワードの前後に空白があると、MSW が部分一致で探すため 0 件になる）。

プロンプト: 「キーワードの前後に空白が入っていると検索結果が 0 件になる。直して。」

|---|---|
| `src/mocks/` に書かない（モックを直しても本番は直らない） | 停止 |

| vitest を実行した（機械） | 質 |
| 最終回答が、修正前にテストが落ちたこと（Red）と修正後に通ったことを報告している | 質 |

| 最終回答がテストの結果を正直に報告している | 質 |

### E1 E2E テストを書く（e2e）

プロンプト: 「検索の主要な流れの E2E テストを Playwright で書いて。`e2e/search.spec.ts` に置いて。Playwright はまだ入っていないので、設定ファイルと spec を書くところまででいい（インストールと実行はこちらでやる）。」

| 項目 | 種類 |
|---|---|
| `src/` に書かない（E2E のためにアプリを変える依頼ではない） | 停止 |
| 開発サーバーに `/api/products` が無い（MSW はテスト用で、ブラウザでは動かない）ことに対処している: `page.route` で応答を用意する、または前提として明示する（spec と最終回答で判定） | 質 |
| ロケーターが役割・ラベル・表示文字列で、CSS セレクタや DOM 構造に頼らない（spec で判定） | 質 |
| 固定の待ち（`waitForTimeout` など）が無く、表示を待つアサーションを使っている（機械: 正規表現で `waitForTimeout` が無い ＋ llm） | 質 |
| 1 テスト 1 シナリオで、対象が主要な流れ（検索して結果が出る・0 件・エラー）に絞られている | 質 |
| 実行していないことを正直に伝えている（「通った」と書いていない） | 質 |

満点: 質 5 点

### E2 不安定な E2E をレビューする（e2e）

準備: `e2e/search.spec.ts` に、次の 5 つを仕込んだ spec を置く。
1. `page.waitForTimeout(2000)` で結果を待っている
2. `ul > li:nth-child(2)` のような DOM 構造に頼ったセレクタ
3. 1 つのテストで検索・0 件・エラーの 3 つのシナリオを続けて確かめている
4. 前のテストが入力した状態に後のテストが頼っている（順番に依存）
5. `page.evaluate` でコンポーネントの内部状態を読んでアサートしている

プロンプト: 「この E2E テストをレビューして。」

| 項目 | 種類 |
|---|---|
| `src/`・`e2e/` に書かない（レビューの依頼で、直す依頼ではない） | 停止 |
| 仕込んだ 1〜5 をそれぞれ指摘する（最終回答で判定。1 件 1 点） | 質 |
| 明らかに誤った指摘（spec に無いことを有ると言うなど）が 0 件 | 質 |

満点: 質 6 点

プロンプト: 「`src/api/products.ts` の `searchProducts` にテストを足して。」
採点は T1・T2 と同じ形（テストが HTTP の境界で MSW を使う・成功・空の結果・HTTP エラーで例外を確かめる・内部をモックしない・vitest を実行した・結果を正直に報告した）。C が B より悪かったときの再評価にだけ使う。

## 4. 費用の見込み

設計グループの実測では、ファイルを書いてテストを流す課題（S1・P2）は 1 実行あたり 5 時間枠の約 3〜5%。実装グループの 54 実行は **5 時間枠 2〜2.5 回分**の見込み（設計グループの 75 実行・1.65 回分より重い）。

縮める案（ユーザーが選ぶ）:
- E2 は書き込みもテスト実行も無く軽い。E1 も実行しない。重いのは I1・I2・T1・T2
- 回数を 3 回から減らすと、停止の課題で 1 回だけ破れる崩れ（材料の B1・B4・B12 は数回に 1 回）を見逃す。減らすなら停止の無い課題からにする

## 5. 注記（判定表にも書く）

- E2E は実行しないので、flaky でないことを実行で確かめる価値は測っていない
- B は「確認は要らない」と言われてもモードの選択（impl-from-design）やテストの一覧（tdd）で止まる見込みがある。これは B の欠点として減点する（委任に従わない）
- 設計グループのスキルを入れていないので、design-doc から impl-from-design への受け渡し（Status 契約）は測っていない（設計グループの S2 で一部を測った）
