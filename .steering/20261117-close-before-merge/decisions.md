## 20261117 — 実装の前に、手で試す

- 設計は DRAFT のまま、設計だけを main に入れる（feature ブランチだけに置くと、別のブランチから見えず、試すのを忘れるため）
- hook（SessionStart の印）は、手で試した結果を見てから作るかを決める

### 試し方

APPROVED のタスクを pr-create で PR にするときに、次を手で行う。

1. PR を示すときに、design.md の「pr-create の Step 4」の予告の 1 行を添える
2. PR を作った後に、tasklist の PR の項目にチェックと番号を付け、閉じてよい状態なら、閉じる確認（索引の行・消すフォルダ・「承認したら 1 つのコミットにして push する」）を続けて出す
3. 承認されたら、`gh pr view --json state` で OPEN を確かめ、1 つのコミットにして push する
4. 気づいたこと（確認の時機・承認の回数・レビューで直しが入ったときの扱い）を、下に日付の節で書く

この PR（設計だけ・DRAFT）では、1 の「設計だけのため、閉じずに残します」の場合を試す。

### 試した結果

#### 20261117 — 1 回目: PR #32（設計だけ・DRAFT）

- 予告の 1 行（「設計だけのため、タスク 20261117-close-before-merge は閉じずに残します」）は、PR の内容と一緒に出せば目に入り、邪魔にもならなかった
- 設計どおり、DRAFT なので閉じる確認を出さず、tasklist にも触らなかった
- 設計に無い穴: PR を作った後に `.steering/` に書く記録（この試した結果・tasklist の PR の項目へのチェック）は、未コミットの変更になる。PR に載せるには、追加のコミットと push の承認がもう 1 回要る（この記録が、その 1 回）
  - 閉じる場合は、閉じるコミットに含められる（設計のとおり）
  - 閉じない場合（DRAFT・ほかの項目が残る）は、宙に浮く。設計の「tasklist の更新は未コミットのまま残し、そう伝える」は、その場の承認を後回しにしているだけ
  - 直す方向の候補: 閉じない場合は、PR の後に tasklist に触らない（PR の番号は次に tasklist を更新するときに書く）。または、追加の push の承認を PR の後の報告と一緒に取る
- 閉じる確認まで続く流れは、まだ試していない（APPROVED のタスクの PR で試す）

#### 20261120 — 2 回目: PR #33（20261116-verify-tree-guard・APPROVED）

- 予告の 1 行（「PR の後、タスク <名前> を閉じる確認を続けて出します」）は、PR の内容と一緒に出して問題なかった
- PR の後に tasklist の PR の項目へチェックと番号を付け、閉じる確認を続けて出せた。承認は「PR を作る」「閉じる」の 2 回で済んだ
- 設計に無い穴 1: 閉じる確認を、steering のスキルを呼ばずに手順を写して出した。ユーザーに「閉じるのは steering?」と聞かれ、呼び直した。設計の「steering の閉じるの手順 1〜3 で確認を出す」は、スキルを呼ぶことまで書かないと抜ける
- 設計に無い穴 2: tasklist のチェックが未コミットのため、steering の閉じるの手順 2（先にコミットするか聞く）に当たる。設計の「tasklist の更新と閉じるのを 1 つのコミットにする」と食い違う。今回は、チェックとこの記録を先にコミットし、閉じるのを別のコミットにした（2 コミット・push は 1 回）。直す方向: steering の手順 2 に「PR の項目のチェックだけなら、閉じるコミットに含めてよい」と足すか、設計を 2 コミットに合わせる
- レビューで直しが入る場合は試していない（閉じた後に直しが要れば、フォルダが無い状態で直すことになる）
