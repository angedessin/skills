# スキル群の修正: 設計 → 実装 → レビュー → 知見のループをつなぐ

（20261111 改訂: プレモータムの所見と、それを受けた決定（decisions.md）を本文に反映した）

## 目的

実装のたびに、AI が自分の作業をテストで判定する状態を機械で保証する。テストを書かないことと、テストを通すためだけのテストを避ける。あわせて、貯めた知見を設計で使い、レビューの手順を保守しやすくする。

## 背景（2026-11-10〜11 の会話の要約）

- 公式の記事（Building agents）と best practices に照らすと、今のスキル群は「1 つのループと段階的な読み込み」の形になっていて、作り直しは要らない
- 実装用のスキルは、評価で差が無かったため削除済み（`f7a8b2b`）。公式も「スキルにはモデルが知りえないことだけを書く」としている。実装の質は、スキルではなく「確かめる手段」で担保する
- 一方で、ループに次の切れ目があった
  - テストは設計のテスト方針に書かせるだけで、実装中も終了時も強制していない（Stop hook は型検査だけ）
  - `review-test` はテストファイルが変わったときだけ起動する。テストを書き忘れた差分ほど、テストの担当がレビューに参加しない
  - `docs/knowledge/` を読むのはレビューだけで、design-doc は読まない
  - steering の実装手順に、design.md の完了条件を確かめて証拠を残す指示が無い
- ユーザーの方針: テストは、AI が自分の作業を機械で判定できる唯一の手段で、AI 駆動の開発の背骨。テストを書かないことと、テストを通すためだけのテストは避けたい
- 考え方: コードとテストを同じ AI が書くので、テストは人が承認した完了条件から書き起こす。ゲートはテストがあることを、完了条件はテストが正しい仕様を見ていることを、レビューと「変える前のコードで流す」判定はテストが形だけでないことを保証する

## 振る舞い

### 共通: 実装ファイルとテストファイル

ゲートとレビューで同じ定義を使う。

- テストファイル: `*.test.*`・`*.spec.*`・`__tests__/` と `tests/`・`e2e/` の下
- 実装ファイル: 上以外の `*.ts`・`*.tsx`・`*.js`・`*.jsx`。ただし `*.d.ts`・`*.config.*`・`*.stories.*` は除く

### A1 — テストのゲート（新規 `stop-test-gate.sh`）

終了のたびに判定する。

1. 素通しにする条件: git の管理下でない・`node_modules/.bin/vitest` が無い・`jq` が無い
2. 根: 入力の `cwd` から `git rev-parse --show-toplevel` で決める（worktree でも作業中の場所を見る）
3. 対象の実装ファイル: ベースブランチとの分岐点（`merge-base`）からの差分と、未コミットの変更（未追跡は `git ls-files --others --exclude-standard`）を合わせる。削除だけの変更は除く。ベースは `origin/HEAD` → `main` の順に探し、ベースそのものの上にいるときは未コミットの変更だけを見る。対象が 0 件なら素通し
4. **関係するテストが無い**: `vitest related <実装ファイル>` で関係するテストが拾えない実装ファイルがあり、免除のファイルの「テスト不要」に載っていなければ差し戻す（終了コード 2）
5. **テストが落ちる**: 関係するテストを流し、落ちたら、失敗の文を末尾から取って差し戻す。落ちたテストが免除のファイルの「失敗を残す」に載っていれば通す
6. **時間切れ**: vitest を hook の制限時間（180 秒）より短い時間（仮に 150 秒）で打ち切り、打ち切ったら「流しきれなかった」と差し戻す。抜けるのは「失敗を残す」
7. **道具の故障**: node が無い・設定のエラー・127 など、テストの失敗でないものは区別して警告にし、差し戻さない
8. **テストを弱めた**: 差分の中のテストファイルで、`expect` が減った・`skip`・`only`・`todo` が増えたら差し戻す。正当な理由は免除のファイルに書いて抜ける
9. **同じ差分で何度も流さない**: テストが通った差分のハッシュを、プロジェクトの外（`${TMPDIR}` の下に session_id で）に残し、同じ差分なら流さない
10. **免除中のファイルが再び変わった**: タスクの外の免除（`.steering/test-exemptions.md`）に載ったファイルが変わったら、通しつつ理由を添えて警告する
11. ループ: `stop_hook_active` では緩めない（免除のファイルが逃げ道）。Claude Code の上限（連続の差し戻し 8 回。ツールを呼ぶたびに数え直し）に任せる

### 免除のファイル

- アクティブなタスクがあれば `.steering/[task]/test-exemptions.md`。タスクを閉じるとフォルダごと消える
- タスクが無ければ `.steering/test-exemptions.md`（無ければ作る）
- アクティブなタスクが複数あれば、全タスクのファイルを合わせて見る
- 設計の時点の免除は design-doc が書き、設計のレビューで人が承認する。実装中の例外は AI が書き足す。どちらも差分で人の目に入る（AI が勝手に足すことは防げないが、隠せない）
- 形:

```markdown
# テストの免除

## テスト不要
- src/components/Header.tsx — 文言の変更だけ。表示は E2E で確かめる（20261111）

## 失敗を残す
- src/features/cart/cart.test.ts — 外部 API の仕様変更待ち。#123 で直す（20261111）

## テストを弱める
- src/features/search/search.test.ts — 重複したテストの整理（20261111）
```

### A1' — 型検査の hook

`stop_hook_active` ではなく、差し戻した tsc の出力のハッシュで判定する。同じエラーが 2 回続いたときだけ警告で通す。エラーの内容が変われば再び差し戻す（`stop_hook_active` はどの Stop hook の差し戻しでも立つので、ゲートと並べると型検査が素通りになるため）。

### A2 — steering の 3・4

- 項目を進めたら、design.md の完了条件のうち、その項目に関わるものをテストで確かめる。実行したコマンドと結果（通った件数・落ちたもの）を回答に書き、tasklist の項目の注記に 1 行残す
- 確かめられない（テストの道具が無い・環境が無い）ときは、そう書いて「通った」と書かない
- テストを書かない・失敗を残すときは、免除のファイルに理由付きで書き足す

### A4 — design-doc の 4

- tasklist の実装の項目には、それを確かめるテストを含める（実装とテストを別の項目にしない）
- 設計の時点でテストを書かないと決めたファイルは、`.steering/[task]/test-exemptions.md` に理由付きで書き、design.md・tasklist と一緒にレビューに出す

### C3 — validate の検査

小さな作業にしない 3 つの条件を、ファイルごとの目印で検査する（CLAUDE.md は「3 ファイル以上」「公開している API」「承認制のパス」、design-doc は「3 ファイル以上」「公開している API」「CLAUDE.md」「docs」「.claude」）。条件の数（3 つ）の一致も見る。

### B1 — design-doc の 2

「調べる」に 1 行足す: `docs/knowledge/` があれば、触る範囲に関係する知見を読み、設計に反映する。読んだファイルは設計の構成か前提に書く。無ければ飛ばす。

### A3 — レビューのテストの担当と確かめる役

- `review-test` の起動条件に「実装ファイルが変わり、テストファイルが変わっていないとき」を足す。渡す範囲は、変更した実装ファイルと、その近くにある既存のテスト
- `review-test` の観点に、下の 3 種類を足す。`review-verify` の基準を次のとおり厳しくする

| 指摘 | 残す条件 | 確かめ方 |
|---|---|---|
| テストが足りない | 今回変えた振る舞いを具体的に挙げられ（分岐・入力）、それを通るテストが無い | コードを読んで示す |
| 形だけのテスト（壊しても通る） | 確かめているはずの振る舞いを壊しても通る | 作業ツリーのコピーで実装の該当行を壊してテストを流す。流せなければ読みで示す。報告に「どう壊したか」を必ず書く |
| 起こらない場面のテスト（過剰） | その入力が実際に来ないことをコードで示せる | 呼び出し元を読む。重要度は Low |

### C1 — 差分を数えるスクリプト

差分の行数・ファイル数・ディレクトリごとの内訳を数えるスクリプトを、スキルのフォルダに置く。本文は、スクリプトを呼ぶ 1 行と、閾値・止まり方だけにする。スクリプトが使えないときは、そう伝えて止まる（代わりの手順は残さない。スクリプトはスキルのフォルダで一緒に配るので、自己完結はスキルのフォルダ単位で満たす）。

### C2 — 担当の表示

報告の各指摘に、出した担当（bug・rules・ui-a11y・test）を添える。

### A5 — 変える前のコードで流す判定（PR 4）

レビューの中で 1 回、新しく書いた・変えたテストを、ベースのコードに持ち込んで流す。変える前でも通るテストは「新しい振る舞いを確かめていない」として報告する。import のエラーで落ちたものは「落ちた」と数える。リファクタリング（振る舞いを変えない変更）は除く。

## 論点

すべて決定済み（decisions.md）。残っているのは実装時に決める細部だけ:

- 打ち切り時間（仮に 150 秒）。実際のプロジェクトで測って見直す
- テストを弱めた判定の細部（`expect` の数え方。`expect.assertions` などの扱い）

## 却下した案

- 型検査の hook に組み込む・1 つの hook にまとめる → 型検査だけ外せなくなる
- 1 回だけ差し戻して 2 回目は通す → もう一度終われば素通りできる
- 回答の文章から目印の行（`テスト不要: <理由>`）を探す → 書き方の揺れで見落とす・引用で誤って通す・記録が残らない。免除のファイルにした
- 免除をプロジェクトの直下や docs/ に置く → 一度載せるとずっと免除のまま・古い行が溜まる。docs/ は承認制。タスクごとに置いた
- タスクの無い作業では警告だけ → テストを書かずに通れる
- 未コミットの変更だけを判定 → コミットすれば抜ける
- 実装用のスキルを作る → 評価で差が無かった。手順は steering と design-doc、強制は hook に置く
