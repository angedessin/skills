# 決定事項: skill-loop-fixes

## 20261111 — tasklist の規則（プレモータムの穴 2・論点 12）

- 決定: A。design-doc の tasklist の規則に「実装の項目には、それを確かめるテストを含める」を足す。PR 1 に入れる（ゲートと同時）
- 理由: 実装とテストを別の項目にすると、ゲートの逃げ道が毎回の手順になる。項目を終えるたびにテストで判定された状態にする
- 合わせて直すもの: 評価の s1・s2 の fixture の tasklist と `q1-right-item` の文言
- 考え方（ユーザーと合意）: テストは、AI が自分の作業を機械で判定できる唯一の手段で、AI 駆動の開発の背骨。ただしコードとテストを同じ AI が書くので、テストは人が承認した完了条件から書き起こす（A2）。ゲート（A1）はテストがあることを、完了条件（A2）はテストが正しい仕様を見ていることを保証する
- E2E・見た目のようにテストを書きにくい項目は `テスト不要: <理由>` で通す（正しい使い方として扱う）

## 20261111 — 型検査の hook との干渉（プレモータムの穴 1）

- 決定: A。`stop-typecheck.sh` を `stop_hook_active` ではなく自分の状態で判定する形に変える。差し戻した tsc の出力のハッシュを残し、同じエラーが 2 回続いたときだけ警告で通す。エラーの内容が変われば再び差し戻す
- 理由: `stop_hook_active` はどの Stop hook の差し戻しでも立つので、ゲートと並べると型検査が素通りになる
- 合わせて: PR 1 の構成に `stop-typecheck.sh` を入れる。fixture に「ゲートの差し戻しの後でも型エラーなら 2」「同じエラーが 2 回目なら 0」「エラーが変われば 2」を足す
- 却下: 1 つの hook にまとめる（型検査だけ外せなくなる）／`型エラーを残す: <理由>`（残す理由のある場面がまれで、延々と差し戻すと作業が止まる）

## 20261111 — 判定する範囲・コミットで抜ける件（論点 2・プレモータムの論点 9）

- 決定: C。実装ファイルは、ベースブランチとの分岐点（`merge-base`）からの差分と未コミットの変更を合わせて取る。テストの有無は「テストファイルが変わったか」ではなく、`vitest related <実装ファイル>` で関係するテストが拾えるかで見る
- 理由: 未コミットの変更だけだと、コミットすればゲートを抜ける（AI が自分でコミットする運用）。テストファイルの有無だけだと、ブランチの先の方で書いたテスト 1 つで全部が通る。項目ごとにテストを書く運用（穴 2 の決定）では、実装ファイルに関係するテストがあるのが普通の状態になる
- 前提（未確認）: `vitest related` で関係するテストが 0 件のときを判定できること。tasklist の 1 で確かめ、判定できなければ A（未コミットの変更だけ。コミット済みはレビューで拾う）に戻す
- 決めること（実装時）: ベースの決め方（`origin/HEAD` → `main` の順など）。ベースそのものの上にいるとき（main へ直接のコミット）は未コミットの変更だけを見る
- 弱さ: 関係するテストが既にあれば、新しい振る舞いを確かめていなくても通る。A2（完了条件をテストで確かめる）とレビュー（A3）で補う

## 20261111 — テストの時間切れ（プレモータムの論点 10）

- 決定: A。hook の中で vitest を hook の制限時間より短く（仮に 150 秒。hook の timeout は 180）打ち切り、打ち切ったら「流しきれなかった」と差し戻す。抜けるのは `テスト失敗を残す: <理由>`（書き方は増やさない）
- 理由: 時間切れの hook は差し戻さないエラーとして扱われる見込み（公式の PreToolUse の節。Stop の節には明記が無い）で、黙って通ると「テストで判定した」と誤って信じて進む
- 合わせて: README に「打ち切りが続くプロジェクトでは、この hook を外して CI に移す」目安を書く（型検査の hook と同じ扱い）。fixture に「偽の vitest が打ち切り時間を超えると 2」を足す（テストでは打ち切り時間を短く渡せるようにする）
- 弱さ: 150 秒に根拠は無く、実際のプロジェクトで測るまで仮の値

## 20261111 — 逃げ道の仕組み（プレモータムの穴 4・論点 8）と、形だけのテストへの対策

- 決定: 回答の文章から目印の行を探す仕組みはやめる。免除は専用の markdown ファイルにパス単位で書き、ゲートはそれと照らし合わせる
  - アクティブなタスクがあれば `.steering/[task]/test-exemptions.md`（タスクを閉じるとフォルダごと消える。設計の時点の免除は design-doc が design.md・tasklist と一緒に書き、実装中の例外は AI が書き足す。どちらも差分で人の目に入る）
  - タスクが無ければ `.steering/test-exemptions.md`（無ければ作る）。閉じても消えないので、免除中のファイルが再び変わったら、通しつつ理由を添えて警告する
  - アクティブなタスクが複数あるときは、全タスクの免除のファイルを合わせて見る
  - 形: `## テスト不要` と `## 失敗を残す` の 2 節に、`- <パス> — <理由>（YYYYMMDD）` の行
- 理由: 回答の文章からの検索は、書き方の揺れで見落としたり、引用で誤って通したりする。記録も残らない。ファイルにすると、記録が残り（git・PR の差分）、パスで変更と免除が対応し、通した差分のハッシュの仕組みも要らなくなる
- タスクの無い作業でも止める（警告だけにはしない）: ユーザーの方針「テストを書かない・テストを通すためのテストは避けたい」
- 決定: 「テストを弱めた」判定をゲートに入れる。テストファイルで `expect` が減った・`skip`・`only`・`todo` が増えたら差し戻す。正当な理由は免除のファイルに書いて抜ける（節は実装時に決める）
- 決定: 「変える前のコードで流す」判定を PR 4 としてレビュー（frontend-code-review）に足す。新しく書いた・変えたテストを、ベースのコードに持ち込んで流し、変える前でも通るテストを「新しい振る舞いを確かめていない」として報告する。リファクタリングは除く
- 弱さ: 「実装をなぞっているだけ」のテストは、変える前のコードでは落ちるので見つからない。完了条件（A2）とレビューと人の目に頼る。AI が免除を勝手に足すことは防げない（隠せないだけ）
- 不要になったもの: 振る舞いの 5（回答の文章の目印）・6（通した差分のハッシュ）。テストの成功時のハッシュ（穴 3）は、vitest を流す回数を減らすために残す

## 20261111 — レビューの「テストが足りない」と、確かめる役の基準（プレモータムの穴 8）

- 決定: `review-test` に観点を足し、`review-verify` の基準を次の 3 種類で厳しくする。起動の条件は A3（実装ファイルが変わればテストが変わっていなくても起動）。実装ファイルの定義はゲートと共通にする
  | 指摘 | 残す条件 | 確かめ方 |
  |---|---|---|
  | テストが足りない | 今回変えた振る舞いを具体的に挙げられ（分岐・入力）、それを通るテストが無い | コードを読んで示す |
  | 形だけのテスト（壊しても通る） | 確かめているはずの振る舞いを壊しても通る | 作業ツリーのコピーで実装の該当行を壊してテストを流す。流せなければ読みで示す。報告に「どう壊したか」を必ず書く |
  | 起こらない場面のテスト（過剰） | その入力が実際に来ないことをコードで示せる | 呼び出し元を読む。重要度は Low |
- 理由: ゲートは「関係するテストが 1 つでもあれば通す」ので、今回変えた振る舞いの抜けはレビューで補う。形だけのテストは「確かめた」と思い込ませる害がある。過剰なテストは害が小さく、足しすぎを招かないよう Low にとどめる（公式の best practices の警告）
- PR 4（変える前のコードで流す）とは両方残す: PR 4 は全部の新しいテストを機械的に、確かめる役は指摘されたテストだけを見る
- 弱さ: 壊し方がずれると正しいテストを「形だけ」と誤判定しうる（報告の「どう壊したか」で人が確かめる）。レビューの時間と費用が増える（PR 3 で測り直す）

## 20261111 — `vitest related` で関係するテストの有無を判定できるか（tasklist 1）

- 結論: 判定できる。ただし終了コードではできない。判定する範囲は C（`merge-base` からの差分＋未コミット）のまま
- 確かめ方: スクラッチパッドに一時プロジェクトを作り（vitest 5.1.0・node 24）、`a.ts`＋通るテスト・`b.ts`（テスト無し）・`c.ts`＋落ちるテスト・`d.ts`（`a.ts` を import するだけ）で `vitest related <file> --run` を流した
- 結果:
  | 対象 | 終了コード | 出力 |
  |---|---|---|
  | a.ts（テストあり・通る） | 0 | `Affected 1 of 2 test files` |
  | b.ts（テスト無し） | 0 | stdout に `No affected test files found, exiting with code 0`（`--passWithNoTests` の有無で変わらない） |
  | c.ts（テストが落ちる） | 1 | `Test Files 1 failed` |
  | d.ts（テストが import していない） | 0 | b.ts と同じ。間接に使われるだけのファイルは「テスト無し」になる |
  | 存在しないファイル | 0 | b.ts と同じ |
  | a.ts と b.ts をまとめて | 0 | `related to 2 files` と合計だけ出る。どのファイルにテストが無いかは分からない |
- `--reporter=json --outputFile=<path>` で `numTotalTestSuites` を読むと、0 件（b.ts）と 1 件以上を区別できる。`numFailedTests`・`success` で成否も取れる
- 実装への影響:
  - 有無の判定はファイルごとに `vitest related <file> --run --reporter=json --outputFile=<TMPDIR の下>` を呼び、`numTotalTestSuites == 0` を「関係するテストが無い」とする。まとめて呼ぶと区別できない
  - `--outputFile` を省くと、json の結果はプロジェクトの中（`.vitest/json/output.json`）に書かれる。必ずプロジェクトの外を指す
  - `list` には `--related` が無い（`Unknown option`）。流さずに有無だけを見る手段は無い
  - 1 回の起動は小さなプロジェクトで 0.3 秒ほど。ファイルが多いと回数が増えるので、実際のプロジェクトでの時間は打ち切り時間（150 秒）の見直しと一緒に測る
- 補足: このマシンでは、mise の設定の無い場所で `mise exec -- pnpm` を呼ぶと `~/Library/pnpm` の壊れた pnpm 11.12.0（実行ファイルが置き場所の文字列のまま）が呼ばれる。`mise exec pnpm@10.34.5 -- pnpm` と明示して避けた（20261112 にユーザーが直した。mise の設定の無い場所でも `mise exec -- pnpm` が 10.34.5 になり、壊れた 11.12.0 は消えている）

## 20261112 — ゲートの成否・打ち切り・道具の故障の細部（tasklist 4）

- テストの失敗と道具の故障の見分け方: json に `numTotalTestSuites` の数があればテストの結果、無ければ道具の故障（警告だけで差し戻さない）。vitest 5.1.0 で確かめた: テストの失敗とテストファイルの import のエラーはどちらも `numFailedTestSuites` が 1 以上で `testResults[].status == "failed"`。設定のエラーは終了コード 1 で件数が無い
- 「## 失敗を残す」の行は 2 通りに効く: テストファイルなら、そのテストが落ちても通す。実装ファイルなら、その実装ファイルはテストを流さない（時間切れの逃げ道。設計の「抜けるのは『失敗を残す』」を、何を書けば抜けられるかが分かる形にした）
- 打ち切りは全体で 1 つの持ち時間（`STOP_TEST_GATE_TIMEOUT`、既定 150 秒）。超えたら vitest をプロセスグループごと止め、判定していない残りのファイルも挙げて差し戻す。macOS に `timeout` が無いので bash の `set -m` と監視の子で書いた
- 同じ差分の記録は、テストが通り、道具の故障も無かったときだけ残す。ハッシュには根のパス（別のリポジトリと混ざらない）と免除のファイルの中身（`.steering/` を gitignore していても免除の変更で判定し直す）を入れる
- 落ちたテストの文は、末尾のログではなく json の `assertionResults[].failureMessages` の 1 行目と、テストファイルの `message`（import のエラーなど）から作る（reporter の出力の形に左右されない）
- 気づき: bash 3.2 では `$var（` のように変数の直後に全角の文字が続くと、そのバイトまで変数名として読み、出力が UTF-8 として壊れる。日本語の文を組む hook では `${var}` と囲む。fixture は stderr に U+FFFD が出たら FAIL にする

## 20261112 — テストを弱めた判定と、タスクの外の免除の警告の細部（tasklist 5。設計の論点「expect の数え方」）

- 比べ方: 差分の中のテストファイルごとに、ベース（merge-base）の版と今の版で数える。ベースに無いファイルは 0 件から、消したファイルは 0 件へ、として比べる（新しいテストファイルに todo を足しても差し戻す。テストファイルを消すのは expect が減るので差し戻す）
- expect の数え方: `expect(`・`expect.soft(`・`expect.poll(` を数える。`expect.assertions`・`expect.hasAssertions`・`expect.any` などの補助は数えない。前が英数字・`_`・`$`・`.` の場合は別の名前として数えない
- skip・only・todo: `it`・`test`・`describe`・`suite`・`bench` に `.skip`・`.skipIf`・`.only`・`.todo` が付いたもの（間に `.each` などがあってもよい）と、`xit`・`xtest`・`xdescribe`・`fit`・`fdescribe`。`ctx.skip()` や `latest.only` は数えない
- 弱めた判定は、実装ファイルが変わっていない差分でも行う（テストだけを弱める変更を見逃さない）。抜けるのは「## テストを弱める」に載せたテストファイルだけ
- 弱さ: 文字列の数え方なので、コメントや文字列の中の `expect(` も数える。1 つの expect を別の形の検査（`assert` など）に置き換えると「減った」になる。そのときは免除のファイルに書いて抜ける
- タスクの外の免除の警告: タスクが無く `.steering/test-exemptions.md` を使っているときだけ、変わったファイル（削除を除く）がそこに `- <パス> — ` で載っていれば、その行を添えて警告する。差し戻さない
