# AI駆動開発スキルシステム 改善レポート

対象: `angedessin/skills` リポジトリ `.claude/skills/` 配下 **全29スキット**
評価軸: (1) コスト構造 (2) スキルである必要性 (3) fork/model/effort設定の余地

---

## 0. まず結論より先に: 公式ツールで実測してから動くこと

このレポートはSKILL.md本文を全件読んでの**静的な**評価。実際に「どのスキルが呼ばれてない/重い」かは、憶測より公式の `/skill-doctor` コマンドの実測値の方が正確。ただし **このリポジトリは「マスター→配置先へ手動コピー」という横展開運用**のため、`/skill-doctor`は**測る場所を2箇所に分ける**必要がある。

```
/skill-doctor
```

スキルの使用履歴はセッション/プロジェクトごとに記録されるため、**どのディレクトリで実行するかによって見える実績が変わる**:

| 実行場所 | 何が測れるか | 対象スキル |
|---|---|---|
| **このマスターリポジトリ**のセッション | マスターでしか動かない運用ツールの実績。ここでの実行は**そのまま正しい実測値**になる | `skill-deploy`・`skill-harvest`・`skill-test`・`adr`・`empirical-prompt-tuning`・`security-audit` |
| **実際の配置先プロジェクト**(例: Next.jsプロジェクト)のセッション | 日常の開発フローで使うワークフロー系の本当の使用頻度・コスト | `design-doc`・`impl-from-design`・`tdd`・`debug`・`frontend-code-review`とその7サブスキル・`pr-create`/`pr-feedback`・`knowledge-capture`・`compound`等 |

マスターリポジトリだけで`/skill-doctor`を回しても、ワークフロー系スキルの実績は「スキル自体の動作確認で試し打ちした回数」にしかならず、本当の使用頻度を反映しない。**両方の場所で実行し、結果を突き合わせてから**、以下の判定を確定させてほしい。以下のセクションは実測できるまでの仮説と捉えて。

## 2. 最優先 Top 3

### 🔴 ① `frontend-code-review` の7エージェント並列フルモード

**何が問題か**: ロジック/コンポーネント変更を検知すると、`test-agent`・`impl-agent`・`security-agent`・`perf-agent`・`a11y-agent`・`correctness-agent`・`ui-agent` の**7つを単一メッセージで同時ディスパッチ**。各エージェントは新規のフレッシュコンテキストで起動するため、7回分のシステムプロンプト処理・SKILL.md読み込み・diff読み込みが毎回発生する。

**なぜ最優先か**: このシステムの中で**唯一、単一の呼び出しで確実に数倍のコストが乗る**箇所。design-docやdebugと違って「対話が本質」ではなく、純粋に処理量の問題なので、統合による削減効果が数値としてそのまま出る。

**具体策**:
- `review-performance`(110行・3軸)と`review-security`(131行・4軸)を1つの`review-quality`スキルに統合し、7エージェントを6エージェントに削減する候補。両者は「対象外」の書き方から見ても概念的に近い(どちらも「実装品質の非機能要件」という括り)
- あるいは軽量モードの発動条件（ロジック変更/コンポーネント変更の判定）を見直し、「ロジック変更かつ一定行数以上」のような閾値を足して、小さめの変更はフルモードに倒さない設計にする(現状は「上記のどれにもマッチしない→ロジック変更として扱う（安全側に倒す）」となっており、これがフルモード発動を広げている可能性がある)

### 🟡 ② `compound` の無条件フルリード

**何が問題か**: Step 1で`docs/knowledge/`(現在847行)・`CLAUDE.md`・4種類の`.steering`ファイルを**毎回無条件に全文読み**にいく。docs/knowledge/は今後も増える前提のファイルなので、実行コストがプロジェクトの成長とともに際限なく伸びる構造。

**具体策**: Step 1の重複確認とStep 4の洗い出しを`context: fork`+`agent: Explore`で切り出す。読み取り専用・大量データ・結果は要約だけでいい、という3条件が揃っているので理想的な切り出し対象。

```yaml
---
name: compound-scan
context: fork
agent: Explore
model: haiku
background: false
---
候補パターンの重複確認とルール違反箇所の洗い出しだけを行い、
候補リストと違反箇所リストを要約して返す。
```

### 🟡 ③ `design-doc` / `feature-pipeline` の常時ロード分の肥大化

**何が問題か**: `design-doc`(287行)は新機能着手のたびに毎回呼ばれる入口スキル。`feature-pipeline`(342行・全スキル中最長)もエンドツーエンド開発のたびに呼ばれる。どちらも「SPIKEレーン」「方針転換」「Phase 3.5/3.7のPR往復詳細」のような**エッジケースにしか使わない手順**が本文に混在していて、毎回のロード時にその分のトークンを払っている。

**具体策**: 以下をそれぞれ`references/`配下に切り出す:
- `design-doc`: 「SPIKEレーン」(~35行)・「方針転換が起きた場合」(~45行) → `references/spike-lane.md` / `references/pivot.md`
- `feature-pipeline`: Phase 3.5/3.7のPR関連詳細 → `references/pr-phases.md`(主要フローの計画→実装→レビューのコア部分だけ本文に残す)

## 3. カテゴリ別詳細レビュー

### 3-1. コアワークフロー(design-doc / impl-from-design / tdd / debug / e2e / steering)

| スキル | 評価 |
|---|---|
| `design-doc` | 判断軸(Phase 1.5の決定インタビューを2〜3問に制限、契約コア/付録の境界読み)が既にコスト意識的。ただし②で述べた通りエッジケース手順を本文に持ちすぎ |
| `impl-from-design` | code-explorerの発動条件分岐(単純作業ならスキップ)は模範的。`model: haiku`を明示すると微増の削減 |
| `tdd` | 「エンジン+カートリッジ」構成でreferences分離が徹底されてる。**このシステムの中で最も完成度が高いスキルの一つ**、変更不要 |
| `debug` | Step 0以外は対話が発生しない一本道のフロー。まるごと`context: fork`にできる数少ない好例(詳細は前回のやり取り参照) |

| `steering` | 軽量な読み書きのみ。resumeモードは契約コアまでしか読まない設計が既に効率的 |

### 3-2. レビュースイート(frontend-code-review + 7サブスキル)

7つのサブスキル(`test-review`・`impl-review`・`review-security`・`review-performance`・`review-a11y`・`review-correctness`・`review-ui`)は、単独利用時の設計としては**非常に良くできている**: それぞれ100〜180行と軽量で、境界線(「When NOT to use」)が相互参照されていて重複を最小化する工夫(例: `<div onClick>`の指摘はreview-a11yのみ担当、review-correctnessとreview-uiでエラー握りつぶし/表示を分担、等)が随所にある。

**問題はフルモードで7つ同時に動かしたときだけ**発生する。単独利用(「セキュリティだけ見て」等)ではこの設計のままがベスト。→ 統合を検討するなら**フルモード時の並列数を減らす目的のみ**で、review-performance/review-securityの統合を提案する(セクション2参照)。

### 3-3. 統合・PR系(pr-create / pr-feedback)

どちらも「エンジン+カートリッジ」構成でreferences/commands.mdに具体コマンドを逃がしてる。外向き操作(プッシュ・PR作成・返信投稿)の前に必ずSTOPする設計も一貫していて、コスト面で特に問題なし。変更不要。

### 3-4. ナレッジ/ルール系(knowledge-capture / compound / rule-audit / adr / session-retrospective)

| スキル | 評価 |
|---|---|
| `knowledge-capture` | 274行と長いが、blockers.mdの取捨判定など分岐が本質的に複雑。referencesに逃がせる部分が少なく、複雑さに見合った行数と判断 |
| `compound` | セクション2で述べた通り最適化余地あり |
| `rule-audit` | compoundと対になる剪定スキル。5基準の判定ロジックは全部が本文で必要な判断軸なので圧縮しにくい。現状維持 |
| `adr` | **境界線上**。「却下した代替案がある決定」だけを対象にする低頻度スキルで、knowledge-capture(decisions.mdへの追記)やcompound(ルール昇格)と機能的に隣接している。正直に言うと、**knowledge-capseptureの中の1モードとして統合しても運用は成立する**と思う。ただし現状の分離は「ADRの権威は文書ではなく批准プロセスから来る」という明確な設計思想に基づいていて、意図的。低頻度スキルなので統合してもコスト削減効果はごく小さい(呼ばれない限りコンテキストに乗らない)。**削除や統合を急ぐ理由は薄い** — 判断はチームの意思決定文化次第 |
| `session-retrospective` | 摩擦の採掘に特化した明快な責務。99行で軽量。変更不要 |

### 3-5. 設計補助(design-premortem / impl-tournament)

どちらも「常用しない」ことが明記された低頻度スキル。design-premortemはdesign-docから任意提案される形、impl-tournamentは明示的なコスト見積+承認ゲートを自前で持つ。**この2つはこのシステムの中で最も「コスト意識の実装」が優れている部類** — 変更する必要はない。

### 3-6. オーケストレーター(feature-pipeline)

342行と全体最長。ただし状態検出テーブル(現在地判定)の複雑さは本質的にこの行数を要求する— ルーターとして「今どこか」を誤判定すると全体が壊れるため、圧縮は慎重にすべき。セクション2で述べたPR関連の詳細部分のみ参照分離を推奨。

### 3-7. マスター専用ツール群(skill-deploy / skill-harvest / skill-test / empirical-prompt-tuning / security-audit)

これらは実行頻度が低い(配置・回収・回帰テスト・監査は日常の開発フローではなく、リポジトリ運用の節目でのみ動く)。**問題は「実行コスト」ではなく「常時ロードされる`description`のコンテキスト消費」**。

公式ドキュメントによると、スキルのdescriptionは`disable-model-invocation: true`を付けない限り**常にコンテキストに乗り続ける**(呼ばれるかどうかに関わらず)。これら5スキルは：

- 全て「マスター専用」または「単発のオンデマンド」であることが明言されている
- 自然文フレーズ経由でClaudeが自動発動する設計(例:「スキルを配置して」)

**トレードオフを正直に言うと**: `disable-model-invocation: true`を付けると、これらスキルの説明文がコンテキストから完全に消えてコスト削減になる。しかしその代わり、自然文での自動発動ができなくなり、`/skill-deploy`のように**コマンド名を直接タイプする**運用に変わる。29スキル中5つがマスター専用ツールなので、常時ロードされる説明文の総量としては無視できない可能性がある一方、開発体験(自然文で頼める便利さ)を犠牲にする。

**推奨**: まず**マスターリポジトリ**で`/skill-doctor`を回す(このスキル群はマスターでしか動かないため、ここでの実測がそのまま正しい実績になる)。コスト影響が大きく・かつ「結局いつも`/コマンド名`で明示的に呼んでいる」実態があるなら`disable-model-invocation: true`を追加する、という順序で判断するのが安全。

## 4. 削除候補について(正直な結論)

依頼にあった「スキルである必要性がないものは削除してよい」について、率直に言うと **29スキットの中で「スキルとして存在すべきでない」と断言できるものは見つからなかった**。理由:

- 全スキルに`When NOT to use`と`Related skills`が書かれていて、責務の重複が構造的に排除されている
- 純粋に決定論的な処理(バリデーション等)は`scripts/*.py`にすでに逃がされていて、スキル側は「承認判断」「分類」「提示」という**LLMの判断が本質的に必要な部分**だけを担っている
- 唯一境界線上なのは`adr`だが、これも「意図的な分離」であって「不要な重複」ではない

もし本当に29個が多すぎると感じるなら、**個数を減らす方向ではなく「常時ロードされる範囲を絞る」方向**(`disable-model-invocation`・`skillOverrides`の`name-only`活用)で対処するのが、この設計思想と整合的だと思う。無理に統合すると、今回読んだ限り非常に丁寧に設計された境界線を壊すことになりかねない。

## 5. モデル/エフォート設定マッピング(全29スキル)

判断基準:
- **一発回答・パターンマッチ寄り**(分類・チェックリスト照合)→ エフォートを下げても品質が落ちにくい
- **多段階のエージェント的作業**(仮説検証・設計判断・トーナメント採点)→ エフォートを下げると手戻りが増えて逆に高くつくリスクがある(実測で確認済み)ので、下げるより先に「本当に必要な思考量か」を疑う
- **見逃しのコストが高い軸**(セキュリティ・ロジック正当性・設計整合)→ モデルもエフォートも下げない
- **見逃しても後工程で拾える軸**(UI・パフォーマンス・a11yの機械的パターン)→ ミディアムまで下げる余地あり

### マスター専用ツール群

| スキル | モデル | エフォート | 根拠 |
|---|---|---|---|
| `empirical-prompt-tuning`(評価・修正判断) | Sonnet 5〜Opus 5 | high | 「軸名と判定文言は別物」のような微妙な言語化のズレを検出する判断が必要 |
| `security-audit` | Sonnet 5 | **high** | grepヒットの3分類(例示/実行指示/要確認)を誤ると危険な指示を見逃す |
| `skill-deploy` | Sonnet 5 | medium | dry-run提示と承認ゲートの運用が主体 |
| `skill-harvest` | Sonnet 5 | medium | 同上 |
| `skill-test` | Sonnet 5 | medium | スクリプト実行の編成が主体、判断自体は薄い |

**Fable 5.1について**: このシステムの中で常用を推奨できるスキルは無い。`debug`でOpus 5でも根本原因に辿り着けず失敗ループを繰り返す場合、`feature-pipeline`を無人で長時間回して失敗が多発する場合など、**「Opusで繰り返し失敗している」という実測が出てから**の最終エスカレーション先として位置づけるのが妥当。

## 6. サブエージェントの設定

このシステムでサブエージェント(または`context: fork`によるフォーク実行)が発生する箇所と、その設定案:

| 呼び出し元 | サブエージェントの役割 | モデル | エフォート | 根拠 |
|---|---|---|---|---|
| `impl-from-design` Step 1.5 | code-explorer(既存パターン調査・読み取り専用) | **Haiku 4.5** | low | 既存コードの規約を探すだけの探索作業。品質要求が低く、実測でも低エフォートで品質が落ちない典型パターン(単純な分類・検索タスク) |
| `compound` Step 1/4(前回提案のfork化) | 重複確認・grepベースの違反箇所洗い出し(読み取り専用) | **Haiku 4.5** | low | 同上。大量データの機械的走査で、結果は要約だけ返せばいい |
| `debug` Step 1〜5(前回提案のfork化) | 仮説検証・根本原因特定 | Sonnet 5(詰まればOpus 5) | **high** | 見た目は「探索」だが中身は多段階の推論。Haikuに落とすと誤診断のリスクが上がり、実装まで進んでからの手戻りという最悪コストを招く |
| `frontend-code-review` フルモード7エージェント | test/impl/security/perf/a11y/correctness/ui の各agent | Sonnet 5 | 軸ごとに上表参照(impl/security/correctnessはhigh、他はmedium) | セクション5のレビュースイート表と同じ理由 |
| `impl-tournament` Step 2 | 各アプローチの独立実装(N個) | Sonnet 5 | high(デフォルト) | スキル自身の指定を踏襲 |
| `impl-tournament` Step 3 | 採点(frontend-code-review等が無い場合のフォールバック評価) | **Opus 5** | high | 複数実装を同一基準で比較評価する判断力が必要 |
| `design-premortem` | 設計への敵対的レビュー | **Opus 5** | high | 前掲の通り、このスキルの存在意義そのものがモデルの推論力に依存する |
| `empirical-prompt-tuning` Step 2 | 対象プロンプトの実行者(白紙で読む役) | **Sonnet 5** | **デフォルト(session設定を継承)** | ここだけは意図的に「本番相当」の設定にする。評価の目的は「本番でどう振る舞うか」を測ることなので、実行者側を強くしすぎると本番の弱点を見逃す |
| `security-audit`(Step1のヒット分類を切り出す場合) | grepヒットの3分類(例示/実行指示/要確認) | Sonnet 5 | high | Haikuでは危険な指示を「例示コード」と誤判定するリスクが上がる。ここはコスト最適化の対象から外す |

**全体方針としてのモデル固定設定**:

```json
// .claude/settings.json — 明示的にmodelを指定していないサブエージェントのデフォルトをHaikuに
{
  "env": {
    "CLAUDE_CODE_SUBAGENT_MODEL": "haiku"
  }
}
```

これを土台にして、上表で「Sonnet 5」「Opus 5」と明記した個別のサブエージェント(code-explorer以外の大半)には、各サブエージェント定義またはスキルのfrontmatterで`model:`を明示的に上書きする。**「弱いデフォルト+要所だけ強く上書き」の方が、「強いデフォルト+安全な箇所だけ弱く下げる」より事故った時の被害が小さい**(上書き忘れの失敗モードが「安全側」に倒れるため)。

## 7. 実装優先順位(やるならこの順)

1. **`/skill-doctor`を2箇所で実行**して実測データを取る — マスターリポジトリ(マスター専用ツール群向け)と、実際の配置先プロジェクト(ワークフロー系スキル向け)の両方。このレポートの仮説はこの実測で検証・修正する
2. **`frontend-code-review`のフルモード**を見直す(review-performance/review-security統合 or 発動閾値の調整)— 配置先での実測でフルモード発動頻度が高いことを確認してから着手
3. **`compound`のStep1/Step4を`context: fork`化**
4. **`design-doc`/`feature-pipeline`のエッジケース手順をreferencesへ分離**
5. マスター専用5スキルの`disable-model-invocation`検討(マスターリポジトリでの実測データを見てから)
