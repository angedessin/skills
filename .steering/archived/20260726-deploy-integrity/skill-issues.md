# スキル改善候補: 20260726-deploy-integrity

## compound への申し送り: 検証工程の 2 つの混同（行動ルール化の候補）

**knowledge-capture では意図的に書かなかった。** 内容は行動ルールで compound の担当であり、
知識に書いてから昇格させると同じ内容が 2 箇所に載る（今回のセッションで塞いだ片側修正そのもの）。
昇格先が CLAUDE.md の 1 行ルールか、スキル手順か、hook による機械化かは compound が決める。

### 混同 1: 「手で確認した」を「機械化した」と扱う

**事象**: 出荷前検証（Phase 4）で `.claude/settings.json` の hook 登録と実ファイルの突合を
手作業で行い、「登録があるのにファイルが無い: なし ✓ / ファイルがあるのに登録が無い: なし ✓」と
報告した。だが**契約として encode しなかった**ため、次のセッション以降は誰も見ない状態だった。
レビューで「master 自身の settings.json の hooks 登録が突合対象外」と High で指摘された。

**期待**: 検証工程で手作業の突合をしたら、その場で「契約（機械検査）に入れる」か
「一回限りと明記する」かを決める。報告書に「確認した ✓」と書くことは、次のセッションに対して
何の保証もしない。

**昇格先の候補**: 検証系スキル（`skill-test` / `frontend-code-review`）の手順に「手作業で突合した
項目は、機械化するか一回限りと明記するかを決める」を入れる / CLAUDE.md の 1 行ルール。

### 混同 2: 「単体で効く」を「全体で効く」と扱う

**事象**: `check_asset_consistency.py` の 6 契約それぞれを故意に壊して落ちることを実測し、
「7 シナリオ全て検出」と報告した。しかし **契約の組み合わせ**（対象不在 + 別契約の違反）と
**既定の呼び出し経路**（`--verbose` 無しの実行・npm script・hook 経由）を測っていなかった。
結果、持ち出し worktree が無い環境では検査が恒久的に無音になる状態で「検査は効いている」と
記録していた。レビューで High 2 件として指摘された。

**期待**: 個別の検出力を測ったら、**呼び出し側から見た挙動**も測る。具体的には
(1) 複数の契約が同時に成立しない状態、(2) フラグを付けない既定の起動経路、(3) 呼び出し側
（hook / npm script / CI）が終了コードをどう解釈するか。

**昇格先の候補**: 同上。あるいは `docs/knowledge/skill-design-patterns.md` の
「検出ツールの規律」に統合（ただし knowledge 側には規律 #6 #7 として近い内容を入れる案が
あるため、compound 側で重複を避ける判断が必要）。

### 共通の型

どちらも「検査を書いた」ことを「検査が効いている」ことの証拠にしてしまう型で、
このリポジトリは繰り返し踏んでいる:

- 20260726: `grep -c` が 0 件で `0` を出力して exit 1 を返すため `|| echo 0` で値が `0\n0` になり
  AND 条件が効いていなかった
- 20260725: セッション中に追加した PreToolUse hook が発火せず、「機械防御を足した」という
  結論だけが残っていた
- 20260723 / 20260726: `expected_hooks()` に足したが `HOOK_REGISTRATIONS` に登録し忘れ

**書いた本人の確認は、書いた範囲の外を見ない。**
