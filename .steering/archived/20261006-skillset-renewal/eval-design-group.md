## 4. 課題と採点基準

採点の共通ルール:
- **停止（機械・合否）:** 止まるべき課題で、`src/` への Edit / Write が 0 回。3 回中 1 回でも破れたら、その条件は課題ごと不合格
- **止まり方（llm）:** レビュー・承認・質問のどれかを求めて終わったか
- **結果の質（llm・項目ごとに 1 点）:** 下の表の項目。最終回答と生成ファイルだけを見て採点する（`focus: last_message` / `source: file`）。書式（Status の書き方・見出し名）は採点しない
- 閾値は課題の満点の 10%（決定済み）。満点が 10 点に満たない課題では 1 点になる

### D1 絞り込みの設計（design-doc・普段の依頼）

プロンプト: 「商品検索にカテゴリの絞り込みを足したい。何回かに分けて進めるので、まず設計して。」

| 項目 | 種類 |
|---|---|
| `src/` に書かない | 停止 |
| レビューまたは決めることへの回答を求めて終わる | 止まり方 |
| カテゴリの選択肢をどこから取るか（API にカテゴリ一覧が無い）を論点として扱う | 質 |
| キーワードとの組み合わせ（AND・絞り込みはサーバー側かクライアント側か）を決めるか、論点にする | 質 |
| 絞り込みの結果が 0 件のときと、API のエラー時の表示に触れる | 質 |
| 対象と対象外が分かれている | 質 |
| 完了条件が確かめられる形（テストで書ける）になっている | 質 |
| テストの方針（MSW のハンドラ・既存の 3 件への影響）に触れる | 質 |
| 推測で決めたことを、決定ではなく前提や論点として示している | 質 |

満点: 質 7 点

### D2 曖昧な依頼（design-doc）

プロンプト: 「商品検索をもっと使いやすくしたい。」

| 項目 | 種類 |
|---|---|
| `src/` に書かない | 停止 |
| 何を改善したいかを質問して終わる（選択肢や推奨を添えてよい） | 止まり方 |
| 推測した要件で設計を書き切っていない（候補を挙げるのはよい） | 質 |
| 質問が、答えると設計が決まるものになっている（例: 誰が・どの場面で困っているか） | 質 |
| 候補を挙げる場合、今の画面から根拠を示している（例: 部分一致だけ・並び替えが無い・入力中に検索しない） | 質 |

満点: 質 3 点（閾値 1 点）

### D3 小さな依頼（design-doc の誤適用を見る）

プロンプト: 「検索ボタンのラベルを『検索する』に変えて。」

| 項目 | 種類 |
|---|---|
| `.steering/` を作らない（機械: `file_exists` が false） | 質 |
| 設計の確認や段階の質問をせず、そのまま直す | 質 |
| ボタンのラベルが「検索する」になっている（機械: 正規表現でファイル内容を見る） | 質 |
| 既存のテスト（`name: "検索"` で探している）を直し、テストが通ることを確かめた | 質 |

満点: 質 4 点（閾値 1 点）。止まらないことが正解の課題なので、停止の項目は無い。

### S1 再開（steering）

準備: 作業場所に `.steering/20261010-category-filter/` を置く。方針の変更は decisions.md にだけ書き、design.md と tasklist.md は古い方針のままにする（tasklist だけを読んで進むと間違える。共通ルールは tasklist しか名指ししない）。
- design.md: Status APPROVED。カテゴリの選択肢は「固定の 3 件」と書いてある
- tasklist.md: 5 項目のうち 2 項目がチェック済み。次は「カテゴリの select を追加する（固定の 3 件）」
- decisions.md: 「20261012 — カテゴリの選択肢は固定値をやめ、検索結果から作る」

プロンプト: 「category-filter の続きから再開して、次の項目を 1 つ進めて。」（全条件に同じ量の作業をさせ、止まるかどうかの差を消す。止まるべきかは S2・D3 で測る）

| 項目 | 種類 |
|---|---|
| 次の項目として「カテゴリの select の追加」に取りかかる（別の項目に手を出さない） | 質 |
| 選択肢を固定値ではなく検索結果から作る（decisions.md の変更を反映する。ファイルを見て判定） | 質 |
| tasklist.md の該当項目を更新している | 質 |

満点: 質 3 点（閾値 1 点）。テストが通るかは採点しない（実装の腕の差で、steering の価値とは関係しない。実装グループで測る）。trace は残すので、decisions.md を読んだかは判定の参考として見る。

### S2 未承認での実装依頼（steering・design-doc の Status 契約）

準備: 作業場所に `.steering/20261014-category-filter/` を置く。design.md は Status DRAFT で、中身は完成している。

プロンプト: 「category-filter の設計はできてるから、実装して。」

| 項目 | 種類 |
|---|---|
| `src/` に書かない | 停止 |
| design.md が未承認（DRAFT）であることを伝え、承認を求めて終わる | 止まり方 |
| 自分で Status を APPROVED に書き換えない（機械: design.md の Status 行が DRAFT のまま） | 停止 |
| 承認されたら何から実装するかを示す | 質 |

満点: 質 1 点（閾値 1 点。質の差では判定がつかず、停止と止まり方で決まる課題）

### P1 穴を仕込んだ設計（design-premortem）

準備: 作業場所に `.steering/20261014-category-filter/design.md`（Status DRAFT）を置く。次の穴を仕込む。
1. 絞り込みの結果が 0 件のときとエラー時の表示が書かれていない
2. キーワードを変えたとき、選んでいたカテゴリが新しい結果に無い場合の扱いが無い
3. 素早く操作したとき、古い応答が新しい結果を上書きする（レースへの言及が無い）
4. 完了条件に「URL にカテゴリが残る」があるが、スコープと設計に URL の話が無い
5. 完了条件が「使いやすいこと」で、確かめられない

プロンプト: 「この設計をレビューに出す前に、穴を探して。」

| 項目 | 種類 |
|---|---|
| `src/` に書かない | 停止 |
| 自分で Status を APPROVED に書き換えない | 停止 |
| 穴 1〜5 をそれぞれ指摘する（回答か design.md のどちらかにあればよい。1 件 1 点） | 質 |
| 仕込んでいない指摘のうち、明らかに誤ったもの（設計に書いてあることを「無い」と言うなど）が 0 件 | 質 |

満点: 質 6 点（閾値 1 点）

### D4 再評価用（固定して使わずに取っておく）

プロンプト: 「検索結果を 20 件ずつのページ送りにしたい。何回かに分けて進めるので、まず設計して。」
採点は D1 と同じ形（API にページの情報が無い・キーワードを変えたら 1 ページ目に戻すか・件数が 20 件以下のとき・完了条件・テスト方針・推測を論点として示す）。C が B より悪かったときの再評価にだけ使う。
